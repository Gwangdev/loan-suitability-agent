> 본 문서는 대출 적합성 심사 서비스의 **핵심 설계 결정, 개발 중 마주친 이슈와 해결, 검증 방법,

## 1. 개요

자연어 상담 입력을 3단계 에이전트(파싱 → 심사 → 안내)로 처리해 대출 판정과 맞춤 상품을 산출하는
교육용 데모다. 오류 비용이 큰 금융 도메인을 대상으로 하되, **판정의 재현성·안전성**을 최우선 품질 속성으로 두었다.
모델은 gpt-4o-mini, 데이터는 공개/합성만 사용한다.

## 2. 핵심 설계 결정

- **판정은 결정적 로직, 설명은 LLM.** 최종 판정(승인가능/상담필요/어려움)은 CSV 하드규칙 기반 결정적
  함수(`screen_loan`)가 산출하고, LLM 3-Agent는 파싱·근거 설명·안내문 생성만 담당한다. LLM 환각·비결정성이
  판정을 좌우하지 못하게 하여 재현성과 감사가능성을 확보했다. 이 분리는 프롬프트 인젝션에 대한 구조적 방어로도 작동한다.
- **상환능력 지표의 고도화.** 초기에는 간이 지표(기존부채÷연소득)를 사용했으나, 신규 신청분의 상환부담을
  반영하지 못하는 한계가 있어 이후 **DSR(연간 원리금상환액÷연소득)**로 교체했다. 기존부채와 신규 희망금액을
  모두 원리금균등상환으로 환산·합산하며, 판정 밴드 40%는 은행권 DSR 규제 상한을 반영한다.
- **다기준 상품 랭킹.** 최저금리 단일 기준을 금리·승인여유·중도상환수수료의 3단 정렬로 확장했다.
- **도구를 안전 게이트로 설계.** 심사·상품 조회를 도구로 강제해 LLM이 CSV 외의 값을 생성하지 못하게 했다.

## 3. 개발 중 이슈와 해결

실제로 마주쳐 해결한 문제들이다.

1. **노트북 실행 중 이벤트 루프 충돌.** 노트북에서 동기 `crew.kickoff()`를 호출하자 Jupyter의 실행 중 이벤트
   루프와 충돌해 `RuntimeError`가 발생했다(스크립트 실행에서는 재현되지 않음). → 파이프라인을 `async`로 전환하고
   `await crew.kickoff_async()`로 호출하도록 수정했다.
   - **회귀의 근본 원인까지 추적:** 초기 검증 스크립트가 단순 `exec` 방식이라 *실행 중 이벤트 루프가 없어* 이 버그를
     포착하지 못했다. 재검증을 실제 Jupyter 조건(실행 중 asyncio 루프 내 top-level await)으로 재현하도록 바꾸어
     동일 결함을 다시 놓치지 않게 했다. → *"테스트 환경이 실제 실행 환경과 다르면 버그를 놓친다"*는 교훈.
2. **도구 이름 규칙.** 한글 도구명이 OpenAI function name 규칙에 위배되어 오류가 발생했다. → 도구명을 ASCII로
   교체했다(`assess_loan_eligibility`, `lookup_loan_product`).
3. **기법 정의와 구현의 차이 인지.** Self-Consistency를 "한 응답 내 다관점 서술"로 구현했는데, 이는 엄밀한 정의
   ("동일 질의를 N회 독립 추론 후 다수결")와 다르다. → 이 차이를 **문서와 프롬프트에 명시**하고, 최종 판정은
   SC가 아니라 결정적 하드규칙이 내리도록 하여 단일 모델의 오류 상관 위험을 회피했다.
4. **배포 환경 차이로 인한 임포트 실패.** 클라우드 배포 시 실행 방식(`streamlit run`) 때문에 저장소 루트가
   `sys.path`에 없어 패키지 임포트가 실패했다. → 진입 파일에서 저장소 루트를 경로에 추가해 실행 방식과 무관하게
   동작하도록 수정했다.

## 4. 검증

자기보고가 아니라 실제 실행 증거로 검증했다.

- **결정적 로직 자체 테스트:** 대표 케이스에서 판정이 기대와 일치함을 확인(키 없이 실행 가능).
- **환각·안전 점검:** 안내문의 금리·한도 수치가 CSV 값과 일치(환각 0), 디스클레이머 전건 포함, 확정 표현 대신
  조건부 표현, 소스에 API 키 노출 0.
- **독립 검증(격리 컨텍스트).** 개발 주체의 자기 판정을 신뢰하지 않고 별도 컨텍스트에서 증거 기반으로 재검증했다.
  이 과정에서 **배포 대상이 아닌 참고용 자료에 자격증명이 하드코딩된 것을 발견**해 배포 범위에서 분리했다
  (검증 게이트가 실제로 보안 이슈를 포착한 사례).
- **토큰 사용량 관측**으로 추론 비용의 트레이드오프를 확인했다.

## 5. 개발 방법 (프로세스 통제)

LLM 기반 개발에서 흔한 두 실패(규제·리스크 검토 누락, 대화가 길어지며 초기 제약이 흐려지는 컨텍스트 휘발)를
막기 위해, **단계별 승인 게이트 + 상태의 파일 외부화 + 격리된 독립 검증**으로 개발을 통제했다. 규제·금지행위·데이터
등급 등 핵심 제약을 상태 파일에 고정해 두어 세션이 바뀌거나 대화가 길어져도 유지되도록 했고, 각 단계는 사람이
검토·승인한 뒤에만 다음으로 진행했다.

## 6. 이후 고도화 경과

초기 구축 이후 서비스 완성도와 운영 관점을 다음 순서로 보강했다.

- 상환능력 지표를 간이 DTI → **실제 DSR**로 교체, **다기준 상품 랭킹** 도입.
- **pytest(45개) + GitHub Actions CI** — 단위·API 테스트가 무거운 LLM 의존성 없이 동작하도록 로직 계층을 분리.
- **FastAPI 서비스 계층** — 결정적/LLM 경로를 URL로 분리(`/screen`·`/advise`), 값비싼 호출 전 방어(422/503).
- **무토큰 데모** — 키 없는 사용자도 사전 녹화된 실제 3-Agent 출력을 열람.
- **방문자별 키 입력 + 비용 보호장치** — 세션 한정 키(누출 방지), 입력·횟수 상한, 쿨다운.
- **Docker화** 및 **Streamlit Community Cloud 배포**([라이브 데모](https://loan-suitability-agent.streamlit.app/)).
