# 기술 선정 기획서 — 대출 적합성 심사 3-Agent 파이프라인

> 본 문서는 프로젝트에 적용한 핵심 기술의 **선정 근거·대안 비교·트레이드오프**를 정리한다.
> 대상 독자: 리뷰어·채용 담당자·향후 유지보수자.

---

## 0. 설계 목표 (기술 선정의 상위 기준)

이 서비스가 우선한 품질 속성은 다음 4가지이며, 모든 기술 선택은 이 기준으로 판단했다.

1. **안전성(Safety)** — 금융 도메인이므로 잘못된 승인/거절은 치명적. 판정은 재현 가능해야 한다.
2. **재현성(Reproducibility)** — 같은 입력엔 항상 같은 판정. LLM 비결정성이 판정을 흔들면 안 된다.
3. **설명가능성(Explainability)** — 왜 그 판정인지 고객이 이해할 수 있어야 한다.
4. **저비용·저마찰(Low friction)** — 교육용 데모로서 키 없이도 핵심 로직을 검증·시연할 수 있어야 한다.

---

## 1. 아키텍처: "판정은 코드, 설명은 LLM" (결정적 로직 + LLM 분리)

| 항목 | 선택 | 근거 |
|---|---|---|
| 최종 판정 주체 | **결정적 함수(`screen_loan`)** | LLM에게 판정을 맡기면 환각·비결정성으로 같은 고객이 다른 결과를 받을 수 있음. 하드규칙으로 고정해 재현성·감사가능성 확보 |
| LLM의 역할 | **파싱·근거 설명·안내문 작성만** | LLM의 강점(자연어 이해·설명)만 취하고, 약점(수치 판단의 불안정성)은 코드로 대체 |

**대안과 기각 사유**
- *LLM 단독 판정(프롬프트로 규칙 주입):* 구현은 빠르나 재현성·감사 불가 → 금융 도메인 부적합. 기각.
- *전통 룰엔진(Drools 등):* 규칙 표현력은 좋으나 데모 규모엔 과함. 순수 파이썬 함수로 충분. 기각.

> 이 분리가 **프롬프트 인젝션에 대한 구조적 방어**도 된다: 악의적 입력이 안내문 톤은 흔들 수 있어도 판정 자체(배지·적격상품)는 코드가 내리므로 바뀌지 않는다.

## 2. 멀티에이전트 오케스트레이션: CrewAI

| 비교 항목 | CrewAI (선택) | LangGraph | 직접 구현(raw SDK) |
|---|---|---|---|
| 역할 기반 Agent 추상화 | ★ 기본 제공(role/goal/backstory) | 그래프 노드로 표현 | 직접 설계 |
| 순차 파이프라인 | `Process.sequential` 한 줄 | 엣지 정의 필요 | 루프 직접 작성 |
| Tool 연동 | `@tool` 데코레이터 | 지원 | 직접 |
| 학습 곡선 | 낮음 | 중간 | 높음 |
| 이 프로젝트 적합성 | **선형 3단계라 딱 맞음** | 분기·순환 많을 때 유리 | 제어권은 최대지만 보일러플레이트 과다 |

**근거:** 파이프라인이 *파싱 → 심사 → 안내*의 **단순 선형 구조**라, 그래프 기반(LangGraph)의 분기·순환 표현력이 불필요했다. CrewAI의 role/goal/backstory 추상화가 "3명의 담당자 협업"이라는 도메인 은유와 자연스럽게 맞아 가독성이 높다. 분기·재질문(멀티턴)이 필요해지면 LangGraph 전환을 검토한다(로드맵).

## 3. Agent별 프롬프팅 기법

| Agent | 기법 | 선정 근거 |
|---|---|---|
| 1. 정보 파싱가 | **구조화 추출(JSON)** + 규칙기반 파서 교차검증 | 후속 단계가 정확한 필드에 의존 → 출력 스키마를 JSON으로 고정. 규칙기반 파서를 폴백·검증 축으로 병행 |
| 2. 심사 판단가 | **CoT(4단계)** + **Self-Consistency(응용)** | 상환능력 근거를 단계적으로 노출해 설명가능성 확보. 단, 판정은 도구(결정적)를 최우선으로 따르고 SC는 *근거 설명의 다각 검증*으로 응용(주석·프롬프트에 한계 명시) |
| 3. 결과 안내가 | **ReAct** | 금리·한도 수치를 안내 전 `lookup_loan_product` 도구로 **재확인** 후 서술 → 환각 수치 방지 |

> **정직성 노트:** Agent 2의 Self-Consistency는 "동일 질문 N회 독립 추론 후 다수결"이라는 엄밀한 정의가 아니라, 한 응답 내 3관점(보수·낙관·중립) 서술로 근거를 교차 점검하는 **응용**이다. 최종 판정은 SC가 아니라 결정적 도구가 내린다는 점을 프롬프트에 명시했다.

---

## 4. 도구(Tool) 설계 — `@tool` 함수 툴

- `assess_loan_eligibility`: 결정적 판정을 Agent가 반드시 호출하게 해, LLM이 판정을 지어내지 못하도록 강제.
- `lookup_loan_product`: 상품 금리·한도의 **진실의 원천(CSV)** 조회. 동명이품(여러 은행 동일 상품명) 모호성을 후보 리스트로 드러내 조용한 오답을 방지.

**근거:** 툴을 "LLM이 CSV 밖 값을 만들지 못하게 하는 게이트"로 설계. 툴이 곧 안전장치다.

## 5. 상환능력 지표: 간이 DTI → 실제 DSR (원리금균등상환)

| 항목 | 선택 | 근거 |
|---|---|---|
| 지표 | **DSR = 연간 원리금상환액 ÷ 연소득** | 금융위 실제 정의. 이번 신청분의 상환부담까지 반영 |
| 상환액 산식 | **원리금균등상환(annuity)** | 실제 대출 상환 방식의 표준. 신규+기존 부채를 월상환액으로 환산·합산 |
| 판정 밴드 | ≤30% 여유 / ≤40% 보통 / >40% 부족 | **40%는 은행권 실제 DSR 규제 상한**을 데모에 반영 |
| 가정 처리 | **대표 고정금리(연 6%)·기간(60개월)** | 상환능력 판정을 상품과 독립적으로 유지(단순·설명 용이). 상품별 실제 금리 반영은 로드맵 |

**대안과 기각:** *상품별 실제 금리로 DSR 계산* — 더 현실적이나 판정 순서를 바꿔야 하고 로직이 복잡해져, 데모 단계에선 대표금리로 단순화(트레이드오프 명시).

## 6. 프론트엔드: Streamlit

| 비교 | Streamlit (선택) | FastAPI + React | Gradio |
|---|---|---|---|
| 개발 속도 | ★ 매우 빠름(파이썬 단일) | 느림(풀스택) | 빠름 |
| 커스텀 디자인 | CSS 주입으로 가능 | 자유도 최상 | 제한적 |
| 데모 배포 | Streamlit Cloud 원클릭 | 인프라 필요 | HF Spaces |

**근거:** 1인·단기 데모에서 **파이썬 하나로 UI까지** 끝낼 수 있어 생산성이 압도적. 기본 크롬을 CSS로 제거해 "실제 제품"처럼 재구성함으로써 Streamlit의 약점(밋밋한 기본 UI)을 보완했다. 상용 다중 사용자 서비스로 가면 FastAPI+프론트 분리를 검토한다.

## 7. 지원 기술 결정

| 기술 | 근거 |
|---|---|
| **모델: gpt-4o-mini** | 파싱·설명 중심 작업엔 소형 모델로 충분. 비용/지연을 크게 절감. 환경변수로 교체 가능하게 설계 |
| **키 관리: python-dotenv + st.secrets** | 로컬은 `.env`, 배포는 `secrets.toml`. 키를 코드/저장소에서 분리(`.gitignore`) |
| **CSV 파싱: 표준 라이브러리(no pandas)** | 22행 데이터에 pandas는 과한 의존성. 설치 부담·콜드스타트 감소 |
| **지연 초기화(lazy init)** | 키 없이도 import·핵심 로직·자체 테스트가 동작해야 함 → Agent/Crew 생성을 호출 시점까지 미룸 |
| **core.py 단일 진실 원천** | 노트북과 앱이 로직을 공유. 로직 수정이 양쪽에 일관 반영 |
| **규칙기반 파서 폴백** | API 키·비용 없이 파이프라인 오프라인 검증 가능. LLM 파싱의 교차검증 축 |

## 8. 요약 — 한 문장 근거

> **"금융 도메인의 안전성·재현성을 코드(결정적 로직)로 보장하고, 그 위에 LLM 멀티에이전트(CrewAI)로 설명가능성과 자연어 UX를 얹되, 데모 제약(비용·1인 개발)에 맞춰 경량 기술(gpt-4o-mini·Streamlit·표준 라이브러리)을 선택했다."**
