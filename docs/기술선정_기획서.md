# 기술 선정 기획서 — 대출 적합성 심사 3-Agent 파이프라인

> 본 문서는 프로젝트에 적용한 핵심 기술의 선정 근거, 대안 비교, 트레이드오프를 정리한다.
> 대상 독자: 리뷰어, 채용 담당자, 유지보수자.

---

## 0. 설계 목표

본 서비스가 우선한 품질 속성은 다음 네 가지이며, 모든 기술 선택은 이 기준에 따라 결정하였다.

1. **안전성(Safety)** — 금융 도메인에서 오승인·오거절은 치명적이므로 판정은 재현 가능해야 한다.
2. **재현성(Reproducibility)** — 동일 입력은 항상 동일 판정을 산출해야 하며, LLM 비결정성이 판정을 좌우해서는 안 된다.
3. **설명가능성(Explainability)** — 판정 근거를 고객이 이해할 수 있어야 한다.
4. **저마찰(Low friction)** — 교육용 데모로서 키 없이도 핵심 로직을 검증·시연할 수 있어야 한다.

## 1. 아키텍처: 판정은 코드, 설명은 LLM

| 항목 | 선택 | 근거 |
|---|---|---|
| 최종 판정 주체 | 결정적 함수(`screen_loan`) | LLM에 판정을 위임하면 환각·비결정성으로 동일 고객이 상이한 결과를 받을 수 있다. 하드규칙으로 고정하여 재현성·감사가능성을 확보한다 |
| LLM의 역할 | 파싱·근거 설명·안내문 생성 | LLM의 강점(자연어 이해·설명)만 취하고, 약점(수치 판단의 불안정성)은 코드로 대체한다 |

**대안 및 기각 사유**

- *LLM 단독 판정(프롬프트로 규칙 주입):* 구현은 빠르나 재현성·감사가 불가능하여 금융 도메인에 부적합하다. 기각.
- *전통 룰엔진(예: Drools):* 규칙 표현력은 우수하나 데모 규모에는 과도하다. 순수 파이썬 함수로 충분하다. 기각.

이 분리는 프롬프트 인젝션에 대한 구조적 방어로도 작동한다. 악의적 입력이 안내문의 톤을 교란할 수는 있어도,
판정 자체(배지·적격상품)는 코드가 산출하므로 변경되지 않는다.

## 2. 멀티에이전트 오케스트레이션: CrewAI

| 비교 항목 | CrewAI (선택) | LangGraph | 직접 구현(raw SDK) |
|---|---|---|---|
| 역할 기반 Agent 추상화 | 기본 제공(role/goal/backstory) | 그래프 노드로 표현 | 직접 설계 |
| 순차 파이프라인 | `Process.sequential` 한 줄 | 엣지 정의 필요 | 루프 직접 작성 |
| Tool 연동 | `@tool` 데코레이터 | 지원 | 직접 구현 |
| 학습 곡선 | 낮음 | 중간 | 높음 |
| 본 프로젝트 적합성 | 선형 3단계에 적합 | 분기·순환이 많을 때 유리 | 제어권은 최대이나 보일러플레이트 과다 |

파이프라인이 *파싱 → 심사 → 안내*의 단순 선형 구조이므로 그래프 기반(LangGraph)의 분기·순환 표현력은 불필요하였다.
CrewAI의 role/goal/backstory 추상화는 "세 담당자의 협업"이라는 도메인 은유와 부합하여 가독성이 높다.
분기·재질문(멀티턴)이 요구되면 LangGraph 전환을 검토한다(로드맵).

## 3. Agent별 프롬프팅 기법

| Agent | 기법 | 선정 근거 |
|---|---|---|
| 1. 정보 파싱가 | 구조화 추출(JSON) + 규칙기반 파서 교차검증 | 후속 단계가 정확한 필드에 의존하므로 출력 스키마를 JSON으로 고정하고, 규칙기반 파서를 폴백·검증 축으로 병행한다 |
| 2. 심사 판단가 | CoT(4단계) + Self-Consistency(응용) | 상환능력 근거를 단계적으로 노출하여 설명가능성을 확보한다. 판정은 결정적 도구를 최우선으로 따르며, SC는 근거 설명의 다각 검증으로 응용한다 |
| 3. 결과 안내가 | ReAct | 금리·한도 수치를 안내 전 `lookup_loan_product` 도구로 재확인한 뒤 서술하여 환각 수치를 방지한다 |

Agent 2의 Self-Consistency는 "동일 질문을 N회 독립 추론한 뒤 다수결"이라는 엄밀한 정의가 아니라,
한 응답 내에서 세 관점(보수·낙관·중립)으로 근거를 교차 점검하는 응용이다. 최종 판정은 SC가 아니라
결정적 도구가 산출한다는 점을 프롬프트에 명시하였다.

## 4. 도구(Tool) 설계

- `assess_loan_eligibility`: Agent가 결정적 판정을 반드시 호출하도록 하여 LLM이 판정을 임의 생성하지 못하게 한다.
- `lookup_loan_product`: 상품 금리·한도를 진실의 원천(CSV)에서 조회한다. 동명이품(여러 은행의 동일 상품명)의 모호성을 후보 목록으로 노출하여 조용한 오답을 방지한다.

도구는 "LLM이 CSV 외의 값을 생성하지 못하게 하는 게이트"로 설계하였다. 즉 도구가 곧 안전장치다.

## 5. 상환능력 지표: 간이 DTI → DSR(원리금균등상환)

| 항목 | 선택 | 근거 |
|---|---|---|
| 지표 | DSR = 연간 원리금상환액 ÷ 연소득 | 금융위 정의. 신규 신청분의 상환부담까지 반영한다 |
| 상환액 산식 | 원리금균등상환(annuity) | 실제 대출 상환 방식의 표준. 신규·기존 부채를 월상환액으로 환산·합산한다 |
| 판정 밴드 | ≤30% 여유 / ≤40% 보통 / >40% 부족 | 40%는 은행권 DSR 규제 상한을 반영한다 |
| 가정 처리 | 대표 고정금리(연 6%)·기간(60개월) | 상환능력 판정을 상품과 독립적으로 유지한다(단순·설명 용이). 상품별 실제 금리 반영은 로드맵 항목이다 |

**대안 및 기각:** *상품별 실제 금리로 DSR 산출* 방식은 더 현실적이나 판정 순서를 변경해야 하고 로직이 복잡해지므로,
데모 단계에서는 대표금리로 단순화하였다(트레이드오프 명시).

## 6. 프론트엔드: Streamlit

| 비교 항목 | Streamlit (선택) | FastAPI + React | Gradio |
|---|---|---|---|
| 개발 속도 | 매우 빠름(파이썬 단일) | 느림(풀스택) | 빠름 |
| 커스텀 디자인 | CSS 주입으로 가능 | 자유도 최상 | 제한적 |
| 데모 배포 | Streamlit Cloud 원클릭 | 인프라 필요 | HF Spaces |

1인·단기 데모에서 파이썬만으로 UI까지 완결할 수 있어 생산성이 높다. 기본 크롬을 CSS로 제거하여 제품형 UI로
재구성함으로써 Streamlit의 약점(단조로운 기본 UI)을 보완하였다. 다중 사용자 상용 서비스로 확장할 경우
FastAPI + 프론트엔드 분리를 검토한다(§기술노트 참조).

## 7. 지원 기술 결정

| 기술 | 근거 |
|---|---|
| 모델: gpt-4o-mini | 파싱·설명 중심 작업에는 소형 모델로 충분하며 비용·지연을 절감한다. 환경변수로 교체 가능하게 설계하였다 |
| 키 관리: python-dotenv + st.secrets | 로컬은 `.env`, 배포는 `secrets.toml`을 사용하며 키를 저장소에서 분리한다(`.gitignore`) |
| CSV 파싱: 표준 라이브러리(no pandas) | 22행 데이터에 pandas는 과도한 의존성이다. 설치 부담·콜드스타트를 줄인다 |
| 지연 초기화(lazy init) | 키 없이도 import·핵심 로직·자체 테스트가 동작해야 하므로 Agent/Crew 생성을 호출 시점까지 지연한다 |
| core.py 단일 진실 원천 | API·앱·노트북이 로직을 공유하여 수정이 일관되게 반영된다 |
| 규칙기반 파서 폴백 | API 키·비용 없이 파이프라인을 오프라인 검증하며, LLM 파싱의 교차검증 축으로 사용한다 |

## 8. 요약

금융 도메인의 안전성·재현성을 코드(결정적 로직)로 보장하고, 그 위에 LLM 멀티에이전트(CrewAI)로
설명가능성과 자연어 UX를 부가하되, 데모 제약(비용·1인 개발)에 맞추어 경량 기술
(gpt-4o-mini, Streamlit, 표준 라이브러리)을 선택하였다.
