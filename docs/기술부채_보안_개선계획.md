## A. 기능적 아쉬운 점 (Functional Gaps)

임팩트 높은 순.

| # | 항목 | 근거 위치 | 문제 | 개선 방향 |
|---|---|---|---|---|
| A1 | **판정 이중 경로** | `app.py` `_render_result` → `core.screen_loan(parsed)` | 화면 배지·적격상품은 앱이 Agent 1 원문을 재파싱해 재계산, 안내문은 Agent 2 툴 결과 기반 → LLM이 중간에 값을 바꾸면 배지와 안내문이 불일치 가능 | 단일 파싱 결과를 파이프라인 전체가 공유하도록 고정 |
| A2 | **게이트/심사 파서 불일치** | `app.py` 필수정보 게이트는 `rule_based_parse`, 실제 심사는 LLM 파싱 | 두 파서 결과가 갈리면 게이트 통과 후 엉뚱한 파싱으로 심사될 수 있음 | 게이트와 심사가 같은 파싱 소스를 쓰도록 통일 |
| A3 | **규칙 파서 표현 취약** | `core.py` `parse_korean_amount` 등 정규식 | `연봉 8400만`, `4천만원`, `삼천만원`(한글수사), `월 300`(단위생략) 등 미지원 | 한글수사·연봉·통화단위 정규화 추가, 단위 테스트로 회귀 방지 |
| A4 | **추천이 최저금리 단일 기준** | `core.py` `screen_loan` 추천 로직 | 한도 충족·승인 가능성·우대조건 미반영 → 더 나은 상품 누락 가능 | 다기준 스코어링(§C-2) |
| A5 | **멀티턴 재질문 부재** | `app.py` 누락 시 "다시 입력"만 | 부족 항목만 되묻는 대화형 흐름 없음 | 필드별 입력 + 부족분 하이라이트(§C-3) |
| A6 | **DSR 가정 정밀도** | `core.py` `monthly_payment` 가정값 | 기존부채도 대표금리·60개월로 환산, 신용등급별 금리차 미반영 | 신용등급별 예상금리 테이블(로드맵) |
| A7 | **관측성·테스트 커버리지** | `usage_metrics` 미노출, 통합 5케이스뿐 | 경계값(DSR 30/40%, 한도 경계, 연소득 0)·파서 단위 테스트 없음 | pytest 도입(다음 로드맵) + usage 화면 노출 |

## B. 예상 보안 취약점 (Security)

공개 배포 전제, 위험도 순.

| # | 취약점 | 근거 | 영향 | 완화책 |
|---|---|---|---|---|
| S1 | **비용 남용 / 레이트리밋 부재** | `text_area`에 `max_chars` 없음, 호출 빈도 제한 없음 | 무제한 호출 → 비용 폭탄 (앱 소유자 키면 치명적) | 방문자별 자기 키 + 고객보호장치(§C-4) |
| S2 | **프롬프트 인젝션** | 고객 자유 입력이 프롬프트에 그대로 삽입 | 안내문 톤·디스클레이머 조작 시도. **단, 판정은 코드가 내려 못 흔듦(구조적 방어)** | 입력을 구분자로 격리, 디스클레이머는 코드 후처리로 강제 append |
| S3 | **PII 제3자 전송·로깅** | 소득·부채·신용등급이 OpenAI로 전송, `verbose=True`로 평문 로그 | 민감정보 노출 | 데모에 "실제 개인정보 입력 금지" 고지, 배포 시 `verbose=False`·로그 비저장 |
| S4 | **예외 원문 노출** | `app.py` `st.code(str(e))` | 예외에 조직ID·엔드포인트 등 메타 노출 소지 | 배포판에서 상세오류 마스킹/접기 |
| S5 | **XSS (현재 안전, 취약해지기 쉬움)** | `unsafe_allow_html=True` 다수, 단 삽입값은 내부 상수뿐. 안내문은 HTML 미실행(기본값) | 향후 LLM/사용자 출력에 `unsafe_allow_html=True`를 붙이면 즉시 인젝션 XSS | "LLM·사용자 출력엔 절대 unsafe_allow_html 금지" 규칙 문서화 |
| S6 | **의존성 공급망** | `requirements.txt` 대부분 `>=`만 | 재현성·취약점 관리 약함 | 락파일(`pip freeze`/`uv.lock`), Dependabot |

## C. 설계 결정 (Design Decisions)

리뷰 중 제기된 4가지 논점에 대한 결정.

### C-1. 반복 호출·처리시간 최적화 — "CSV 웹 캐시"가 아니라 "LLM 턴 제거 + 결과 캐시"

- **오해 정정:** `lookup_loan_product`가 읽는 CSV는 import 시점에 이미 메모리 로드(`PRODUCTS`). CSV 조회는 서버 왕복이 아니라 거의 0ms → **CSV를 웹 캐시에 올려도 이득 없음.**
- **진짜 비용:** Agent 3의 ReAct 재조회는 **LLM 추론 1턴을 추가**(느림·토큰). 
- **결정:**
  1. **Agent 3 재조회 제거** — 추천상품의 금리·한도는 이미 `screen_loan` 결정적 결과에 CSV값 그대로 존재. 그대로 관통시켜 LLM 턴 1회 절약.
  2. **파이프라인 결과 캐시** — 입력 해시 기준 `st.cache_data`로 동일 입력 재실행 시 LLM 호출 0회.
  3. **OpenAI 프롬프트 캐싱** — 정적 시스템 프롬프트 재사용으로 반복 비용·지연 감소.

### C-2. 대출상품 다기준 랭킹 — 금융권 통상 기준

- 실무 축: **실질 총부담(APR+수수료) · 한도 충족도 · 승인 가능성 · 금리유형/우대 · 상환방식/중도상환수수료.**
- 현재 CSV로 계산 가능한 것: 금리, 한도, 승인여유(등급), 우대 일부. (수수료·상환방식·중도상환 컬럼은 없음 → 추가 필요.)
- **데모용 스코어(낮을수록 우선):**
  ```
  score = w1·예상적용금리 + w2·(1/한도여유) − w3·승인여유마진 − w4·우대적합
  # 예: w1=0.5, w2=0.2, w3=0.2, w4=0.1
  ```
- **결정:** 1차는 **예상 적용금리(소비자 총부담 프록시) 주축**, 동률 시 **승인 가능성(등급 여유)**으로 tie-break 하는 2단 정렬. 실서비스는 APR·수수료·중도상환 컬럼 확장 후 가중합.

### C-3. 재입력 UX — 하이브리드(자유 서술 → 필드별 폼)

- 순수 폼은 "자연어 파싱 에이전트" 강점 스토리를 잃음 → **하이브리드 채택.**
  1. 자유 서술 입력 → 파싱
  2. 파싱값을 **필드별 input에 자동 채움**(월소득/부채/신용등급/희망금액/직장유형/담보)
  3. 누락·오류 필드만 **하이라이트 + 안내**, 충족 필드는 유지
  4. 사용자가 부족분만 보완 후 제출
- 순수 폼은 fallback 옵션으로 제공.

### C-4. 고객(방문자) 보호장치 — 자기 키라도 지갑 보호

- **입력 길이 상한**(`text_area(max_chars=…)`) → 토큰 폭증 차단
- **세션당 실행 횟수 상한** + **연속 호출 쿨다운**
- **실행 전 예상 비용/토큰 표시** 후 실행
- **누적 토큰·비용 표시**(`usage_metrics` 이미 반환 → 화면 노출) + 소프트 상한 경고
- 실행 중 버튼 비활성(중복 실행 방지)

## D. 우선순위 로드맵 반영

1. **pytest + CI** — A7·A3 회귀 방지 기반 마련 (다음 단계)
2. **배포 + 방문자 키 입력 + C-4 보호장치** — S1 해소
3. **C-1 최적화(Agent 3 턴 제거·결과 캐시)** — 비용·지연 개선
4. **C-2 다기준 랭킹 / C-3 하이브리드 입력** — 기능 완성도
