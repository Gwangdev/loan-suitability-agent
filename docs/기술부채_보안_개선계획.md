# 기술 부채 · 보안 · 개선 계획

> 본 문서는 현재 데모의 기능적 한계, 예상 보안 취약점, 그리고 이를 다루기 위한 설계 결정을 정리한다.
> 리스크를 인지하고 우선순위와 해법을 갖추었음을 문서화하는 것이 목적이다.

## A. 기능적 한계 (Functional Gaps)

영향도 순으로 정리한다.

| # | 항목 | 근거 위치 | 문제 | 개선 방향 |
|---|---|---|---|---|
| A1 | 판정 이중 경로 | `app.py` `_render_result` → `core.screen_loan(parsed)` | 화면 배지·적격상품은 앱이 Agent 1 원문을 재파싱하여 재계산하고, 안내문은 Agent 2 도구 결과에 기반한다. LLM이 중간에서 값을 변경하면 배지와 안내문이 불일치할 수 있다 | 단일 파싱 결과를 파이프라인 전체가 공유하도록 고정 |
| A2 | 게이트/심사 파서 불일치 | `app.py` 필수정보 게이트는 `rule_based_parse`, 실제 심사는 LLM 파싱 | 두 파서의 결과가 상이하면 게이트 통과 후 부정확한 파싱으로 심사될 수 있다 | 게이트와 심사가 동일 파싱 소스를 사용하도록 통일 |
| A3 | 규칙 파서 표현 취약 | `core.py` `parse_korean_amount` 등 정규식 | `연봉 8400만`, `4천만원`, `삼천만원`(한글 수사), `월 300`(단위 생략) 등을 인식하지 못한다 | 한글 수사·연봉·통화 단위 정규화 추가, 단위 테스트로 회귀 방지 |
| A4 | 추천의 단일 기준 | `core.py` `screen_loan` 추천 로직 | 한도 충족·승인 가능성·우대 조건을 반영하지 못해 더 적합한 상품을 누락할 수 있다 | 다기준 스코어링(§C-2) |
| A5 | 멀티턴 재질문 부재 | `app.py` 누락 시 재입력 안내만 제공 | 부족 항목만 되묻는 대화형 흐름이 없다 | 필드별 입력 + 부족분 강조(§C-3) |
| A6 | DSR 가정의 정밀도 | `core.py` `monthly_payment` 가정값 | 기존부채도 대표금리·60개월로 환산하며 신용등급별 금리차를 반영하지 않는다 | 신용등급별 예상금리 테이블(로드맵) |
| A7 | 관측성·테스트 커버리지 | `usage_metrics` 미노출, 통합 5개 케이스 | 경계값(DSR 30/40%, 한도 경계, 연소득 0)·파서 단위 테스트가 없다 | pytest 도입 + usage 화면 노출 |

## B. 예상 보안 취약점 (Security)

공개 배포를 전제로 위험도 순으로 정리한다.

| # | 취약점 | 근거 | 영향 | 완화책 |
|---|---|---|---|---|
| S1 | 비용 남용 / 레이트리밋 부재 | `text_area`에 `max_chars` 부재, 호출 빈도 제한 부재 | 무제한 호출로 과다 비용 발생(앱 소유자 키 사용 시 치명적) | 방문자별 자기 키 + 보호장치(§C-4) |
| S2 | 프롬프트 인젝션 | 고객 자유 입력이 프롬프트에 직접 삽입됨 | 안내문 톤·디스클레이머 조작 시도가 가능하다. 다만 판정은 코드가 산출하므로 변경되지 않는다(구조적 방어) | 입력을 구분자로 격리, 디스클레이머는 코드 후처리로 강제 삽입 |
| S3 | PII 제3자 전송·로깅 | 소득·부채·신용등급이 OpenAI로 전송되고 `verbose=True`로 평문 로그에 남음 | 민감정보 노출 | 데모에 실제 개인정보 입력 금지 고지, 배포 시 `verbose=False` 및 로그 비저장 |
| S4 | 예외 원문 노출 | `app.py` `st.code(str(e))` | 예외 메시지에 조직 ID·엔드포인트 등 메타데이터 노출 소지 | 배포판에서 상세 오류 마스킹·접기 |
| S5 | XSS (현재 안전, 취약해지기 쉬움) | `unsafe_allow_html=True`를 다수 사용하나 삽입값은 내부 상수뿐이며, 안내문은 HTML을 실행하지 않는다(기본값) | 향후 LLM·사용자 출력에 `unsafe_allow_html=True`를 적용하면 인젝션 XSS 발생 | LLM·사용자 출력에는 `unsafe_allow_html`을 사용하지 않는다는 규칙 문서화 |
| S6 | 의존성 공급망 | `requirements.txt`가 대부분 `>=`만 지정 | 재현성·취약점 관리 취약 | 락파일(`pip freeze`/`uv.lock`), Dependabot |

## C. 설계 결정 (Design Decisions)

리뷰 과정에서 제기된 네 가지 논점에 대한 결정이다.

### C-1. 반복 호출·처리시간 최적화 — 결과 캐시(ReAct 유지)

- `lookup_loan_product`가 조회하는 CSV는 import 시점에 이미 메모리에 로드된다(`PRODUCTS`).
  CSV 조회는 서버 왕복이 아니라 거의 0ms이므로, CSV를 웹 캐시에 두어도 이득이 없다.
- 실제 비용은 Agent 3의 ReAct 재조회가 추가하는 LLM 추론 1턴이다.
- **ReAct 제거 여부 재검토 결과, 제거하지 않기로 결정하였다.** 제거 시 절감은 1턴에 불과한 반면,
  (1) Agent 3가 도구에 근거하지 않고 안내문 수치를 자유 생성하여 환각·오기재 위험이 증가하고,
  (2) ReAct는 본 프로젝트가 시연하는 핵심 기법이므로 제거 시 가치가 손실된다. 위험 증가가 절감 이득을 상회한다.
- 무위험 최적화만 채택한다.
  1. 파이프라인 결과 캐시 — 입력 해시 기준 `st.cache_data`로 동일 입력 재실행 시 LLM 호출을 0회로 줄인다.
  2. OpenAI 프롬프트 캐싱 — 정적 시스템 프롬프트 재사용으로 반복 비용·지연을 절감한다.
  3. Agent 3 재조회 제거는 위 재검토에 따라 기각한다.

### C-2. 대출상품 다기준 랭킹 (구현 완료)

- 실무 기준: 실질 총부담(APR+수수료), 한도 충족도, 승인 가능성, 금리 유형·우대, 상환방식·중도상환수수료.
- 실제 데이터 확인: 금융감독원 「금융상품 한눈에」(finlife.fss.or.kr) 오픈API가 개인신용대출의
  금리·상환방식·금리방식·중도상환수수료를 공시한다. 다만 실데이터 연동은 (1) 실명 은행 노출에 따른
  공개 데모의 impersonation 위험, (2) API 키·네트워크 의존에 의한 CI·오프라인 결정성 저하,
  (3) 월별 변동에 의한 테스트 재현 불가라는 문제가 있다. 따라서 결정성 유지를 위해 합성 데이터를 사용하되,
  공시가 노출하는 실제 컬럼(상환방식·금리방식·중도상환수수료)을 CSV에 추가하여 현실 스키마를 모사하였다.
- 구현된 랭킹(`screen_loan`, 3단 정렬키, 모두 작을수록 우선):
  ```
  key = ( 최저금리,              # (1) 소비자 총부담(예상 적용금리) 프록시 — 주축
          -(승인여유마진),        # (2) 승인여유 = 필요신용등급 − 고객신용등급(클수록 안전) → 내림차순
          중도상환수수료 )        # (3) 낮을수록 유리
  ```
  결과에 최종 추천(1위)과 상위 3위 랭킹(`추천후보`)을 반환하고, 앱의 "대안 상품 비교" 표로 제시한다.
- 잔여 확장(실서비스): APR(수수료 포함 실효금리)·상환기간·우대조건의 가중합.

### C-3. 재입력 UX — 하이브리드(자유 서술 → 필드별 폼) ✅ **구현 완료**

순수 폼은 "자연어 파싱 에이전트"라는 강점을 상실하므로 하이브리드 방식을 채택하였다.

1. 자유 서술을 입력하고 "자연어에서 채우기"로 규칙기반 파싱해 폼을 채운다(키 불필요).
2. 파싱값이 필드별 입력창(월소득/부채/신용등급/희망금액/직장유형/담보)에 자동으로 들어간다.
3. 누락·오류 필드만 강조·안내하고(`missing_required_fields`), 충족 필드는 유지한다.
4. 사용자가 부족분만 보완해 **폼(진실의 원천)** 으로 제출한다.

- **부수 효과 1 — A1(판정 이중 경로) 해소:** 배지·적격상품이 LLM 재파싱이 아니라 사용자가 확정한
  구조화 값으로 계산되어, 화면 판정과 안내문이 어긋나지 않는다.
- **부수 효과 2 — 키 없이 결정적 심사:** "결정적 심사(키 불필요)" 버튼으로 폼 값을 `screen_loan`에
  바로 넣어 판정·추천·적격상품을 **토큰 0**으로 확인한다. "AI 안내문까지 생성"은 키가 있을 때만 실행한다.

### C-4. 방문자 보호장치 (구현 완료)

- 방문자별 키(세션 한정): 사이드바 password 입력으로 받으며, 키는 `session_state`에만 두고
  `os.environ`에 저장하지 않는다. 따라서 Streamlit Cloud 공유 프로세스에서 타 방문자에게 키가 누출되지 않는다.
  파이프라인에는 인자(`api_key`)로만 전달한다(`get_llm(api_key=…)`).
- 입력 길이 상한(`text_area(max_chars=2000)`)으로 토큰 폭증을 차단한다(API도 동일).
- 세션당 실행 횟수 상한(`MAX_RUNS_PER_SESSION=10`)과 연속 실행 쿨다운(`COOLDOWN_SEC=5`)을 둔다.
- 세션 사용량을 표시하며("이번 세션 실행 N/10회"), 키·한도가 없으면 실행 버튼을 비활성화한다.
- 무토큰 데모는 키와 독립적으로 동작한다(키가 없어도 사전 녹화 결과를 열람 가능하며, 라이브 검증을 완료하였다).
- 향후: 실행 전 예상 비용 표시, 누적 토큰(usage_metrics) 상세 노출.

## D. 우선순위 로드맵

1. C-2 다기준 랭킹 — 완료(CSV에 FSS 공시 컬럼 추가, 3단 정렬, 상위 3위 후보).
2. pytest + CI — 완료(45개 테스트, GitHub Actions).
3. FastAPI 서비스 계층 — 완료(core → REST API).
4. 무토큰 데모 — 완료(키 없이 사전 녹화 결과 열람).
5. C-4 방문자 키 + 비용 보호장치 — 완료(S1 해소: 세션 키, 길이·횟수 상한, 쿨다운).
6. 배포 마무리 — Dockerfile(완료) + Streamlit Community Cloud 라이브 데모(예정).
7. C-1 최적화(결과 캐시·프롬프트 캐싱, ReAct 유지), C-3 하이브리드 입력.
