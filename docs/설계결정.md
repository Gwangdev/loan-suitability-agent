# 설계 결정 기록 (ADR)

> 각 결정에 **기각한 대안과 사유**를 반드시 적는다. 대안 비교가 없는 선택은 근거가 아니라 결과 서술이다.
> 관통 논리: **신뢰할 수 없는 기술을 개선하기보다, 확실한 결과를 보장받도록 적용 범위를 조절하고 신뢰 가능한 다른 기술을 함께 쓴다.**
> 뒤집힌 결정은 여기서 지우고 `PROJECT_LOG.md`의 「뒤집힌 설계 결정」으로 내린다.

## ADR-001. 모듈러 모놀리스 (FastAPI) — 서비스 분리 기각

**결정.** FastAPI 단일 프로세스의 모듈러 모놀리스로 간다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| Spring + Python AI 서비스 분리 | 분리 사유가 트래픽·조직·배포 독립성이 아니라 **기술 시연**이다. 포트폴리오 규모 대비 배포·테스트·장애 지점만 늘어난다 |
| 전체 Spring 재작성 | 기존 AI 코드 통합 비용이 크고, 남은 일정(2026-08-26 → 실질 완료 09-10) 안에 제품·데이터·검증 설계가 함께 약해진다 |

**「Java/Spring 증거 부재」라는 단점은 소멸했다.** 이 단점은 Loan이 유일한 포트폴리오일 때만 성립한다. SKALA Code Review Lab(Spring Boot 3.3.4 · JPA · OAuth2 · Testcontainers · 69/69)이 보조 증거로 그 축을 담당한다.

**뒤집는 조건.** 독립 배포가 필요한 컴포넌트가 생기거나 / 장애 격리를 프로세스 경계로 해야 하거나 / 확장·보안 요구가 갈리거나 / 단일 프로세스로 수용 불가한 실부하가 존재할 때. **기술을 더 보여주려는 목적의 분리는 사유가 아니다.**

## ADR-002. 자연어 원문 미저장

**결정.** 자연어 상담 원문과 전체 프롬프트를 저장·로깅하지 않는다. 구조화 필드로 파싱한 뒤 폐기한다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 암호화해서 저장 | **수집하지 않은 데이터는 유출되지 않는다.** 암호화는 키 관리·접근통제·파기 절차를 새로 만들지만, 미저장은 그 문제군 자체를 없앤다 |
| 마스킹 후 저장 | 마스킹 규칙의 누락을 계속 검증해야 한다. 관통 논리대로 개선 대신 범위를 없앤다 |

**대가(정직하게).** 파싱 품질 회귀를 실사용 입력으로 사후 분석할 수 없다. 그래서 회귀 검증을 **녹화 픽스처 + 결함 주입**으로 대체했다(ADR-007).

## ADR-003. LLM 실행을 판정 트랜잭션에서 분리

**결정.** 심사 생성 트랜잭션과 LLM 호출을 분리한다. 심사 응답은 결정적 결과 + `explanation_run` 작업 ID를 즉시 반환하고, 설명은 별도 상태로 진행한다. **LLM 호출 동안 DB 트랜잭션·커넥션을 잡지 않는다.**

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 동기 처리(요청 하나가 3-Agent 완료까지 대기) | 현행 `POST /advise`가 이 방식이며 요청당 10~30초를 점유한다. 워커 N개면 동시 N명에서 포화하고, 커넥션을 함께 잡으면 풀이 즉시 고갈된다 |
| 외부 큐(Celery/RQ) 도입 | 현재 규모에서 인프라 1종·운영 표면이 늘어나는 비용이 이득을 넘는다. **다중 인스턴스 또는 재시작 간 작업 보존이 필요해지면 그때 도입한다** |

**부수 효과 — 아웃박스.** `explanation_run(PENDING)`을 심사와 **같은 트랜잭션**에 넣으므로, 커밋과 작업 발행이 원자적이다. 별도 아웃박스 테이블 없이 아웃박스 패턴의 성질을 얻는다(T1 #7).

## ADR-004. 멱등성 = Idempotency-Key + 요청 해시 + DB UNIQUE

**결정.** `POST /assessments`는 `Idempotency-Key` 헤더를 요구한다. 키와 요청 본문 해시를 함께 저장하고 UNIQUE 제약을 최종 방어선으로 둔다.

| 상황 | 처리 |
|---|---|
| 새 키 · 새 요청 | 심사 생성 |
| 같은 키 · 같은 요청 해시 | 기존 심사 반환 (200) |
| 같은 키 · 다른 요청 해시 | **409 Conflict** |
| 처리 중 동일 요청 | UNIQUE 위반을 잡아 현재 상태 재조회 후 반환 |

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 애플리케이션 선조회만으로 중복 차단 | PostgreSQL 기본 격리 수준(READ COMMITTED)에서 **조회와 삽입 사이에 경쟁이 존재한다.** 선조회는 최적화이지 보장이 아니다 |
| UI에서 버튼 비활성화 | 클라이언트 재시도·네트워크 재전송을 막지 못한다. 서버가 보장해야 한다 |

**검증 방법.** 같은 키로 병렬 요청 N개를 보내 심사가 정확히 1건 생성되는지 확인한다(T1 #9). **이 테스트가 없으면 위 주장은 전부 무증거다.**

**하드닝 원칙 「검증을 한 계층에만 두지 않는다」의 적용 사례**이기도 하다 — 앱 검증과 DB 제약은 우회 경로가 다르므로 중복이 아니다.

## ADR-005. 규칙·상품·모델·프롬프트 4종 버전을 결과에 불변 저장

**결정.** 판정 결과에 `rule_version`·`product_dataset_version`을, 설명 실행에 `model_name`·`prompt_version`을 저장한다. 저장 후 변경하지 않는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 로그에만 남긴다 | 로그는 보존기간이 짧고 유실·회전된다. **과거 판정을 당시 규칙으로 재현할 수 없으면 감사 주장이 성립하지 않는다** |
| 현재 규칙으로 재계산해 보여준다 | 규칙이 바뀐 뒤 과거 결과가 조용히 달라진다. 감사에서 최악의 형태다 |

**모델명과 프롬프트 버전을 분리하는 이유.** 둘은 독립적으로 바뀐다. 합치면 「모델 때문인가 프롬프트 때문인가」를 사후에 가릴 수 없다.

## ADR-006. JSONB와 정규화 테이블의 경계

**결정.** **조회·정렬·제약이 필요한 데이터는 관계형 컬럼**, 형태가 변하고 검색하지 않는 상세는 JSONB.

- 관계형: `recommendation`(순위·적격여부로 정렬·제약), `decision_result`의 판정·DSR
- JSONB: `eval_result.detail`(실패 근거), `decision_result.monthly_payment`(표시용 내역), `audit_event.metadata`

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 추천을 `decision_result`의 JSONB 배열로 | **JSONB 배열에는 `(assessment_id, product_code)` UNIQUE를 걸 수 없다.** 순위 정렬·부분 인덱스도 불가 |
| 전부 정규화 | `eval_result.detail`처럼 지표별로 형태가 다른 실패 근거는 컬럼으로 고정하면 지표 추가마다 마이그레이션이 발생한다 |

**`decision_result`를 `assessment_case`와 1:1인데 분리한 이유.** 생명주기가 다르다 — **심사는 상태가 변하고 판정은 불변이다.** 한 테이블에 두면 불변이어야 할 행이 `UPDATE` 대상 행과 섞인다.

## ADR-007. 실패한 AI 설명은 공개하지 않는다

**결정.** Eval을 통과한 설명만 노출한다. 실패 시 `EXPLANATION_FAILED`(호출 실패) 또는 `REVIEW_REQUIRED`(Eval 실패)로 두고 **결정적 판정은 그대로 조회 가능**하게 한다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 경고 문구와 함께 노출 | 금융 안내문에서 「부정확할 수 있음」 고지는 오정보 제공 책임을 면제하지 않는다. 사용자는 본문을 읽는다 |
| 사후 사람 검수로 거른다 | 확장 불가이고 검수자마다 기준이 달라 비결정적이다 |
| LLM-as-judge로 통과 여부 판정 | **판정자가 비결정적이면 회귀 판정도 비결정적이 된다.** 프롬프트를 고쳤을 때 품질이 올랐는지 내렸는지 말할 수 없게 된다 |

**LLM-as-judge 도입 조건.** 표현의 자연스러움·설득력 같은 **정성 품질**을 측정해야 할 때, 규칙 기반 지표를 대체하지 않고 **병행**으로 도입한다.

## ADR-008. 테스트 DB는 실제 PostgreSQL (Testcontainers 우선)

**결정.** DB 통합 테스트는 실제 PostgreSQL에서 돌린다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| SQLite | JSONB·부분 인덱스·격리 수준·`ON CONFLICT` 동작이 다르다. **다른 DB로 검증하고 PostgreSQL 동작을 주장하면 그것은 거짓이다** |
| 모킹된 리포지토리 | 이 프로젝트가 증명하려는 것이 제약·트랜잭션·경쟁이다. 그 계층을 모킹하면 검증 대상이 사라진다 |

**Testcontainers가 환경 문제로 불가하면** docker-compose의 실제 PostgreSQL을 CI에서 띄워 쓴다. **어느 쪽이든 실제 PostgreSQL이라는 조건은 양보하지 않는다.**

## ADR-009. 인증·인가는 범위 밖 — 명시적 비범위

**결정.** 인증·인가를 구현하지 않는다. **누락이 아니라 결정이다.**

**근거.** 데모에는 사칭할 두 번째 사용자가 없으므로 IDOR이 성립하지 않는다. 인증을 흉내 내면 실제로 보호하지 않으면서 보호하는 것처럼 보이는 표면이 생기고, 그것이 더 위험하다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 간단한 API 키·베이직 인증 추가 | 실질 보호 없이 「인증이 있다」는 인상만 만든다. 방어질문에서 곧바로 무너진다 |
| 심사 ID를 UUID로 두는 것을 접근 통제로 간주 | **추측 난이도는 접근 통제가 아니다.** 이 혼동 자체가 결함이다 |

**실서비스 전환 시 도입 검토.** 상담원 계정 인증(OIDC), 소속 지점 단위 인가, 조회 범위 제한, 접근 감사 기록. → `docs/리스크_통제_대장.md`

## ADR-011. 3-tier를 컨테이너·네트워크 경계로 구현 — D7 해소

**결정.** Compose를 `ui`(Streamlit) → `app`(FastAPI) → `postgres` 3개 서비스로 구성한다. **`postgres`는 내부 전용 네트워크에만 두고 호스트 포트를 게시하지 않는다.**

**세부기술서 §16이 `app`·`postgres` 둘만 적어 UI 실행 경로가 없던 문제(D7)를 함께 해소한다.**

| 계층 | 서비스 | 네트워크 | 호스트 노출 |
|---|---|---|---|
| Presentation | `ui` (Streamlit) | `frontend` | 노출 |
| Application | `app` (FastAPI) | `frontend` + `backend` | 노출(Swagger를 포트폴리오 증거로 쓰기 위해) |
| Data | `postgres` | `backend` **전용** | **미노출** |

**CORS를 설정하지 않는다 — 필요가 없기 때문이다.** Streamlit은 서버사이드 렌더링이라 브라우저가 API를 직접 호출하지 않고 `ui` 서버가 호출한다. 하드닝 원칙대로 **「CORS를 안전하게 설정한다」가 아니라 「CORS 설정이 필요 없는 구조」**를 택했다.

**`app`을 호스트에 노출하는 것은 데모 조건의 타협이다.** 실서비스라면 진입점을 리버스 프록시 하나로 모으고 `app`도 내부에만 둔다. 이 타협을 리스크 대장에 3단 구조로 기록한다.

**함께 적용하는 하드닝 원칙:** non-root + read-only 루트 파일시스템을 한 세트로(`I2`), 헬스체크는 의존 자원을 실제로 호출(`I3`, ADR-012), 관리 도구(DB 어드민)는 기본 기동 대상에서 제외.

## ADR-012. 판정 라벨·상태 어휘 확정 — D1·D2 해소

**D1 — API는 영문 enum, 화면은 한글.** 세부기술서가 §8.1에서 한글(`승인가능`), §9.1에서 영문(`ELIGIBLE`)을 섞어 쓰던 것을 고정한다. API 계약은 안정적이어야 하고, 한글 라벨은 표현 계층의 관심사다.

| 판정(`verdict`) | 화면 |
|---|---|
| `ELIGIBLE` | 승인가능 |
| `CONDITIONAL` | 상담필요 |
| `INELIGIBLE` | 어려움 |

`CONDITIONAL`을 쓰는 이유: 상태값에 이미 `REVIEW_REQUIRED`가 있어 **판정 어휘와 상태 어휘가 겹치면 안 되기 때문이다.**

**D2 — `RECEIVED`·`REJECTED_INPUT` 삭제.** 심사 생성이 단일 트랜잭션(ADR-003)이므로 커밋 시점에 이미 `SCREENED`다. `RECEIVED`는 트랜잭션 내부에만 존재해 외부에서 관측되지 않는 **죽은 상태**였다. 입력 검증 실패는 레코드를 만들지 않고 422로 반환하므로 `REJECTED_INPUT`도 불필요하다.

```
SCREENED ──→ COMPLETED            설명 생성 + Eval 통과
   │
   ├──→ EXPLANATION_FAILED ──→ COMPLETED   (재시도 성공)
   └──→ REVIEW_REQUIRED ────→ COMPLETED   (재생성·검토 통과)
```

상태 전이가 닫혀 있고 빠져나올 수 없는 상태가 없다. `EXPLANATION_FAILED`·`REVIEW_REQUIRED`에서도 **결정적 판정은 항상 조회 가능**하다.

## ADR-013. 유효한 설명을 명시 포인터로 지정 — D3 해소

**결정.** `assessment_case.current_explanation_run_id`(FK, nullable)로 현재 유효한 설명을 가리킨다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 「가장 최근 `COMPLETED`」 규칙 | 재시도가 실패했을 때 **이전 성공본을 계속 노출할지**를 규칙만으로 표현할 수 없다. 조회마다 정렬·필터가 붙어 인덱스도 더 필요하다 |
| `explanation_run.is_current` 불리언 | 두 행이 동시에 참이 되는 상태를 막으려면 부분 UNIQUE 인덱스가 필요하다. 포인터 하나가 단순하다 |

## ADR-014. 성능 인덱스를 별도 마이그레이션으로 분리 — D5 해소

**결정.** 초기 마이그레이션에는 PK·FK·UNIQUE 등 **정합성 제약만** 넣고, 조회 성능용 복합 인덱스는 **후속 마이그레이션**으로 분리한다.

**사유.** 세부기술서 §8.2가 인덱스를 처음부터 정의해 두면 §18의 「인덱스 전후 `EXPLAIN ANALYZE` 비교」가 성립하지 않는다. 마이그레이션을 나누면 합성 이력 10,000건을 넣고 **전 → 후를 실제로 측정**할 수 있다.

측정 결과는 실행 환경·데이터 건수와 함께 기록하고 **절대값을 일반화하지 않는다.**

## ADR-015. 목록 API 페이지네이션 — 채택 (커서 기반)

`reference/insights/backend-adoption-candidates.md`는 페이지네이션을 **기본 보류**로 둔다. 그럼에도 채택하는 사유를 적는다.

| 판정 칸 | 내용 |
|---|---|
| 가치가 생기는 조건 | 레코드가 실제로 쌓일 때 |
| 이 프로젝트의 조건 | **충족.** §18의 성능 실험이 합성 이력 **10,000건**을 생성한다. 쌓이는 것이 전제다 |
| 지금 넣는 비용 | 후보 문서가 지적한 비용은 「API 계약 변경」인데, **이 표면은 아직 명세에 나가지 않았다.** 지금 정하면 변경 비용이 0이다 |
| 확인 | 완료 — `SPEC.yaml`에 `GET /api/v1/assessments`가 처음 등재되는 시점이다 |

**OFFSET이 아니라 커서 기반을 쓰는 이유.** OFFSET은 깊어질수록 건너뛴 행을 모두 읽어 열화된다. 커서는 `(created_at, id)` 복합 인덱스를 그대로 탄다.

## ADR-016. 로그 로테이션 채택 · 리소스 상한 조건부 채택

**로그 로테이션 — 채택.** 비용이 설정 몇 줄이고 기존 구조에 영향이 없다. 여러 서비스에 같은 값을 쓰므로 YAML 앵커로 한 번만 정의한다.

**서비스별 리소스 상한 — 조건부 채택.** 후보 문서의 확인 항목이 「런타임이 실제로 반영하는가」다. **`docker compose config`로 해석 결과를 먼저 출력해 확인한다.** 오케스트레이터 전용 키로 취급돼 조용히 무시되면 「상한을 걸었다」는 문서상 사실만 남으므로, 그 경우 런타임이 지원하는 키로 바꾸거나 **채택을 보류하고 사유를 기록한다.**

## ADR-017. 멱등 스키마 마이그레이션 — 보류

**결정.** 「있으면 넘어가고 없으면 추가」 형태의 멱등 마이그레이션을 도입하지 않는다. **보류는 결정이며 누락이 아니다.**

**사유.** 후보 문서의 확인 항목은 「데이터가 컨테이너 수명과 분리돼 있는가」다. 볼륨으로 분리되어 있으나, Alembic이 버전 테이블로 적용 이력을 관리하므로 같은 보장을 이미 얻는다. 멱등 규칙을 별도로 두면 **같은 규칙이 초기화 경로와 기동 경로 두 자리에 생겨 갈라질 위험**이 비용으로 붙는다.

**도입 조건.** 무중단 스키마 변경이 필요해질 때, expand-contract 절차와 함께 도입한다.

## ADR-018. LLM 재시도는 SDK 내장을 쓴다 — 직접 구현 기각

**설계 검토 §6에서 발견해 정정한 결정이다.** T1 목록은 처음에 「LLM 재시도 지수 백오프를 **구현**」으로 적혀 있었다. 검토 기준은 「재시도·서킷 브레이커를 직접 구현하지 않았는가. 대부분의 클라이언트·SDK가 내장한다」이고, `CLAUDE.md` 불변 카드도 「프레임워크·표준 라이브러리가 제공하는 기능은 기본 채택」이다. **직접 구현은 두 규칙을 동시에 어긴다.**

**결정.** OpenAI SDK가 내장한 재시도(`max_retries`)를 채택하고, **횟수·타임아웃 상한을 명시적으로 설정**한다. 직접 백오프 루프를 만들지 않는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 애플리케이션에서 백오프 루프 직접 구현 | **호출 체인의 여러 계층이 각자 재시도하면 지연이 곱해진다.** SDK가 3회, 우리가 3회면 최악 9회다. 사용자는 그동안 대기한다 |
| 재시도를 아예 끄고 즉시 실패 | 429·일시적 5xx는 재시도로 해결되는 실패다. 설명 재생성을 사용자가 수동으로 눌러야 한다 |

**함께 정하는 것.** 재시도 총 대기에 **상한**을 둔다(`ADR-019`의 타임아웃 계층에 포함). 재시도 대상은 설명 생성뿐이며 **결정적 판정은 재시도 대상이 아니다** — 판정은 이미 커밋되어 있다.

## ADR-019. 설명 재생성의 동시성 통제 — 검토에서 발견

**설계 검토 §4(검사와 실행 사이)에서 발견한 결함이다.** ADR-013이 `assessment_case.current_explanation_run_id`를 도입하면서 **불변이던 심사 레코드에 유일한 가변 필드**를 만들었는데, 그 갱신의 경쟁을 다루지 않았다. 재시도 두 건이 동시에 완료되면 lost update가 발생한다.

**결정.**

1. 같은 심사에 `PENDING`·`RUNNING` 상태의 `explanation_run`이 있으면 새 재시도를 **409 Conflict**로 거절한다.
2. 이를 애플리케이션 조건문에만 맡기지 않고 **`(assessment_id)` 부분 UNIQUE 인덱스**(상태가 `PENDING`·`RUNNING`인 행에 한정)로 DB에서 강제한다.
3. `current_explanation_run_id` 갱신은 해당 심사 행을 잠근 상태에서 수행한다.

**하드닝 원칙 「검증을 한 계층에만 두지 않는다」의 두 번째 적용 사례다.** ADR-004(멱등성)와 같은 형태 — 앱 검사는 그 API를 거치는 요청만 막고, DB 제약은 거치지 않는 경로까지 막는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 마지막 완료본이 이기게 둔다 | 어느 것이 이길지 비결정적이다. **감사 대상 시스템에서 「그때 무엇이 유효했는지 모른다」는 허용되지 않는다** |
| 낙관적 잠금(버전 컬럼 + 412) | 재시도는 사용자가 버튼을 누르는 저빈도 연산이다. 버전 왕복을 클라이언트 계약에 넣는 비용이 이득보다 크다 |

## ADR-020. 로컬 sLLM은 교체가 아니라 비교 축으로 넣는다

**제안 배경.** 금융권은 데이터 외부 전송 때문에 상용 LLM 사용을 꺼린다. 로컬 sLLM으로 바꾸면 리스크 대장 A4(국외 제3자 전송)가 「전환 시 검토」에서 「이미 해결」로 올라간다. 방향은 정확하다.

**결정.** 전면 교체하지 않는다. **선택 가능한 백엔드로 추가하고 같은 Eval 지표로 상용과 비교한다.**

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 상용 LLM을 로컬 sLLM으로 전면 교체 | **도구 호출 신뢰도.** 이 아키텍처는 Agent 2가 `assess_loan_eligibility`를, Agent 3이 `lookup_loan_product`를 반드시 호출해야(ReAct) 성립하는데 7~8B 로컬 모델은 function calling이 불안정하다. 3~5일을 쓰고도 아키텍처가 동작하지 않을 수 있다 |
| 도메인 파인튜닝까지 포함 | 데이터셋 구성·학습·평가·베이스라인 비교로 최소 1~2주인 **별개 프로젝트**다. 「데이터셋을 어떻게 구성했나 / 과적합은 어떻게 봤나 / 베이스라인 대비 얼마나 좋아졌나」에 답하지 못하는 파인튜닝은 **피하려던 「실습 과제」 인상을 오히려 강화한다** |

**일정이 결정적이었다.** 잔여 15일에 전면 교체 4일 + 파인튜닝 1주를 넣으면 P0-a를 포기해야 하는데, 중단·축소 기준이 **「P0-a가 위태로우면 기능이 아니라 제출 범위를 줄인다」**고 못박아 두었다.

**비교 축이 더 강한 이유 — 이것이 이 결정의 핵심이다.**

관통 논리는 **검증 가능한 예측**을 품고 있다.

> 신뢰할 수 없는 기술의 적용 범위를 좁히고 신뢰 가능한 기술로 채웠다면,
> **모델을 갈아끼워도 판정은 변하지 않아야 한다.**

이 예측을 확인하지 않으면 관통 논리는 주장이고, 확인하면 증거가 된다. 설명 품질이 6/6 → 4/6으로 떨어지는데 **판정 정확도는 불변**인 표 하나가 이 프로젝트의 주장 전체를 증명한다.

**Eval 결함 주입과 같은 구조다.** 전 지표 통과만으로는 「평가가 작동한다」의 증거가 못 되어 결함을 주입해 역검증했다. 여기서도 「판정은 코드가 한다」는 말만으로는 주장이고, 모델을 실제로 바꿔 판정 불변을 보이면 증거가 된다.

**부수 효과 셋.** ①Eval 하네스가 회귀 방지 도구에서 **의사결정 도구**로 올라간다 ②리스크 대장 A4의 ③칸이 문서에서 실측 근거로 바뀐다 ③**도구 호출이 실패해도 그것이 결과다** — 「8B 모델은 도구 호출 신뢰도가 낮아 현행 구조에 부적합했고, 그래서 판정을 코드가 갖는 설계가 온프레미스 전환에서 더 중요해진다」. 전면 교체였다면 같은 사실이 프로젝트 실패가 된다.

**착수 시점.** P0-a가 궤도에 오른 뒤(9/3~5 감사·Eval 강화 구간). Eval 케이스 확대와 겹쳐 비용이 준다. 등급은 **P0-b**이며 하한은 「비교표 1개」다.

**파인튜닝의 자리.** 전략기획서 §7 10페이지 「검증된 범위·한계·입사 후 확장」. 비교에서 관측한 품질 격차를 도메인 파인튜닝으로 좁히는 것이 다음 단계라고 쓰면, 근거 없는 희망이 아니라 **실측에 근거한 확장 계획**이 된다.

## ADR-021. 상태 컬럼은 네이티브 `ENUM`이 아니라 `TEXT` + `CHECK`

**결정.** `status`·`verdict` 등 상태 컬럼을 PostgreSQL 네이티브 `ENUM` 타입이 아니라 `TEXT` + `CHECK` 제약으로 둔다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| PostgreSQL `ENUM` 타입 | 값 추가는 `ALTER TYPE`으로 가능하나 **값 제거·순서 변경은 사실상 타입 재생성**이다. 이 프로젝트는 `/design` 중 `RECEIVED`·`REJECTED_INPUT`을 실제로 삭제했다(ADR-012) — 그 비용을 이미 겪을 뻔했다 |

`CHECK` 제약은 마이그레이션에서 갈아 끼우기 쉽고 「정의되지 않은 상태를 막는다」는 보장은 동일하다. 상세는 [`데이터모델.md`](데이터모델.md) §5.

## ADR-022. 자원 상한 — 커넥션 풀 · 타임아웃 계층 · 재시도 상한

세 값은 서로 맞물리므로 함께 정한다. 따로 정하면 안쪽이 바깥쪽보다 길어지는 구성이 생긴다.

### 22.1 커넥션 풀 — 동시 사용자 수가 아니라 점유 시간으로 정한다

**흔한 오해는 「동시 사용자 100명이면 커넥션 100개」다.** 커넥션은 요청이 오는 동안이 아니라 **DB를 실제로 점유하는 동안**만 필요하다.

필요 커넥션 ≈ 도착률 × 평균 점유시간 (Little's Law)

| 구성 | 트랜잭션 점유시간 | 100 req/s에서 필요 커넥션 |
|---|---|---|
| **채택 — LLM을 트랜잭션 밖에(ADR-003)** | 약 10ms (5개 테이블 INSERT + 커밋) | **1개** |
| 기각 — LLM을 트랜잭션 안에 | 10~30초 | **약 2,000개** |

**이 대비가 ADR-003의 값어치다.** PostgreSQL `max_connections` 기본값이 100인데 2,000이 필요하면 **어떤 풀 크기로도 버틸 수 없다.** 즉 커넥션 풀을 키워서 푸는 문제가 아니라 트랜잭션 경계를 옮겨서 푸는 문제였다.

| 설정 | 값 | 근거 |
|---|---|---|
| `pool_size` | **5** | 계산값 1개에 안전계수 5배. 인스턴스당 |
| `max_overflow` | **5** | 순간 피크 흡수. 최대 동시 10개 |
| `pool_timeout` | **5초** | 커넥션 대기 상한. **앱 타임아웃(10초)보다 짧아야** 대기하다 함께 죽지 않는다 |
| `pool_recycle` | **1800초** | 네트워크·DB의 유휴 커넥션 정리에 앞서 우리가 먼저 재활용한다. 죽은 커넥션을 꺼내 쓰는 것을 막는다 |
| `pool_pre_ping` | **켬** | 꺼낼 때 값싼 생존 확인. 재시작·페일오버 직후 첫 요청이 깨지는 것을 막는다 |

**인스턴스당 10개**이므로 앱을 3대로 늘려도 30개다. `max_connections` 100 안에서 마이그레이션·관리 도구 몫이 남는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 풀을 크게(50~100) 잡아 두기 | 커넥션은 PostgreSQL에서 **프로세스**다. 놀고 있어도 메모리를 쓰고, 많을수록 컨텍스트 스위칭이 늘어 **오히려 느려진다** |
| 풀 없이 요청마다 연결 | 연결 수립 비용(TCP + 인증)이 트랜잭션 자체보다 크다 |
| PgBouncer 도입 | 인스턴스 수가 늘어 커넥션 총량이 `max_connections`에 닿을 때 필요해진다. **현재 규모에서는 운영 표면만 늘린다** — 도입 조건을 기록하고 보류 |

### 22.2 타임아웃 계층 — 바깥이 길어야 한다

**안쪽이 바깥보다 길면 좀비 요청이 쌓인다.** 바깥이 먼저 포기해도 안쪽 작업은 계속 돌면서 커넥션과 워커를 붙잡기 때문이다.

```
UI HTTP 클라이언트        15초
  └─ 앱 요청               10초
       ├─ DB statement       5초
       └─ 풀 대기            5초
```

| 값 | 근거 |
|---|---|
| DB `statement_timeout` **5초** | 우리 쿼리는 밀리초 단위다. **5초가 걸린다면 정상 동작이 아니라 사고**이므로 끊는 편이 낫다 |
| 앱 요청 **10초** | 결정적 경로는 검증 + 짧은 트랜잭션이라 1초 안에 끝난다. 10초는 이상 상황용 여유다 |
| UI 클라이언트 **15초** | 앱이 먼저 응답하거나 먼저 포기하도록 |

**설명 생성은 이 계층에 없다.** ADR-003으로 요청 경로에서 빠져 배경 작업이 됐으므로 요청 타임아웃의 지배를 받지 않는다. 별도 상한을 둔다.

```
설명 작업 전체 상한  200초
  └─ LLM 호출 1회당   60초
```

전체 상한을 넘으면 `explanation_run`을 `FAILED`로 전이한다. **결정적 판정은 영향받지 않는다.**

### 22.3 재시도 상한 (ADR-018 구체값)

SDK 내장 재시도를 쓰고 **직접 백오프 루프를 만들지 않는다.**

| 설정 | 값 |
|---|---|
| `max_retries` | **2** (최초 1회 + 재시도 2회 = 최대 3회) |
| 재시도 대상 | 429 · 5xx · 타임아웃 |
| 재시도 **안 하는** 것 | 4xx 스키마·인증 오류. **재시도해도 같은 결과이므로 지연만 늘린다** |
| 총 대기 상한 | 200초 (§22.2의 설명 작업 상한과 동일) |

**결정적 판정은 재시도 대상이 아니다.** 이미 커밋되어 있으므로 다시 할 일이 없다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| `max_retries`를 5 이상 | 60초 × 6회면 사용자가 6분을 기다린다. **재시도는 일시적 실패를 흡수하는 것이지 장애를 견디는 수단이 아니다** |
| 앱에서 백오프 루프 추가 | SDK 3회 × 우리 3회 = 최악 9회. **계층마다 재시도하면 지연이 곱해진다**(ADR-018) |
