# 설계 결정 기록 (ADR)

> 각 결정에 **기각한 대안과 사유**를 반드시 적는다. 대안 비교가 없는 선택은 근거가 아니라 결과 서술이다.
> 관통 논리: **신뢰할 수 없는 기술을 개선하기보다, 확실한 결과를 보장받도록 적용 범위를 조절하고 신뢰 가능한 다른 기술을 함께 쓴다.**
> 뒤집힌 결정은 여기서 지우고 `PROJECT_LOG.md`의 「뒤집힌 설계 결정」으로 내린다.

## ADR-001. 모듈러 모놀리스 (FastAPI) — 서비스 분리 기각

**결정.** FastAPI 단일 프로세스의 모듈러 모놀리스로 간다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| Spring + Python AI 서비스 분리 | 분리 사유가 트래픽·조직·배포 독립성이 아니라 **기술 시연**이다. 포트폴리오 규모 대비 배포·테스트·장애 지점만 늘어난다 |
| 전체 Spring 재작성 | 기존 AI 코드 통합 비용이 크고, 남은 일정(2026-08-26 → 실질 완료 09-10) 안에 제품·데이터·검증 설계가 함께 약해진다 |

**「Java/Spring 증거 부재」라는 단점은 소멸했다.** 이 단점은 Loan이 유일한 포트폴리오일 때만 성립한다. SKALA Code Review Lab(Spring Boot 3.3.4 · JPA · OAuth2 · Testcontainers · 69/69)이 보조 증거로 그 축을 담당한다.

**뒤집는 조건.** 독립 배포가 필요한 컴포넌트가 생기거나 / 장애 격리를 프로세스 경계로 해야 하거나 / 확장·보안 요구가 갈리거나 / 단일 프로세스로 수용 불가한 실부하가 존재할 때. **기술을 더 보여주려는 목적의 분리는 사유가 아니다.**

## ADR-002. 자연어 원문 미저장

**결정.** 자연어 상담 원문과 전체 프롬프트를 저장·로깅하지 않는다. 구조화 필드로 파싱한 뒤 폐기한다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 암호화해서 저장 | **수집하지 않은 데이터는 유출되지 않는다.** 암호화는 키 관리·접근통제·파기 절차를 새로 만들지만, 미저장은 그 문제군 자체를 없앤다 |
| 마스킹 후 저장 | 마스킹 규칙의 누락을 계속 검증해야 한다. 관통 논리대로 개선 대신 범위를 없앤다 |

**대가(정직하게).** 파싱 품질 회귀를 실사용 입력으로 사후 분석할 수 없다. 그래서 회귀 검증을 **녹화 픽스처 + 결함 주입**으로 대체했다(ADR-007).

## ADR-003. LLM 실행을 판정 트랜잭션에서 분리

**결정.** 심사 생성 트랜잭션과 LLM 호출을 분리한다. 심사 응답은 결정적 결과 + `explanation_run` 작업 ID를 즉시 반환하고, 설명은 별도 상태로 진행한다. **LLM 호출 동안 DB 트랜잭션·커넥션을 잡지 않는다.**

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 동기 처리(요청 하나가 3-Agent 완료까지 대기) | 현행 `POST /advise`가 이 방식이며 요청당 10~30초를 점유한다. 워커 N개면 동시 N명에서 포화하고, 커넥션을 함께 잡으면 풀이 즉시 고갈된다 |
| 외부 큐(Celery/RQ) 도입 | 현재 규모에서 인프라 1종·운영 표면이 늘어나는 비용이 이득을 넘는다. **다중 인스턴스 또는 재시작 간 작업 보존이 필요해지면 그때 도입한다** |

**부수 효과 — 아웃박스.** `explanation_run(PENDING)`을 심사와 **같은 트랜잭션**에 넣으므로, 커밋과 작업 발행이 원자적이다. 별도 아웃박스 테이블 없이 아웃박스 패턴의 성질을 얻는다(T1 #7).

## ADR-004. 멱등성 = Idempotency-Key + 요청 해시 + DB UNIQUE

**결정.** `POST /assessments`는 `Idempotency-Key` 헤더를 요구한다. 키와 요청 본문 해시를 함께 저장하고 UNIQUE 제약을 최종 방어선으로 둔다.

| 상황 | 처리 |
|---|---|
| 새 키 · 새 요청 | 심사 생성 |
| 같은 키 · 같은 요청 해시 | 기존 심사 반환 (200) |
| 같은 키 · 다른 요청 해시 | **409 Conflict** |
| 처리 중 동일 요청 | UNIQUE 위반을 잡아 현재 상태 재조회 후 반환 |

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 애플리케이션 선조회만으로 중복 차단 | PostgreSQL 기본 격리 수준(READ COMMITTED)에서 **조회와 삽입 사이에 경쟁이 존재한다.** 선조회는 최적화이지 보장이 아니다 |
| UI에서 버튼 비활성화 | 클라이언트 재시도·네트워크 재전송을 막지 못한다. 서버가 보장해야 한다 |

**검증 방법.** 같은 키로 병렬 요청 N개를 보내 심사가 정확히 1건 생성되는지 확인한다(T1 #9). **이 테스트가 없으면 위 주장은 전부 무증거다.**

**하드닝 원칙 「검증을 한 계층에만 두지 않는다」의 적용 사례**이기도 하다 — 앱 검증과 DB 제약은 우회 경로가 다르므로 중복이 아니다.

## ADR-005. 규칙·상품·모델·프롬프트 4종 버전을 결과에 불변 저장

**결정.** 판정 결과에 `rule_version`·`product_dataset_version`을, 설명 실행에 `model_name`·`prompt_version`을 저장한다. 저장 후 변경하지 않는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 로그에만 남긴다 | 로그는 보존기간이 짧고 유실·회전된다. **과거 판정을 당시 규칙으로 재현할 수 없으면 감사 주장이 성립하지 않는다** |
| 현재 규칙으로 재계산해 보여준다 | 규칙이 바뀐 뒤 과거 결과가 조용히 달라진다. 감사에서 최악의 형태다 |

**모델명과 프롬프트 버전을 분리하는 이유.** 둘은 독립적으로 바뀐다. 합치면 「모델 때문인가 프롬프트 때문인가」를 사후에 가릴 수 없다.

## ADR-006. JSONB와 정규화 테이블의 경계

**결정.** **조회·정렬·제약이 필요한 데이터는 관계형 컬럼**, 형태가 변하고 검색하지 않는 상세는 JSONB.

- 관계형: `recommendation`(순위·적격여부로 정렬·제약), `decision_result`의 판정·DSR
- JSONB: `eval_result.detail`(실패 근거), `decision_result.monthly_payment`(표시용 내역), `audit_event.metadata`

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 추천을 `decision_result`의 JSONB 배열로 | **JSONB 배열에는 `(assessment_id, product_code)` UNIQUE를 걸 수 없다.** 순위 정렬·부분 인덱스도 불가 |
| 전부 정규화 | `eval_result.detail`처럼 지표별로 형태가 다른 실패 근거는 컬럼으로 고정하면 지표 추가마다 마이그레이션이 발생한다 |

**`decision_result`를 `assessment_case`와 1:1인데 분리한 이유.** 생명주기가 다르다 — **심사는 상태가 변하고 판정은 불변이다.** 한 테이블에 두면 불변이어야 할 행이 `UPDATE` 대상 행과 섞인다.

## ADR-007. 실패한 AI 설명은 공개하지 않는다

**결정.** Eval을 통과한 설명만 노출한다. 실패 시 `EXPLANATION_FAILED`(호출 실패) 또는 `REVIEW_REQUIRED`(Eval 실패)로 두고 **결정적 판정은 그대로 조회 가능**하게 한다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 경고 문구와 함께 노출 | 금융 안내문에서 「부정확할 수 있음」 고지는 오정보 제공 책임을 면제하지 않는다. 사용자는 본문을 읽는다 |
| 사후 사람 검수로 거른다 | 확장 불가이고 검수자마다 기준이 달라 비결정적이다 |
| LLM-as-judge로 통과 여부 판정 | **판정자가 비결정적이면 회귀 판정도 비결정적이 된다.** 프롬프트를 고쳤을 때 품질이 올랐는지 내렸는지 말할 수 없게 된다 |

**LLM-as-judge 도입 조건.** 표현의 자연스러움·설득력 같은 **정성 품질**을 측정해야 할 때, 규칙 기반 지표를 대체하지 않고 **병행**으로 도입한다.

## ADR-008. 테스트 DB는 실제 PostgreSQL (Testcontainers 우선)

**결정.** DB 통합 테스트는 실제 PostgreSQL에서 돌린다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| SQLite | JSONB·부분 인덱스·격리 수준·`ON CONFLICT` 동작이 다르다. **다른 DB로 검증하고 PostgreSQL 동작을 주장하면 그것은 거짓이다** |
| 모킹된 리포지토리 | 이 프로젝트가 증명하려는 것이 제약·트랜잭션·경쟁이다. 그 계층을 모킹하면 검증 대상이 사라진다 |

**Testcontainers가 환경 문제로 불가하면** docker-compose의 실제 PostgreSQL을 CI에서 띄워 쓴다. **어느 쪽이든 실제 PostgreSQL이라는 조건은 양보하지 않는다.**

## ADR-009. 인증·인가는 범위 밖 — 명시적 비범위

**결정.** 인증·인가를 구현하지 않는다. **누락이 아니라 결정이다.**

**근거.** 데모에는 사칭할 두 번째 사용자가 없으므로 IDOR이 성립하지 않는다. 인증을 흉내 내면 실제로 보호하지 않으면서 보호하는 것처럼 보이는 표면이 생기고, 그것이 더 위험하다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 간단한 API 키·베이직 인증 추가 | 실질 보호 없이 「인증이 있다」는 인상만 만든다. 방어질문에서 곧바로 무너진다 |
| 심사 ID를 UUID로 두는 것을 접근 통제로 간주 | **추측 난이도는 접근 통제가 아니다.** 이 혼동 자체가 결함이다 |

**실서비스 전환 시 도입 검토.** 상담원 계정 인증(OIDC), 소속 지점 단위 인가, 조회 범위 제한, 접근 감사 기록. → `docs/리스크_통제_대장.md`

## ADR-011. 3-tier를 컨테이너·네트워크 경계로 구현 — D7 해소

**결정.** Compose를 `ui`(Streamlit) → `app`(FastAPI) → `postgres` 3개 서비스로 구성한다. **`postgres`는 내부 전용 네트워크에만 두고 호스트 포트를 게시하지 않는다.**

**세부기술서 §16이 `app`·`postgres` 둘만 적어 UI 실행 경로가 없던 문제(D7)를 함께 해소한다.**

| 계층 | 서비스 | 네트워크 | 호스트 노출 |
|---|---|---|---|
| Presentation | `ui` (Streamlit) | `frontend` | 노출 |
| Application | `app` (FastAPI) | `frontend` + `backend` | 노출(Swagger를 포트폴리오 증거로 쓰기 위해) |
| Data | `postgres` | `backend` **전용** | **미노출** |

**CORS를 설정하지 않는다 — 필요가 없기 때문이다.** Streamlit은 서버사이드 렌더링이라 브라우저가 API를 직접 호출하지 않고 `ui` 서버가 호출한다. 하드닝 원칙대로 **「CORS를 안전하게 설정한다」가 아니라 「CORS 설정이 필요 없는 구조」**를 택했다.

**`app`을 호스트에 노출하는 것은 데모 조건의 타협이다.** 실서비스라면 진입점을 리버스 프록시 하나로 모으고 `app`도 내부에만 둔다. 이 타협을 리스크 대장에 3단 구조로 기록한다.

**함께 적용하는 하드닝 원칙:** non-root + read-only 루트 파일시스템을 한 세트로(`I2`), 헬스체크는 의존 자원을 실제로 호출(`I3`, ADR-012), 관리 도구(DB 어드민)는 기본 기동 대상에서 제외.

## ADR-012. 판정 라벨·상태 어휘 확정 — D1·D2 해소

**D1 — API는 영문 enum, 화면은 한글.** 세부기술서가 §8.1에서 한글(`승인가능`), §9.1에서 영문(`ELIGIBLE`)을 섞어 쓰던 것을 고정한다. API 계약은 안정적이어야 하고, 한글 라벨은 표현 계층의 관심사다.

| 판정(`verdict`) | 화면 |
|---|---|
| `ELIGIBLE` | 승인가능 |
| `CONDITIONAL` | 상담필요 |
| `INELIGIBLE` | 어려움 |

`CONDITIONAL`을 쓰는 이유: 상태값에 이미 `REVIEW_REQUIRED`가 있어 **판정 어휘와 상태 어휘가 겹치면 안 되기 때문이다.**

**D2 — `RECEIVED`·`REJECTED_INPUT` 삭제.** 심사 생성이 단일 트랜잭션(ADR-003)이므로 커밋 시점에 이미 `SCREENED`다. `RECEIVED`는 트랜잭션 내부에만 존재해 외부에서 관측되지 않는 **죽은 상태**였다. 입력 검증 실패는 레코드를 만들지 않고 422로 반환하므로 `REJECTED_INPUT`도 불필요하다.

```
SCREENED ──→ COMPLETED            설명 생성 + Eval 통과
   │
   ├──→ EXPLANATION_FAILED ──→ COMPLETED   (재시도 성공)
   └──→ REVIEW_REQUIRED ────→ COMPLETED   (재생성·검토 통과)
```

상태 전이가 닫혀 있고 빠져나올 수 없는 상태가 없다. `EXPLANATION_FAILED`·`REVIEW_REQUIRED`에서도 **결정적 판정은 항상 조회 가능**하다.

## ADR-013. 유효한 설명을 명시 포인터로 지정 — D3 해소

**결정.** `assessment_case.current_explanation_run_id`(FK, nullable)로 현재 유효한 설명을 가리킨다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 「가장 최근 `COMPLETED`」 규칙 | 재시도가 실패했을 때 **이전 성공본을 계속 노출할지**를 규칙만으로 표현할 수 없다. 조회마다 정렬·필터가 붙어 인덱스도 더 필요하다 |
| `explanation_run.is_current` 불리언 | 두 행이 동시에 참이 되는 상태를 막으려면 부분 UNIQUE 인덱스가 필요하다. 포인터 하나가 단순하다 |

## ADR-014. 성능 인덱스를 별도 마이그레이션으로 분리 — D5 해소

**결정.** 초기 마이그레이션에는 PK·FK·UNIQUE 등 **정합성 제약만** 넣고, 조회 성능용 복합 인덱스는 **후속 마이그레이션**으로 분리한다.

**사유.** 세부기술서 §8.2가 인덱스를 처음부터 정의해 두면 §18의 「인덱스 전후 `EXPLAIN ANALYZE` 비교」가 성립하지 않는다. 마이그레이션을 나누면 합성 이력 10,000건을 넣고 **전 → 후를 실제로 측정**할 수 있다.

측정 결과는 실행 환경·데이터 건수와 함께 기록하고 **절대값을 일반화하지 않는다.**

## ADR-015. 목록 API 페이지네이션 — 채택 (커서 기반)

`reference/insights/backend-adoption-candidates.md`는 페이지네이션을 **기본 보류**로 둔다. 그럼에도 채택하는 사유를 적는다.

| 판정 칸 | 내용 |
|---|---|
| 가치가 생기는 조건 | 레코드가 실제로 쌓일 때 |
| 이 프로젝트의 조건 | **충족.** §18의 성능 실험이 합성 이력 **10,000건**을 생성한다. 쌓이는 것이 전제다 |
| 지금 넣는 비용 | 후보 문서가 지적한 비용은 「API 계약 변경」인데, **이 표면은 아직 명세에 나가지 않았다.** 지금 정하면 변경 비용이 0이다 |
| 확인 | 완료 — `SPEC.yaml`에 `GET /api/v1/assessments`가 처음 등재되는 시점이다 |

**OFFSET이 아니라 커서 기반을 쓰는 이유.** OFFSET은 깊어질수록 건너뛴 행을 모두 읽어 열화된다. 커서는 `(created_at, id)` 복합 인덱스를 그대로 탄다.

## ADR-016. 로그 로테이션 채택 · 리소스 상한 조건부 채택

**로그 로테이션 — 채택.** 비용이 설정 몇 줄이고 기존 구조에 영향이 없다. 여러 서비스에 같은 값을 쓰므로 YAML 앵커로 한 번만 정의한다.

**서비스별 리소스 상한 — 조건부 채택.** 후보 문서의 확인 항목이 「런타임이 실제로 반영하는가」다. **`docker compose config`로 해석 결과를 먼저 출력해 확인한다.** 오케스트레이터 전용 키로 취급돼 조용히 무시되면 「상한을 걸었다」는 문서상 사실만 남으므로, 그 경우 런타임이 지원하는 키로 바꾸거나 **채택을 보류하고 사유를 기록한다.**

## ADR-017. 멱등 스키마 마이그레이션 — 보류

**결정.** 「있으면 넘어가고 없으면 추가」 형태의 멱등 마이그레이션을 도입하지 않는다. **보류는 결정이며 누락이 아니다.**

**사유.** 후보 문서의 확인 항목은 「데이터가 컨테이너 수명과 분리돼 있는가」다. 볼륨으로 분리되어 있으나, Alembic이 버전 테이블로 적용 이력을 관리하므로 같은 보장을 이미 얻는다. 멱등 규칙을 별도로 두면 **같은 규칙이 초기화 경로와 기동 경로 두 자리에 생겨 갈라질 위험**이 비용으로 붙는다.

**도입 조건.** 무중단 스키마 변경이 필요해질 때, expand-contract 절차와 함께 도입한다.

## ADR-018. LLM 재시도는 SDK 내장을 쓴다 — 직접 구현 기각

**설계 검토 §6에서 발견해 정정한 결정이다.** T1 목록은 처음에 「LLM 재시도 지수 백오프를 **구현**」으로 적혀 있었다. 검토 기준은 「재시도·서킷 브레이커를 직접 구현하지 않았는가. 대부분의 클라이언트·SDK가 내장한다」이고, `CLAUDE.md` 불변 카드도 「프레임워크·표준 라이브러리가 제공하는 기능은 기본 채택」이다. **직접 구현은 두 규칙을 동시에 어긴다.**

**결정.** OpenAI SDK가 내장한 재시도(`max_retries`)를 채택하고, **횟수·타임아웃 상한을 명시적으로 설정**한다. 직접 백오프 루프를 만들지 않는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 애플리케이션에서 백오프 루프 직접 구현 | **호출 체인의 여러 계층이 각자 재시도하면 지연이 곱해진다.** SDK가 3회, 우리가 3회면 최악 9회다. 사용자는 그동안 대기한다 |
| 재시도를 아예 끄고 즉시 실패 | 429·일시적 5xx는 재시도로 해결되는 실패다. 설명 재생성을 사용자가 수동으로 눌러야 한다 |

**함께 정하는 것.** 재시도 총 대기에 **상한**을 둔다(`ADR-019`의 타임아웃 계층에 포함). 재시도 대상은 설명 생성뿐이며 **결정적 판정은 재시도 대상이 아니다** — 판정은 이미 커밋되어 있다.

## ADR-019. 설명 재생성의 동시성 통제 — 검토에서 발견

**설계 검토 §4(검사와 실행 사이)에서 발견한 결함이다.** ADR-013이 `assessment_case.current_explanation_run_id`를 도입하면서 **불변이던 심사 레코드에 유일한 가변 필드**를 만들었는데, 그 갱신의 경쟁을 다루지 않았다. 재시도 두 건이 동시에 완료되면 lost update가 발생한다.

**결정.**

1. 같은 심사에 `PENDING`·`RUNNING` 상태의 `explanation_run`이 있으면 새 재시도를 **409 Conflict**로 거절한다.
2. 이를 애플리케이션 조건문에만 맡기지 않고 **`(assessment_id)` 부분 UNIQUE 인덱스**(상태가 `PENDING`·`RUNNING`인 행에 한정)로 DB에서 강제한다.
3. `current_explanation_run_id` 갱신은 해당 심사 행을 잠근 상태에서 수행한다.

**하드닝 원칙 「검증을 한 계층에만 두지 않는다」의 두 번째 적용 사례다.** ADR-004(멱등성)와 같은 형태 — 앱 검사는 그 API를 거치는 요청만 막고, DB 제약은 거치지 않는 경로까지 막는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 마지막 완료본이 이기게 둔다 | 어느 것이 이길지 비결정적이다. **감사 대상 시스템에서 「그때 무엇이 유효했는지 모른다」는 허용되지 않는다** |
| 낙관적 잠금(버전 컬럼 + 412) | 재시도는 사용자가 버튼을 누르는 저빈도 연산이다. 버전 왕복을 클라이언트 계약에 넣는 비용이 이득보다 크다 |

## ADR-020. 로컬 sLLM은 교체가 아니라 비교 축으로 넣는다

**제안 배경.** 금융권은 데이터 외부 전송 때문에 상용 LLM 사용을 꺼린다. 로컬 sLLM으로 바꾸면 리스크 대장 A4(국외 제3자 전송)가 「전환 시 검토」에서 「이미 해결」로 올라간다. 방향은 정확하다.

**결정.** 전면 교체하지 않는다. **선택 가능한 백엔드로 추가하고 같은 Eval 지표로 상용과 비교한다.**

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 상용 LLM을 로컬 sLLM으로 전면 교체 | **도구 호출 신뢰도.** 이 아키텍처는 Agent 2가 `assess_loan_eligibility`를, Agent 3이 `lookup_loan_product`를 반드시 호출해야(ReAct) 성립하는데 7~8B 로컬 모델은 function calling이 불안정하다. 3~5일을 쓰고도 아키텍처가 동작하지 않을 수 있다 |
| 도메인 파인튜닝까지 포함 | 데이터셋 구성·학습·평가·베이스라인 비교로 최소 1~2주인 **별개 프로젝트**다. 「데이터셋을 어떻게 구성했나 / 과적합은 어떻게 봤나 / 베이스라인 대비 얼마나 좋아졌나」에 답하지 못하는 파인튜닝은 **피하려던 「실습 과제」 인상을 오히려 강화한다** |

**일정이 결정적이었다.** 잔여 15일에 전면 교체 4일 + 파인튜닝 1주를 넣으면 P0-a를 포기해야 하는데, 중단·축소 기준이 **「P0-a가 위태로우면 기능이 아니라 제출 범위를 줄인다」**고 못박아 두었다.

**비교 축이 더 강한 이유 — 이것이 이 결정의 핵심이다.**

관통 논리는 **검증 가능한 예측**을 품고 있다.

> 신뢰할 수 없는 기술의 적용 범위를 좁히고 신뢰 가능한 기술로 채웠다면,
> **모델을 갈아끼워도 판정은 변하지 않아야 한다.**

이 예측을 확인하지 않으면 관통 논리는 주장이고, 확인하면 증거가 된다. 설명 품질이 6/6 → 4/6으로 떨어지는데 **판정 정확도는 불변**인 표 하나가 이 프로젝트의 주장 전체를 증명한다.

**Eval 결함 주입과 같은 구조다.** 전 지표 통과만으로는 「평가가 작동한다」의 증거가 못 되어 결함을 주입해 역검증했다. 여기서도 「판정은 코드가 한다」는 말만으로는 주장이고, 모델을 실제로 바꿔 판정 불변을 보이면 증거가 된다.

**부수 효과 셋.** ①Eval 하네스가 회귀 방지 도구에서 **의사결정 도구**로 올라간다 ②리스크 대장 A4의 ③칸이 문서에서 실측 근거로 바뀐다 ③**도구 호출이 실패해도 그것이 결과다** — 「8B 모델은 도구 호출 신뢰도가 낮아 현행 구조에 부적합했고, 그래서 판정을 코드가 갖는 설계가 온프레미스 전환에서 더 중요해진다」. 전면 교체였다면 같은 사실이 프로젝트 실패가 된다.

**착수 시점.** P0-a가 궤도에 오른 뒤(9/3~5 감사·Eval 강화 구간). Eval 케이스 확대와 겹쳐 비용이 준다. 등급은 **P0-b**이며 하한은 「비교표 1개」다.

**파인튜닝의 자리.** 전략기획서 §7 10페이지 「검증된 범위·한계·입사 후 확장」. 비교에서 관측한 품질 격차를 도메인 파인튜닝으로 좁히는 것이 다음 단계라고 쓰면, 근거 없는 희망이 아니라 **실측에 근거한 확장 계획**이 된다.

## ADR-021. 상태 컬럼은 네이티브 `ENUM`이 아니라 `TEXT` + `CHECK`

**결정.** `status`·`verdict` 등 상태 컬럼을 PostgreSQL 네이티브 `ENUM` 타입이 아니라 `TEXT` + `CHECK` 제약으로 둔다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| PostgreSQL `ENUM` 타입 | 값 추가는 `ALTER TYPE`으로 가능하나 **값 제거·순서 변경은 사실상 타입 재생성**이다. 이 프로젝트는 `/design` 중 `RECEIVED`·`REJECTED_INPUT`을 실제로 삭제했다(ADR-012) — 그 비용을 이미 겪을 뻔했다 |

`CHECK` 제약은 마이그레이션에서 갈아 끼우기 쉽고 「정의되지 않은 상태를 막는다」는 보장은 동일하다. 상세는 [`데이터모델.md`](데이터모델.md) §5.

## ADR-022. 자원 상한 — 커넥션 풀 · 타임아웃 계층 · 재시도 상한

세 값은 서로 맞물리므로 함께 정한다. 따로 정하면 안쪽이 바깥쪽보다 길어지는 구성이 생긴다.

### 22.1 커넥션 풀 — 동시 사용자 수가 아니라 점유 시간으로 정한다

**흔한 오해는 「동시 사용자 100명이면 커넥션 100개」다.** 커넥션은 요청이 오는 동안이 아니라 **DB를 실제로 점유하는 동안**만 필요하다.

필요 커넥션 ≈ 도착률 × 평균 점유시간 (Little's Law)

| 구성 | 트랜잭션 점유시간 | 100 req/s에서 필요 커넥션 |
|---|---|---|
| **채택 — LLM을 트랜잭션 밖에(ADR-003)** | 약 10ms (5개 테이블 INSERT + 커밋) | **1개** |
| 기각 — LLM을 트랜잭션 안에 | 10~30초 | **약 2,000개** |

**이 대비가 ADR-003의 값어치다.** PostgreSQL `max_connections` 기본값이 100인데 2,000이 필요하면 **어떤 풀 크기로도 버틸 수 없다.** 즉 커넥션 풀을 키워서 푸는 문제가 아니라 트랜잭션 경계를 옮겨서 푸는 문제였다.

| 설정 | 값 | 근거 |
|---|---|---|
| `pool_size` | **5** | 계산값 1개에 안전계수 5배. 인스턴스당 |
| `max_overflow` | **5** | 순간 피크 흡수. 최대 동시 10개 |
| `pool_timeout` | **5초** | 커넥션 대기 상한. **앱 타임아웃(10초)보다 짧아야** 대기하다 함께 죽지 않는다 |
| `pool_recycle` | **1800초** | 네트워크·DB의 유휴 커넥션 정리에 앞서 우리가 먼저 재활용한다. 죽은 커넥션을 꺼내 쓰는 것을 막는다 |
| `pool_pre_ping` | **켬** | 꺼낼 때 값싼 생존 확인. 재시작·페일오버 직후 첫 요청이 깨지는 것을 막는다 |

**인스턴스당 10개**이므로 앱을 3대로 늘려도 30개다. `max_connections` 100 안에서 마이그레이션·관리 도구 몫이 남는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 풀을 크게(50~100) 잡아 두기 | 커넥션은 PostgreSQL에서 **프로세스**다. 놀고 있어도 메모리를 쓰고, 많을수록 컨텍스트 스위칭이 늘어 **오히려 느려진다** |
| 풀 없이 요청마다 연결 | 연결 수립 비용(TCP + 인증)이 트랜잭션 자체보다 크다 |
| PgBouncer 도입 | 인스턴스 수가 늘어 커넥션 총량이 `max_connections`에 닿을 때 필요해진다. **현재 규모에서는 운영 표면만 늘린다** — 도입 조건을 기록하고 보류 |

### 22.2 타임아웃 계층 — 바깥이 길어야 한다

**안쪽이 바깥보다 길면 좀비 요청이 쌓인다.** 바깥이 먼저 포기해도 안쪽 작업은 계속 돌면서 커넥션과 워커를 붙잡기 때문이다.

```
UI HTTP 클라이언트        15초
  └─ 앱 요청               10초
       ├─ DB statement       5초
       └─ 풀 대기            5초
```

| 값 | 근거 |
|---|---|
| DB `statement_timeout` **5초** | 우리 쿼리는 밀리초 단위다. **5초가 걸린다면 정상 동작이 아니라 사고**이므로 끊는 편이 낫다 |
| 앱 요청 **10초** | 결정적 경로는 검증 + 짧은 트랜잭션이라 1초 안에 끝난다. 10초는 이상 상황용 여유다 |
| UI 클라이언트 **15초** | 앱이 먼저 응답하거나 먼저 포기하도록 |

**설명 생성은 이 계층에 없다.** ADR-003으로 요청 경로에서 빠져 배경 작업이 됐으므로 요청 타임아웃의 지배를 받지 않는다. 별도 상한을 둔다.

```
설명 작업 전체 상한  200초
  └─ LLM 호출 1회당   60초
```

전체 상한을 넘으면 `explanation_run`을 `FAILED`로 전이한다. **결정적 판정은 영향받지 않는다.**

### 22.3 재시도 상한 (ADR-018 구체값)

SDK 내장 재시도를 쓰고 **직접 백오프 루프를 만들지 않는다.**

| 설정 | 값 |
|---|---|
| `max_retries` | **2** (최초 1회 + 재시도 2회 = 최대 3회) |
| 재시도 대상 | 429 · 5xx · 타임아웃 |
| 재시도 **안 하는** 것 | 4xx 스키마·인증 오류. **재시도해도 같은 결과이므로 지연만 늘린다** |
| 총 대기 상한 | 200초 (§22.2의 설명 작업 상한과 동일) |

**결정적 판정은 재시도 대상이 아니다.** 이미 커밋되어 있으므로 다시 할 일이 없다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| `max_retries`를 5 이상 | 60초 × 6회면 사용자가 6분을 기다린다. **재시도는 일시적 실패를 흡수하는 것이지 장애를 견디는 수단이 아니다** |
| 앱에서 백오프 루프 추가 | SDK 3회 × 우리 3회 = 최악 9회. **계층마다 재시도하면 지연이 곱해진다**(ADR-018) |

## ADR-023. 설명 실행기 — 큐 없이 DB 클레임으로

**설계 누락을 메우는 결정이다.** ADR-003이 「실제 호출은 별도 실행기의 몫」이라고 적고 T1 #7이 그 구조를 아웃박스라고 불렀는데, **그 아웃박스를 읽는 주체가 없었다.** 심사마다 `explanation_run(PENDING)`이 쌓이기만 하고 `RUNNING`·`COMPLETED`로 바꾸는 코드가 저장소에 하나도 없었다.

**무엇이 비어 있었는가.** 승인된 요구사항 R7(설명 시도가 모델·프롬프트 버전과 함께 조회 가능하다)이 충족되지 않는다. `model_name`·`prompt_version`·`latency_ms`·토큰·`explanation_text` 컬럼이 전부 비고, `eval_result`에는 행이 생기지 않으며, `current_explanation_run_id`는 영원히 NULL이다. 상태 전이도 `SCREENED`에서 멈춰 `COMPLETED`·`EXPLANATION_FAILED`·`REVIEW_REQUIRED` 세 상태가 도달 불가능해진다 — **ADR-012에서 `RECEIVED`를 죽은 상태라고 지운 것과 같은 문제가 세 배로 남아 있던 셈이다.**

**결정.** 별도 프로세스가 `PENDING`을 집어 실행하고 결과·버전·채점을 기록한다.

### 23.1 작업을 집는 방법

```sql
SELECT id FROM explanation_run
 WHERE status = 'PENDING'
 ORDER BY id
   FOR UPDATE SKIP LOCKED
 LIMIT 1
```

`SKIP LOCKED`가 이미 다른 워커가 잡은 행을 건너뛴다. **워커를 여러 개 띄워도 같은 작업이 두 번 실행되지 않으며, 이 보장을 애플리케이션 로직이 아니라 DB가 준다** — ADR-004의 멱등성 처리와 같은 형태다.

**클레임과 실행을 분리한다.** 행을 `RUNNING`으로 바꾸고 **즉시 커밋해 잠금을 놓은 뒤** LLM을 부른다. 잠금을 쥔 채 호출하면 10~30초 동안 행과 커넥션이 함께 묶여, ADR-003이 트랜잭션 밖으로 밀어낸 문제가 워커 안에서 되살아난다.

### 23.2 죽은 워커가 남긴 작업

클레임 후 프로세스가 죽으면 행이 `RUNNING`인 채로 남아 아무도 다시 집지 못한다. `started_at`이 **설명 작업 상한(200초, ADR-022)을 넘긴 `RUNNING`**을 `PENDING`으로 되돌린다. 상한값을 새로 정하지 않고 이미 있는 것을 쓴다 — 두 곳에 다른 숫자가 생기면 갈라진다.

### 23.3 워커가 채우는 것

| 항목 | 근거 |
|---|---|
| `model_name` · `prompt_version` | ADR-005의 4종 버전 중 나머지 둘 |
| `latency_ms` · `input_tokens` · `output_tokens` | T1 #10 비용 모델의 원자료 |
| `explanation_text` | **Eval 통과분만**(ADR-007) |
| `eval_result` 6지표 + `detail` | 채점은 기존 `loan_agent/eval.py`를 쓴다 |
| `assessment_case.status` · `current_explanation_run_id` | 통과 시에만 갱신(ADR-013) |

Eval 실패는 `REVIEW_REQUIRED`, 호출 실패는 `EXPLANATION_FAILED`. **어느 쪽이든 결정적 판정은 그대로 조회된다.**

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| Celery·RQ + Redis | ADR-003의 기각을 유지한다. 큐가 하는 일(작업을 안전하게 하나씩 꺼내기)을 **`SKIP LOCKED`로 이미 할 수 있고, DB는 어차피 쓰고 있다.** Redis를 넣으면 같은 일을 하는 저장소가 둘이 된다 |
| FastAPI `BackgroundTasks` | 프로세스 안에서만 살아 **재시작하면 작업이 사라진다.** 아웃박스를 쓰는 이유가 작업이 살아남는 것인데 그것을 없앤다 |
| 화면을 실행 주체로 (결과만 API에 기록) | 변경은 작지만 **완료가 클라이언트 생존에 달린다.** 상담원이 탭을 닫으면 그 작업은 영원히 `PENDING`이다. P0-a #5가 「LLM 실패 격리」인데 이것은 격리된 실패가 아니라 **방치된 레코드**이고, 아웃박스라는 서술도 성립하지 않는다 |

### 23.4 넘지 않을 선

**폴링 루프 + `SKIP LOCKED` + 재시도 한도까지만이다.** 분산 스케줄러·리더 선출·우선순위 큐·지수 백오프 자체 구현은 넣지 않는다. 재시도는 SDK 내장을 쓰고(ADR-018) 총 대기는 200초에서 끊는다(ADR-022).

이 선을 적어 두는 이유는, 워커가 생기면 얹고 싶은 것이 계속 나오기 때문이다. **도입 조건은 ADR-003과 같다 — 다중 인스턴스 또는 재시작 간 작업 보존이 DB로 감당되지 않을 때.**

### 23.5 공개 표면

워커는 HTTP 표면이 아니므로 `SPEC.yaml`의 `endpoints`에 들어가지 않는다. 다만 **운영 진입점(실행 명령·compose 서비스)이 하나 늘어나므로** 그 사실을 `SPEC.yaml`에 비HTTP 표면으로 기록한다. 게이트가 대조하지 못하는 자리라 사람이 읽는 기록으로 남긴다.

## ADR-024. 안내문을 실행하는 주체는 키를 가진 쪽이다 — 화면 직접 호출 폐기

> **2026-08-29 개정.** 제목과 결정을 「워커 하나」에서 「키를 가진 쪽」으로 바꿨다. 개정 사유와 무효화 범위는 이 절 끝 **§24-R**에 있다. 아래 본문은 개정 전 서술을 그대로 두되, 뒤집힌 문장은 §24-R이 지목한다.

**검증에서 발견했다(대장 #16).** ADR-003이 「실제 호출은 별도 실행기의 몫」이라 적고 ADR-023이 그 실행기를 만들었는데, **화면은 그것과 무관하게 자기 프로세스에서 LLM을 계속 부르고 있었다.** 「AI 안내문까지 생성」 버튼 한 번이 파이프라인을 직접 돌려 결과를 화면에 그리고, 곧이어 심사를 제출해 `explanation_run(PENDING)`을 하나 더 만든다. 워커가 그 행을 집어 **같은 심사의 안내문을 다시 생성한다.**

**무엇이 틀렸는가.** 토큰이 두 배로 나가는 것은 두 번째 문제다. 첫째 문제는 **방문자가 실제로 읽은 안내문이 아무 데도 기록되지 않는다**는 것이다. 그 실행에는 `explanation_run` 행이 없으므로 모델명·프롬프트 버전·지연·토큰·Eval 점수가 전부 남지 않는다. R7은 「모든 설명 시도가 조회 가능하다」인데 화면에 뜬 바로 그 시도가 조회되지 않는다. 포트폴리오 축 4(버전 감사)가 주장하는 것과 실제 경로가 어긋나 있었다.

**결정.** LLM을 부르는 주체는 워커뿐이다. 화면은 심사를 제출한 뒤 `GET /assessments/{id}/explanation-runs`를 폴링해 실행이 `PENDING`·`RUNNING`을 벗어나기를 기다리고, 완료된 실행의 안내문을 읽어 그린다. `_run_pipeline`을 화면 경로에서 제거한다.

**대가를 적어 둔다.** 화면이 비동기가 되어 「생성 중」 대기 구간이 생긴다. 데모 영상에서 즉답이 사라지는 것은 손해지만, **비동기 아웃박스를 실제로 돌린다는 사실 자체가 보여줄 것이므로** 서사로 회수한다. 즉답을 지키려면 실행 경로를 둘로 유지해야 하고, 그러면 ADR-023의 「워커가 유일한 실행자」가 거짓이 된다.

**새 엔드포인트는 없다.** 폴링이 읽는 것은 R7이 이미 가진 GET이다. 표면이 늘지 않으므로 이것은 범위 확장이 아니라 설계 이행이다.

**검토하지 않은 전제가 하나 있었다(대장 #27).** 이 결정을 쓸 때 **배포 대상을 확인하지 않았다.**
공개 라이브 데모(Streamlit Community Cloud)에는 API도 DB도 워커도 없고, 그곳에서 유일하게
동작하던 경로가 바로 여기서 없애려는 `_run_pipeline` 직접 호출이다. 재구축이 화면을 API
의존으로 바꾼 시점에 이미 그 데모는 끊겼으므로 **이 ADR이 원인은 아니지만, 마지막 남은 경로를
없애는 것은 맞다.** 공개 데모를 어떻게 할지 정해지기 전에는 이 결정을 이행하지 않는다.

**폴링의 상한은 새로 정하지 않는다.** ADR-022 §22.2가 설명 생성을 요청 타임아웃 계층 **밖**에 두고 전체 상한 200초를 이미 정해 놓았다. 화면의 폴링도 그 200초에서 끊는다. 타임아웃 계층(UI 15초)은 폴링 **한 번**의 HTTP 호출에 그대로 적용되고, 기다리는 전체 시간은 200초가 지배한다. **상한을 새로 만들면 같은 것을 가리키는 숫자가 두 개가 되고, 언젠가 갈라진다**(ADR-023 §23.2와 같은 이유).

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 화면 직접 호출을 유지하되 그 실행도 `explanation_run`에 기록 | 기록은 남지만 **실행 경로가 둘로 갈린다.** 워커가 같은 행을 다시 집지 않게 막는 예외 규칙이 생기고, ADR-023의 「워커가 유일한 실행자」 서술을 고쳐야 한다. 감사 경로가 두 벌이 되면 「어느 쪽이 진짜인가」를 매번 따져야 한다 |
| 화면에서 AI 안내문 버튼을 삭제 | 경계는 가장 깨끗하지만 **「AI가 안내문을 쓴다」는 시연을 한 화면에서 못 보여준다.** 관통 논리의 「덧셈」 쪽이 화면에서 사라진다 |

### §24-R. 개정 (2026-08-29)

**개정 사유.** 위 「검토하지 않은 전제」 문단이 유보해 둔 공개 데모 문제가 결론에 도달했다. 사용자 요구가 확정됐다 — **방문자가 자기 토큰으로 시현할 수 있어야 한다.** 그런데 방문자 키는 `ui` 프로세스의 세션 메모리에만 존재하고, 워커는 별도 프로세스라 DB를 통해서만 알 수 있는데 **키를 DB에 넣는 것은 금지 자동화 행위 ⑦이다.** 「워커가 유일한 실행자」와 「방문자 키로 실행 가능」은 양립하지 않는다.

**개정된 결정 — 키를 가진 쪽이 실행한다.**

| 키의 출처 | 실행 주체 | 방식 |
|---|---|---|
| 서버 키 (로컬 · compose · 영상 데모) | **워커** | 비동기 아웃박스. ADR-023 그대로 |
| **방문자 키** | **`app`** | `POST /assessments/{id}/explanation-runs`에 키 헤더가 오면 **동기 실행 후 완료된 실행을 반환** |

`app`이 실행 자리인 이유는 하나다 — **키가 HTTP 요청으로 도달할 수 있는 가장 안쪽**이기 때문이다. 더 안쪽(워커)으로 보내려면 저장해야 하고, 저장은 금지다.

**무효화되는 것.** 개정 전 본문의 「LLM을 부르는 주체는 워커뿐이다」와 기각 대안 표 첫 줄(「실행 경로가 둘로 갈린다」)이 뒤집혔다. 실행 경로는 **둘이 맞다.** 다만 개정 전이 우려한 「감사 경로가 두 벌」은 발생하지 않는다 — **두 경로 모두 같은 `explanation_run` 행을 집어 같은 컬럼을 채우기 때문**이다. 갈라지는 것은 *누가 집는가*이지 *무엇이 기록되는가*가 아니다. 개정 전에 진짜로 문제였던 것은 화면이 **행 없이** 실행한 것이었고, 그 결함은 이 개정에서도 그대로 해소된다.

**필수 부속 조건.** 이미 `PENDING` 행이 있을 때 409로 막으면 **방문자가 항상 409를 받는다** — 심사 생성 트랜잭션이 `PENDING`을 함께 만들기 때문이다(ADR-003 아웃박스). 그러므로 이 경로는 **기존 `PENDING` 행을 집어 실행**해야 한다. ADR-019가 정한 409는 *`RUNNING` 중 재요청*에만 적용된다.

**ADR-003을 위반하지 않는다.** ADR-003이 금지한 것은 **트랜잭션을 쥔 채 LLM을 부르는 것**이다. ADR-023 §23.1의 규율(행을 `RUNNING`으로 바꿔 커밋하고 커넥션을 놓은 뒤 호출)을 그대로 적용하면 커넥션은 호출 동안 풀에 반납된다. 양보하는 것은 **방문자의 HTTP 요청이 실제로 기다린다**는 점 하나이며, 상한은 ADR-022의 200초를 재사용한다(새 숫자를 만들지 않는다).

**운영 배포에는 워커를 두지 않는다.** 근거는 ADR-031 §31.3.

**§24-R-a. 스테일 `RUNNING`은 동기 경로가 함께 회수한다 (논리 검토에서 발견).** ADR-023은 200초를 넘긴 `RUNNING` 행을 `PENDING`으로 되돌리는 일을 **워커**에게 맡겼다. 그런데 ADR-031 §31.3이 운영에 워커를 두지 않으므로, **공개 데모에서 방문자가 실행 도중 브라우저를 닫으면 `RUNNING` 행이 영구히 남고 그 심사는 다시 실행할 수 없다**(ADR-019의 409에 영구히 걸린다). 회수 주체가 없는 상태 전이는 **빠져나올 수 없는 상태**이며 이는 설계 결함이다.

**결정.** 동기 경로가 행을 집을 때 **`PENDING`뿐 아니라 200초를 넘긴 `RUNNING`도 집는다.** 판정 조건은 ADR-023이 이미 쓰는 것과 같은 식이고 상한도 ADR-022의 200초를 그대로 쓴다 — **새 프로세스도 새 숫자도 만들지 않는다.** 스케줄러를 도입하는 대안은 기각한다(ADR-023이 이미 기각한 이유가 그대로 적용된다).

**§24-R-b. 상한 초과는 503으로 나간다 (논리 검토에서 발견).** 동기 실행이 ADR-022의 200초를 넘겼을 때 어떤 코드로 나가는지가 `SPEC.yaml` 오류 계약에 없었다. **503(upstream LLM provider unavailable)으로 통일한다** — 상한 초과는 실질적으로 제공자가 응답하지 않은 것이고, 새 코드를 추가하면 「같은 성격의 실패가 같은 코드로 나간다」는 규칙이 깨진다. 504를 새로 만들지 않는다.

**기각한 대안 (개정 시점)**

| 대안 | 기각 사유 |
|---|---|
| 방문자 키를 DB에 짧게 저장하고 워커가 읽는다 | **금지 자동화 행위 ⑦(키 영속화)을 정면으로 위반한다.** TTL을 붙여도 저장은 저장이고, 백업·로그·복제본으로 번진다 |
| 방문자 키 기능을 포기하고 녹화 데모만 제공 | 사용자 확정 요구 1을 버린다. **자기 키로 실제 실행해 볼 수 없는 데모는 껍데기**라는 것이 그 요구의 취지다 |
| 서버 키를 운영에 두고 모두가 공유 | 비용 남용에 노출된다(대장 B5). 방문자 키 방식은 **사용자 지갑이 열리지 않는다**는 장점이 함께 온다 |

## ADR-025. 추천 항목은 상품 상세까지 싣는다 — 철회한 R8과는 다른 것

**검증에서 발견했다(대장 #17).** 화면의 추천 상품 블록·대안 비교표·적격 상품 목록이 전부 도달 불가였다. `_screen_from_assessment`가 `추천상품: None`·`추천후보: []`를 하드코딩했기 때문인데, **하드코딩한 이유가 핵심이다** — API가 `product_code`와 `rank`만 주고 상품명·은행·금리범위·한도를 주지 않아 렌더할 값이 애초에 없었다.

**결정.** 추천 항목의 표현에 상품 상세(상품명·은행·금리범위·최대한도)를 포함한다. 화면은 하드코딩을 지우고 응답을 그대로 그린다.

**철회한 R8을 되살리는 것이 아니다.** R8은 「상품 데이터셋을 조회하는 **별도 엔드포인트**」였고, 기각 사유는 그것이 사용자 시나리오가 아니라 **기존 엔드포인트에서 역산된 것**이라는 점이었다. 이번 것은 엔드포인트를 추가하지 않는다. 이미 있는 자원의 표현을 채울 뿐이고, 시나리오는 실재한다 — 상담원이 화면에서 그 값을 읽는다. **사후 정당화의 표식(먼저 있는 코드에 요구사항을 맞추기)이 여기엔 없다.**

**부수 효과 하나를 적어 둔다.** 추천은 결정적 로직의 출력이지 LLM의 출력이 아니다. 관통 논리에서 「LLM에게 주지 않은 것」의 자리를 「신뢰 가능한 기술이 메운다」로 보이려면 그 결과가 화면에 있어야 한다. 이 블록이 죽어 있는 동안 **뺄셈만 보이고 덧셈이 안 보였다.**

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 추천 블록을 삭제 | 표면이 줄어 「적지 않은 것은 만들지 않는다」에 충실하지만, **가장 설득력 있는 시연 블록을 잃는다.** 죽은 코드를 지우는 것과 살아 있어야 할 기능을 지우는 것은 다르다 |
| `GET /api/v1/products` 재등재 | 화면 문제는 풀리지만 **철회 사유가 그대로 되살아난다.** 개정 이력에 「같은 판단을 두 번 뒤집었다」가 남고, 감사는 `product_dataset_version`으로 이미 충족된다 |

## ADR-026. 한 자원에 표현은 하나 — POST와 GET의 응답 형상을 통일

**검증에서 발견했다(대장 #22).** 같은 심사 자원인데 POST는 `verdict`·`dsr`을 평면으로 주고 진행 중 실행 **1건만** `explanation_run` 객체로 실었고, GET은 같은 값을 `decision`으로 감싸고 `explanation_runs` **배열 전체**를 실었다. 항목 3에 「재시도 항목에서 응답 형상을 확정한다」는 미결이 적혀 있었으나 항목 6에서 확정되지 않았고, 그대로 굳었다.

**결정.** GET의 형상으로 통일한다 — `decision` 중첩, `recommendations` 배열, `explanation_runs` 배열. POST 직후에는 그 배열에 `PENDING` 실행 하나가 들어 있을 뿐이며, 개수가 다른 것은 시점의 차이지 형상의 차이가 아니다.

**GET을 기준으로 삼은 이유.** 배열이 단건보다 넓다. 단건 형상을 기준으로 삼으면 재시도가 생긴 뒤 반드시 배열로 바꿔야 하고, 그때는 이미 클라이언트가 붙어 있다. **나중에 넓히는 것보다 처음부터 넓은 쪽이 계약을 덜 깬다.**

사유 없는 형제 비대칭은 설계 검토 §1 기준으로 결함이다. 여기엔 사유가 없었다 — 두 핸들러를 다른 시점에 쓰면서 앞의 것을 참조하지 않았을 뿐이다.

## ADR-027. 멱등 키는 클라이언트가 조작마다 만든다 — 내용 해시 폐기

**검증에서 발견했다(대장 #23).** 화면이 멱등 키를 `uuid5(정규화된 payload)`로 만들고 있었다. docstring은 「클릭마다 새 심사를 식별한다」인데 **코드는 정반대다** — 입력 수치가 같으면 시점·세션과 무관하게 영원히 같은 키가 나온다.

**무엇이 틀렸는가.** 그것은 멱등 키가 아니라 **내용 해시**다. 멱등 키의 관례는 「클라이언트가 논리적 조작 하나마다 고유한 키를 만들고, 서버는 그 조작의 재시도를 하나로 합친다」이다. 지금 구조는 R2가 막으려던 「같은 제출의 중복」이 아니라 **수치가 우연히 같은 다른 상담 건**을 삼킨다. 월소득·부채·등급·희망금액이 같은 두 고객은 흔하고, 두 번째 상담원은 새 심사 대신 남의 과거 심사를 200으로 돌려받는다.

**결정.** 화면이 클릭마다 `uuid4()`를 만들어 세션 상태에 보관하고, 같은 제출의 재시도(Streamlit 리런 포함)에서는 보관한 키를 다시 쓴다. 서버 쪽은 그대로다 — 같은 키에 다른 요청 해시면 409, 같으면 기존 심사를 200으로 재생한다. **`CLAUDE.md`의 「관례가 제공하는 것은 기본 채택」에 해당하며, 자체 해석을 쓸 사유가 없다.**

**관측 가능한 동작이 바뀐다.** 수치를 바꾸지 않고 버튼을 두 번 누르면 지금은 같은 심사가 재생되지만, 고친 뒤에는 심사가 둘 생긴다. **그것이 옳다** — 두 번의 상담은 두 건이다. 멱등성 시연은 「같은 제출의 재시도」로 하며, 그것이 원래 R2가 말한 것이다.

## ADR-028. 오류 코드 계약을 참으로 만든다 — 413·415 구현, 429는 기준을 다시 정의

**검증에서 발견했다(대장 #20).** `SPEC.yaml`이 413·415·429를 계약으로 선언했는데 **어느 경로에도 없었다.** 소스 전역에서 이 코드가 나오는 곳은 오류 제목 사전 3줄뿐이다. 실측하면 `text/plain`은 422로 나가고 2MB 본문은 상한 없이 수용된다.

**429가 특히 나빴다.** 명세 문구가 「세션당 실행 상한」이었는데 **인증 표면이 없으므로(ADR-009) API에는 세션이라는 개념 자체가 없다.** 구현할 수 없는 문구였고, 그래서 실행 상한이 Streamlit 세션 카운터에만 남았다. 화면이 API를 호출하는 구조로 바뀐 뒤에는 **API 표면에 상한이 아예 없다** — README가 광고하는 「비용 보호장치」가 그 자리에서 거짓이 된다.

**결정.**

| 코드 | 조치 |
|---|---|
| 413 | 본문 크기 상한을 미들웨어에서 강제한다. 자원 소진 통제이며 인증과 무관하게 성립한다 |
| 415 | 미지원 `Content-Type`을 422가 아니라 415로 내보낸다. 스키마가 틀린 것과 형식을 아예 못 읽는 것은 다른 실패다 |
| 429 | **명세 문구를 고친다** — 「세션당」을 버리고 **클라이언트 주소 기준**으로, 토큰을 쓰는 경로에 한해 API가 강제한다 |

화면의 카운터는 남기되 **통제가 아니라 안내로 격하한다.** 방문자에게 남은 횟수를 읽어주는 역할이며, 실제 상한은 API가 건다. 클라이언트가 거는 제한은 클라이언트를 우회하면 사라지기 때문이다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 세 코드를 명세에서 내린다 | 가장 정직하고 표면이 줄지만, **「비용 보호장치」 주장의 근거가 화면 카운터 하나로 줄어든다.** 413·415는 인증과 무관하게 몇 줄로 참이 되므로 내릴 이유가 약하다 |
| 429를 「세션당」 그대로 두고 인증을 넣는다 | ADR-009를 뒤집는다. **데모에는 사칭할 두 번째 사용자가 없어** 인증이 보호하는 것이 없고, 상한 하나 때문에 인증 표면을 만드는 것은 대가가 훨씬 크다 |

## ADR-029. 파싱 경계를 이중화한다 — 두 파서의 불일치가 검증이다

**재검토에서 발견했다(대장 #18·#28).** 이 프로젝트가 축 1에서 주장하는 명제는 이것이다.

> 에이전트 분리의 산물은 지능이 아니라 **검증 가능성**이다. 경계의 값어치는 **거기에 검증을 넣을 수 있는가**로만 정해진다.

**그 기준을 재구축 이후 상태에 적용하면 경계 3개 중 2개가 비어 있었다.** 판정이 `POST /assessments`에서 파이썬으로 계산돼 DB에 저장되면서 「심사 → 안내」 경계의 도구 강제가 불필요해졌고, 「파싱 → 심사」 경계에서는 검증(규칙 파서 교차검증·필수필드 게이트·사용자 확정 폼)은 살아 있으나 **Agent 1이 그 자리에 없다.** Agent 1은 워커 안에서 기계가 만든 문장을 다시 파싱하며, 그 결과는 어떤 검증도 거치지 않고 쓰이지도 않는다.

**미사용 코드는 결함이다.** 서사를 지키려고 남겨두는 선택은 하지 않는다.

**결정.** `POST /api/v1/parsing-preview`에서 **규칙 파서와 LLM 파서를 나란히 실행하고, 두 결과의 불일치를 응답에 싣는다.** 화면은 불일치 필드를 표시하고 **사람이 확정한다.**

- **자동으로 화해시키지 않는다.** 어느 쪽을 채택할지 코드가 정하면 그 판단이 다시 검증되지 않는 값이 된다
- LLM 키가 없으면 규칙 파서 결과만 반환한다. **저하는 되지만 실패하지 않는다**
- 저장하지 않는다(R5 그대로). 확정된 구조화 입력만 `POST /assessments`로 간다

**왜 이 자리인가.** 여기가 **경계에 결정적 검증을 넣을 수 있는 유일하게 남은 자리**다. 두 독립 파서의 출력 비교는 코드가 판정할 수 있고, 실패하면 사람에게 올라간다. 명제가 문장이 아니라 실행되는 코드로 증명된다.

**부수 효과.** Eval의 「파싱정확도」 지표가 제자리를 찾는다. 지금은 채점 대상이 없어 떠 있는 지표다(대장 #18).

**비용.** 짧은 JSON 1회 호출. 안내문 경로의 지연 문제(ADR-030)와 무관하다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| Agent 1을 안내문 경로에 그대로 둔다 | 지금 상태다. **출력이 검증도 사용도 되지 않는다.** 경계가 비용만 늘린다 |
| Agent 1을 삭제하고 규칙 파서만 남긴다 | 미사용 코드는 사라지지만 **검증을 넣을 수 있는 자리를 스스로 버린다.** 그리고 자연어 입력 처리 폭이 규칙 파서의 정규식으로 축소된다 |
| 불일치 시 LLM 결과를 채택하고 로그만 남긴다 | **검증이 아니라 통계 수집이 된다.** 실패가 흐름을 멈추지 않으면 게이트가 아니다 |
| 불일치 시 규칙 파서를 채택 | 위와 같은 이유. 게다가 규칙 파서가 항상 옳다는 근거가 없다 |

## ADR-030. 안내문은 LLM 1회 호출로 만든다 — 도구 왕복 4회 제거

**시연 중 실제로 문제가 됐다.** 안내문 생성에 30초가 걸린다. 원인은 모델 속도가 아니라 **호출 횟수**다.

| 단계 | LLM 왕복 | 내용 |
|---|---:|---|
| `parse_task` | 1 | 이미 확정된 구조화 값을 문장으로 되돌린 것을 다시 파싱 |
| `review_task` | 2 | `assess_loan_eligibility` 도구 호출 + 서술 |
| `advise_task` | 2 | `lookup_loan_product` 도구 호출 + 안내문 작성 |

**총 5회 순차.** 그런데 **판정·DSR·추천상품은 설명 실행이 시작되기 전에 이미 DB에 있다** — `POST /assessments`가 `core.screen_loan()`을 직접 불러 저장하기 때문이다. 파이프라인 안의 심사는 **밖에서 이미 한 심사를 다시 하는 것**이고, 그 결과는 서술용으로만 쓰고 버린다.

**결정.** 확정된 판정·DSR·추천상품 상세를 **프롬프트에 데이터로 주입하고 안내문만 1회 호출로 받는다.** 도구 왕복 4회가 사라진다.

**보장 수준이 올라간다.** 「도구를 부르라고 프롬프트로 시키는 것」과 「LLM에게 판정 권한이 애초에 없는 것」은 층위가 다르다. 도구 강제는 프롬프트 준수에 의존하지만, 데이터 주입은 **생성할 대상 자체가 없다.** 금지 자동화 행위 ⑤(CSV 밖 수치 생성)의 보장이 강해진다.

**ADR-025가 선행 조건이다.** 추천 항목이 상품명·은행·금리범위·한도를 이미 싣고 있어야 `lookup_loan_product` 왕복이 불필요해진다. 두 결정은 맞물려 있다.

**남는 지연은 스트리밍으로 다룬다 — 다만 이번 범위가 아니다.** 1회로 줄여도 몇 초는 걸린다. 첫 글자를 1초 안에 띄우는 편이 체감상 크지만, **ADR-007(Eval 통과분만 공개)과 부딪힌다.** 초안을 흘려보내고 끝난 뒤 게이트 결과를 표시하는 방식이 정직한 해법이나, 검증되지 않은 문장이 화면에 먼저 뜨는 것을 받아들여야 한다. **이번에 결정하지 않는다.** 지연 실측 후 재검토한다.

**측정이 선행한다.** 위 「5회」는 코드를 읽고 센 것이고 **단계별 실측은 하지 않았다.** `run_service_with_stages(on_stage=...)`가 단계 완료를 통지하므로 단계별 시간을 뽑을 수 있고, 대장 #19(토큰이 항상 None)를 고치면 단계별 출력 토큰이 보인다. **측정에 합격 기준을 두지 않는다. 알아야 할 것은 어디서 꺾이는가다.**

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 5회를 유지하고 모델을 빠른 것으로 교체 | **중복 연산은 그대로 남는다.** 같은 심사를 두 번 하는 구조가 문제이지 모델 속도가 문제가 아니다 |
| 도구 호출을 병렬화 | 도구 결과가 다음 프롬프트의 입력이라 **순차 의존이 실재한다.** 병렬화할 수 없다 |
| 안내문을 미리 만들어 캐시 | 입력 조합이 사실상 무한하다. 적중률이 0에 가깝다 |
| CoT·Self-Consistency 서술을 유지 | 그 서술은 **판정을 만들지 않는다**(판정은 이미 났다). 유지 비용이 왕복 1회인데 얻는 것이 서술 길이뿐이다. 기법 이름을 지키려고 호출을 남기지 않는다 |

## ADR-031. 배포 형상 — AWS EC2 단일 인스턴스 + Compose. EKS 기각

**결정.** 공개 데모를 **AWS EC2 단일 인스턴스에 기존 `docker-compose.yml`을 그대로 올려** 운영한다.

### §31.1 왜 AWS인가

| 근거 | 내용 |
|---|---|
| 대상 조직 정합 | 한화생명이 AWS 하이브리드(Outposts)를 쓰고 신규 서비스를 EKS로 구축한다. 국내 금융권 AWS 활용 53% |
| 작업량 | **새로 만드는 것이 아니라 옮기는 것이다.** Compose가 이미 있다 |
| 설계 검증 | ADR-011의 3-tier 격리가 실환경에서 증명된다 — Security Group으로 `postgres` 미노출을 한 번 더 확인 |

### §31.2 EKS·Kubernetes를 기각한다

**ADR-001의 전환 조건 네 가지가 하나도 성립하지 않는다** — 독립 배포가 필요한 컴포넌트 없음 / 프로세스 경계 장애 격리 불요 / 확장·보안 요구가 갈리지 않음 / 실부하 없음. 인스턴스 1개에 오케스트레이터를 얹는 것은 오케스트레이션 경험이 아니라 **설정 파일 한 벌**이다.

**대신 답변으로 갖는다.** 「대상 조직은 EKS를 쓰는데 왜 모놀리스인가」에 전환 조건 네 가지로 답한다. **기술을 더 보여주려는 목적의 분리는 사유가 아니다**는 ADR-001의 규칙을 여기서도 지킨다.

### §31.3 운영 배포에 두지 않는 것

| 대상 | 이유 |
|---|---|
| **서버 OpenAI 키** | 방문자가 자기 키를 쓰므로 사용자 지갑이 열리지 않는다. 금지 자동화 행위 ⑦과도 정합한다 |
| **워커** | 키가 없어 할 일이 없고, **켜 두면 방문자가 집을 `PENDING` 행을 먼저 집어 실패시킨다**(ADR-024 §24-R). 비동기 아웃박스는 로컬 Compose와 영상 데모에서 보여준다 |

**대가.** 공개 데모에서는 비동기 실행 경로가 동작하지 않는다. 이것을 README에 적는다 — **적지 않으면 문서가 다시 거짓이 된다.**

### §31.5 TLS는 선택이 아니다 (논리 검토에서 발견)

**방문자 API 키가 HTTP 헤더로 서버에 도달한다**(ADR-024 §24-R). Streamlit Community Cloud는 TLS를 제공했지만 **EC2에 직접 올리면 아무도 제공하지 않는다.** 평문 HTTP로 운영하면 방문자의 OpenAI 키가 네트워크를 평문으로 지난다. **이것은 타협 가능한 항목이 아니다** — 데이터 등급상 키는 운영 비밀이고, 대장 A4가 「세션 메모리에만 둔다」고 적은 통제가 전송 구간에서 무의미해진다.

**결정.** 리버스 프록시(Caddy 등)를 앞에 두고 Let's Encrypt로 TLS를 종료한다. 이로써 대장 B3의 「실서비스라면 진입점을 리버스 프록시 하나로 모은다」가 **데모에서 부분적으로 실현된다** — `app`의 호스트 직접 노출도 함께 사라진다.

**Security Group.** 인바운드는 80·443만 연다. SSH는 필요할 때만, 접속 주소를 제한해 연다. `postgres`는 애초에 컨테이너 내부망에만 있어 Security Group 대상이 아니다(ADR-011).

**중단 조건 연동.** TLS가 붙지 않으면 **방문자 키 기능을 켜지 않는다.** 그 경우 공개 데모는 녹화 픽스처 열람만 제공하고, 라이브 실행은 영상으로 대체한다(§31.4).

### §31.6 실제 구성 (2026-08-31 확정)

**도메인:** `gwang.dev` (Cloudflare Registrar, 연 $12.20, 자동 갱신) · **서비스:** `loan.gwang.dev`

**`.dev`를 고른 이유는 가격이 아니다.** 이 TLD는 브라우저가 HSTS를 강제해 **평문 접속이 원천 차단된다.** §31.5의 요구가 서버 설정이 아니라 TLD 성질로 한 번 더 보장된다. 다만 그것에 기대지 않고 `Strict-Transport-Security` 헤더도 명시한다 — 다른 TLD로 옮겨도 보장이 남아야 한다.

**구성 파일 3분할.** 로컬과 운영이 같은 파일을 쓰면 호스트 포트가 운영으로 새어 나간다.

| 파일 | 역할 |
|---|---|
| `docker-compose.yml` | 공통. **호스트 포트 없음.** 워커는 `profiles: ["local"]` |
| `docker-compose.override.yml` | 로컬 전용. 8501·8000 게시. **자동으로 얹힌다** |
| `docker-compose.prod.yml` | 운영 전용. `caddy` 추가(80·443). `-f`로 명시하면 override가 얹히지 않는다 |

```
로컬:  docker compose --profile local up -d --build
운영:  docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

**검증했다.** 로컬 구성은 `worker` 포함·8501·8000, 운영 구성은 `worker` 없음·80·443만. 프로파일과 `-f`의 조합으로 두 형상이 실제로 갈리는 것을 `docker compose config`로 확인했다.

**§31.6-a 리스크 대장 B3가 여기서 닫힌다.** B3는 「`app`의 호스트 노출은 타협이며 사유를 기록한다」였다. Caddy가 유일한 진입점이 되면서 **운영에서 `app`이 내부망에만 있다** — 화면이 서버 사이드에서 `app`을 부르므로 브라우저가 직접 닿을 이유가 없다. Swagger는 로컬과 영상 데모에서 보여준다.

**§31.6-b 접근 로그가 방문자 키를 지운다 (실측으로 확인).** Caddy의 JSON 접근 로그는 **요청 헤더를 기록하고 기본 마스킹 대상은 `Authorization`·`Cookie`뿐이다.** 직접 만든 `X-OpenAI-API-Key`는 그대로 남는다 — 그 상태로 두면 「키는 세션 메모리에만 둔다」는 통제가 로그에서 무너지고 금지 자동화 행위 ⑦을 어긴다.

`format filter`로 그 필드를 삭제하고, **실제로 요청을 흘려 검증했다** — 다른 헤더는 남고 키 문자열은 로그에 0회 등장한다. 문법 통과와 동작 보장은 다르므로 실측했다.

**§31.6-c Cloudflare 프록시는 켜지 않는다.** A 레코드는 **회색 구름(DNS only)** 이어야 한다. 주황색이면 Cloudflare가 TLS를 종료하고 EC2까지는 평문이 되어, ②(CloudFront)를 기각한 이유가 그대로 재현된다.

### §31.4 중단 조건

9월 6일까지 배포가 안정화되지 않으면 **라이브를 포기하고 영상 데모를 기본 증거로 삼는다.** README 배지도 함께 내린다. 이것은 실패가 아니라 이미 정한 축소 순서의 1번이다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| Streamlit Community Cloud 유지 | `streamlit run` **한 프로세스만** 띄운다. API·워커·PostgreSQL이 없다. 현재 공개 URL이 도는 것은 `main`이 재구축 이전 코드이기 때문이며 **병합하면 깨진다** |
| SQLite로 접어 한 프로세스로 배포 | ADR-008이 이미 기각했다(JSONB·부분 인덱스·`ON CONFLICT` 동작이 다르다). 3-tier를 한 프로세스로 접으면 ADR-011의 경계 자체가 없어진다 |
| Railway·Render 등 PaaS | 배포는 쉽지만 **대상 조직의 스택과 무관하고**, 3-tier 네트워크 격리를 스스로 구성해 증명할 기회가 사라진다 |
| ECS Fargate · App Runner | EC2보다 관리 표면은 적으나 **Compose를 그대로 쓰지 못해 작업량이 늘어난다.** 얻는 것이 이 규모에서 없다 |

## ADR-032. 금액·비율의 수치 표현 — 이진 부동소수점을 유지한다

**표준 검토에서 제기됐다.** 금융 소프트웨어에서 십진 금액을 이진 부동소수점(IEEE 754 binary64)으로 다루면 십진 소수를 정확히 표현할 수 없어 오차가 누적된다. 이것은 규범이 아니라 **공학적 사실**이며 실제 금융 사고 사례가 있다.

**이 프로젝트의 노출 지점.** `core.monthly_payment()`가 `float`를 반환하고, `screen_loan()`이 `dsr = 연간_원리금 / 연소득`을 계산해 **`dsr <= 0.30` / `dsr <= 0.40` 밴드 경계와 비교**한다. 경계 비교는 오차에 가장 민감한 연산이다.

**측정했다 — 결함이 아니다.**

DSR이 정확히 0.30이 되는 원금을 `Decimal`(40자리)로 역산하고, 그 지점 ±1원에서 `float`와 `Decimal`의 판정을 비교했다.

| 원금(원) | float DSR | 판정 | Decimal DSR (25자리) | 판정 |
|---:|---|:---:|---|:---:|
| 31,035,335 | 0.29999998597715943 | 여유 | 0.2999999859771539026927628 | 여유 |
| 31,035,336 | 0.29999999564356017 | 여유 | 0.2999999956435546674067220 | 여유 |
| 31,035,337 | 0.3000000053099609 | 보통 | 0.3000000053099554321206812 | 보통 |

**두 방식의 판정이 모든 지점에서 같다.** 이유는 입력 단위에 있다 — **1원이 최소 단위**라 원금이 1원 움직이면 DSR이 약 `1e-9` 변한다. 반면 binary64의 상대오차는 `1e-16` 수준이다. **판정을 뒤집으려면 참값이 경계에서 `1e-16` 이내여야 하는데, 1원 격자 위에 그런 입력이 존재하지 않는다.** 오차가 판정에 도달하기 전에 입력 해상도가 먼저 끝난다.

**결정.** `float`를 유지한다. **단, 조건을 명시한다** — 이 판단은 ①입력이 원 단위 정수이고 ②누적 연산이 없으며(한 번 계산하고 끝난다) ③비교 대상이 두 자리 소수 임계값일 때만 성립한다. **이 중 하나라도 깨지면 재검토한다.**

**깨뜨리는 변경**: 이자 스케줄을 회차별로 누적하는 상환표 / 원 미만 단위(외화·소수점 통화) / 금액을 더해 잔액을 이월하는 연산 / 임계값을 소수 8자리 이상으로 세분.

### §32.1 함께 발견한 결함 — 왕복 타입 불일치 (대장 #29)

`loan_agent/db/models.py:107`

```python
dsr: Mapped[float] = mapped_column(Numeric, nullable=False)
```

SQLAlchemy `Numeric`은 **`asdecimal=True`가 기본값**이라(2.0.51에서 확인) **읽을 때 `Decimal`을 돌려준다.** 쓸 때는 `float`가 들어간다. 타입 힌트 `Mapped[float]`는 왕복의 절반만 참이고, 읽은 값을 그대로 `float`와 섞어 산술하면 `TypeError`가 난다. 게다가 `Numeric`에 precision·scale이 없어 **저장 정밀도가 명시되지 않았다.**

**조치는 `/build`에서 한다.** 타입 힌트를 실제 왕복 타입에 맞추고, precision·scale을 명시하며, **왕복 타입을 확인하는 DB 통합 테스트를 추가한다.** 현재 `tests/test_assessments.py:56`은 `body["dsr"] >= 0`만 보아 타입을 검증하지 않는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 전면 `Decimal` 전환 | 측정 결과 판정이 달라지지 않는다. **바꿔서 얻는 것이 없는 변경**이며, 파싱·CSV·JSON 직렬화 경계마다 변환 지점이 새로 생긴다 |
| 금액을 정수 최소단위(원)로만 다루고 나눗셈을 유리수로 | DSR은 본질적으로 비율이라 어딘가에서 나눗셈이 필요하다. 유리수 유지는 비교 연산까지 직접 만들어야 한다 |
| 근거 없이 `float`를 그대로 둔다 | **이것이 개정 전 상태다.** 금융 도메인에서 「왜 부동소수점인가」는 반드시 나오는 질문이고, 답이 「몰랐다」면 결함이다. **측정해서 안전 범위를 아는 것과 모르고 쓰는 것은 다르다** |

## ADR-033. 준거 표준의 범위 — 무엇을 기준으로 삼고 무엇을 삼지 않는가

**검토 요청에서 나왔다.** 「IEEE 표준이 강제력은 없으나 금융 실무에서 중요하다」는 통념의 사실 여부를 확인했다.

**판정: 일반론으로는 부정확하다. 하나만 실질적으로 중요하다.**

| 구분 | 확인된 사실 |
|---|---|
| 국내 금융권이 실제로 요구하는 체계 | **전자금융감독규정**(전자금융거래법 제21조의 위임에 따른 금융위 고시 — 법적 강제) · **ISMS-P**(금융보안원이 금융권 적합 점검항목을 별도 안내) · **ISO/IEC 27001** · 금융보안원 가이드. **이 체계에 IEEE는 등장하지 않는다** |
| IEEE 소프트웨어공학 프로세스 표준 | 대부분 **IEEE 단독 표준이 아니다.** IEEE 830(요구사항 명세) → `ISO/IEC/IEEE 29148:2011`로 대체·폐지 · IEEE 1471(아키텍처 기술) → `ISO/IEC/IEEE 42010`(2011) · IEEE 829(테스트 문서) → `ISO/IEC/IEEE 29119-3`(2013). **「IEEE 표준」이라는 호칭 자체가 낡았다** |
| 실질적으로 중요한 하나 | **IEEE 754**(부동소수점). 금액 계산의 표현 오차 문제. 규범이 아니라 공학적 사실이라 강제력과 무관하게 걸린다 → **ADR-032에서 다뤘다** |

**결정 — 준거 표준을 다음으로 한정한다.**

| 축 | 기준 | 이 프로젝트의 대응 |
|---|---|---|
| 수치 표현 | IEEE 754 binary64의 한계 인지 | ADR-032 — 안전 범위를 측정하고 조건을 명시 |
| 요구사항 명세 | `ISO/IEC/IEEE 29148`의 **취지**(요구사항은 검증 가능해야 한다) | `SPEC.yaml` — 요구사항 ↔ 엔드포인트 대응, 수용 기준, 게이트 `S3`·`S4`가 기계 대조 |
| 아키텍처 기술 | `ISO/IEC/IEEE 42010`의 **취지**(이해관계자별 관점과 근거를 남긴다) | `docs/설계결정.md` — **기각한 대안을 필수 칸으로** |
| 보안·정보보호 | 전자금융감독규정 · ISMS-P의 **취지** | `docs/리스크_통제_대장.md` B절 · 게이트 `X1`·`I`축 |

**「준수했다」고 주장하지 않는다.** 위 표준들은 인증·심사를 거쳐야 준수를 말할 수 있고, 이 프로젝트는 어느 것도 받지 않았다. **기록하는 것은 「무엇을 기준 삼아 판단했는가」이지 「무엇을 통과했는가」가 아니다.** 리스크 통제 대장의 법령 서술과 같은 원칙이다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 「IEEE 표준 준수」를 포트폴리오에 적는다 | **거짓이 된다.** 대체·폐지된 표준을 현행처럼 인용하는 것은 확인하지 않았다는 증거로 읽힌다 |
| ISO/IEC 25010 품질특성 표를 채워 넣는다 | 표를 채우는 작업이 품질을 만들지 않는다. **이미 있는 증거**(테스트 축 분리·결함 주입·게이트)가 같은 것을 더 강하게 말한다 |
| 표준 항목을 아예 언급하지 않는다 | 「왜 이 기준인가」에 답할 근거가 사라진다. **판단의 출처를 적는 것이 이 프로젝트의 규칙**이다 |
