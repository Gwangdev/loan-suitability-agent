## 3. 근본 재검토가 필요한 것 3가지

### 3.1 에이전트 3개의 근거가 재구축으로 무너졌다

`PROJECT_LOG.md`의 「왜 멀티에이전트인가」가 세운 기준은 이것이다.

> 에이전트 분리의 산물은 지능이 아니라 **검증 가능성**이다.
> 경계의 값어치는 **거기에 검증을 넣을 수 있는가**로만 정해진다.

**그 기준을 재구축 이후 상태에 적용하면 경계 3개 중 2개가 비었다.**

| 경계 | 원래 검증 | 재구축 이후 |
|---|---|---|
| 파싱 → 심사 | 규칙 파서 교차검증 + 필수필드 게이트 + 사용자 확정 폼 | 검증은 살아 있으나 **Agent 1이 그 자리에 없다.** 폼은 `core.rule_based_parse`(파이썬)가 채우고 사람이 확정한다. Agent 1은 워커 안에서 **기계가 만든 문장을 다시 파싱**하며, 그 결과는 어떤 검증도 거치지 않고 쓰이지도 않는다(`#18`이 그 증거) |
| 심사 → 안내 | `assess_loan_eligibility` 도구 호출 강제 | **검증이 더 강해져서 Agent 2가 불필요해졌다.** 판정이 `POST /assessments`에서 파이썬으로 계산돼 DB에 저장된다. 「도구를 부르라고 프롬프트로 시키는 것」과 「LLM에게 판정 권한이 애초에 없는 것」은 보장의 층위가 다르다 |
| 안내 → 사용자 | Eval 6지표 + 디스클레이머 코드 강제 | **그대로 유효.** LLM 호출 뒤에 붙는 검증이라 에이전트 개수와 무관하다 |

**결론(잠정):** 안내문 경로에 남는 LLM의 일은 「확정된 판정을 고객 말로 푸는 것」 하나다.

**이것이 축 1 서사를 무너뜨리는지 여부가 재검토의 핵심이다.**
기록된 인사이트는 「멀티에이전트를 끝까지 밀면 가장 중요한 판정은 어느 에이전트에게도 주지 않게 된다」였다.
끝까지 밀어 판정이 파이썬으로 나갔다면, **「그럼 그 에이전트들은 왜 남아 있나」가 다음 질문**이고
그 답이 「안 남아도 된다」인 것은 반증이 아니라 결론일 수 있다. **판단 필요.**

**살릴 수 있는 자리 하나:** `POST /api/v1/parsing-preview`가 지금 규칙 파서만 쓴다.
여기에 LLM 파서를 나란히 두면 **두 파서의 불일치가 결정적 검증이 된다** — 그 경계에 검증을 넣을 수 있다.
덤으로 Eval의 「파싱정확도」 지표가 제자리를 찾는다(`#18` 참조). 이 경로는 짧은 JSON 1회라 응답시간 문제와 무관하다.

### 3.2 안내문 생성이 30초 걸린다 — 구조적 중복이 원인

**발표 시연 중 실제로 문제가 됐다.** 원인은 모델이 느려서가 아니라 **호출 횟수다.**

| 단계 | LLM 왕복 | 비고 |
|---|---|---|
| `parse_task` | 1 | 이미 확정된 구조화 값을 문장으로 되돌린 것을 다시 파싱 |
| `review_task` (도구 `assess_loan_eligibility`) | **2** | 도구 호출 + 긴 서술(CoT 4단계 + SC 3관점 + 적격/부적격 + DSR) |
| `advise_task` (도구 `lookup_loan_product`) | **2** | 도구 호출 + 안내문 작성 |

**총 5회 순차.** 그런데 판정·DSR·추천상품은 **설명 실행이 시작되기 전에 이미 DB에 있다.**
`POST /assessments`가 `core.screen_loan()`을 직접 불러 저장하기 때문이다.
즉 **파이프라인 안의 심사(②)는 밖에서 이미 한 심사(①)를 다시 하는 것**이고 그 결과는 서술용으로만 쓰고 버려진다.

**개선안(미확정):** 확정된 판정·추천상품 상세를 프롬프트에 데이터로 넣고 **1회 호출로 안내문만 받는다.**
도구 왕복 4회가 통째로 사라진다.

**체감 지연은 스트리밍이 지배한다.** 1회로 줄여도 몇 초는 걸리므로, 첫 글자를 1초 안에 띄우는 쪽이
발표에서 훨씬 크게 느껴진다. 다만 **ADR-007(Eval 통과분만 저장)과 부딪힌다** —
초안을 흘려보내고 끝난 뒤 Eval 배지를 띄우는 방식이 정직한 해법이다. 미확정.

**측정이 먼저다.** 위 「5회」는 코드를 읽고 센 것이고 **단계별 실측은 하지 않았다.**
`run_service_with_stages(on_stage=...)`가 단계 완료를 통지하므로 단계별 시간을 뽑을 수 있고,
`#19`(토큰이 항상 None)를 고치면 단계별 출력 토큰이 보인다. 이 프로젝트 규칙은
「측정은 합격 기준을 두지 않는다. 알아야 할 것은 어디서 꺾이는가다」이다.

### 3.3 공개 데모가 이미 끊겼고, 요구 1과 ADR-024가 충돌한다

- **현재 공개 URL이 도는 이유는 `main`이 재구축 이전 코드이기 때문이다.** 이 브랜치를 합치면 깨진다
- Streamlit Community Cloud는 `streamlit run` **한 프로세스만** 띄운다 — API·워커·PostgreSQL이 없다.
  **재배포는 해결이 아니라 방아쇠다**
- 한 프로세스로 접는 우회는 막혀 있다. SQLite는 ADR-008이 기각했고(JSONB·부분 인덱스·`ON CONFLICT`가 다르다),
  3-tier를 한 프로세스로 접으면 ADR-011이 만든 경계 자체가 없어진다
- **요구 1(방문자 토큰)과 ADR-024(워커 단일화)는 양립 불가다.** 방문자 키는 `ui` 프로세스 세션 메모리에만 있고,
  워커는 별도 프로세스라 DB를 통해서만 알 수 있는데 **키를 DB에 넣는 것은 금지**다

**잠정 구조(미확정):** 키를 가진 쪽이 실행한다.

| 키의 출처 | 실행 주체 |
|---|---|
| 서버 키 (로컬·compose·영상) | 워커. 비동기 아웃박스 — 현행 유지 |
| **방문자 키** | **`app`**. 키가 HTTP 요청으로 도달할 수 있는 가장 안쪽이다 |

실행 자리는 **`POST /api/v1/assessments/{id}/explanation-runs`(R6)** 로 충분하다 — 새 엔드포인트 없음.
키 헤더가 오면 동기 실행 후 완료된 실행을 반환하고, 없으면 지금처럼 `PENDING`만 만든다.
이미 `PENDING`이 있으면 409로 막지 말고 **그 행을 집어 실행**해야 한다(안 고치면 방문자가 항상 409를 받는다).

**ADR-003과의 관계:** ADR-003이 금지한 것은 **트랜잭션을 쥔 채 LLM을 부르는 것**이다.
ADR-023 §23.1의 규율(행을 `RUNNING`으로 바꾸고 커밋해 커넥션을 놓은 뒤 호출)을 그대로 쓰면 위반이 아니다.
양보하는 것은 **방문자의 요청이 실제로 기다린다**는 점이며, 상한은 ADR-022의 200초를 재사용한다.

**배포 형태(미확정):** `app` + `postgres`를 공개 호스트에 올린다.
**운영에는 서버 키를 두지 않는다** — 방문자가 자기 키를 쓰므로 사용자 지갑이 열리지 않는다.
**워커는 운영에 배포하지 않는다** — 키가 없어 할 일이 없고, 켜 두면 방문자가 집을 `PENDING`을 먼저 집어 실패시킨다.
비동기 아웃박스는 compose와 영상 데모에서 보여준다.
UI는 Streamlit Cloud 유지, `API_BASE_URL`을 secrets로 백엔드에 물린다.

**호스트 미선정.** Postgres가 필요하다. 무료 티어는 잠들었다 깨는 지연이 있어 데모 첫인상에 영향을 준다.

## 6. 재논의하지 않아도 되는 것 — 이미 확정

- **ADR-026 · 027** — 응답 형상 통일, 멱등 키를 클라이언트 생성 `uuid4`로.
  **이 둘은 3장의 재검토와 무관하므로 그대로 유효하다**
