# 배포 이후 검토 목록

**작성 2026-08-31 · 배포가 끝난 뒤 한 번에 처리한다**

> **왜 미뤘는가.** 이번 프로젝트에서 결함을 가장 많이 잡은 것은 코드를 읽는 일이 아니라 **실제로 돌리는 일**이었다. `/code-review`가 7건을 냈고, `docker compose up`이 기동 차단 2건을, 오너 키로 한 번 돌린 것이 4건을 더 냈다. `#47`(alpine uid)·`#48`(마이그레이션 부재)·`#49`(임포트 누락)는 **읽어서는 원리상 나올 수 없는 종류**다.
>
> 그리고 리뷰 커맨드는 **커밋 범위당 1회**다. 배포 전에 돌리면 배포 후 또 돌려야 하고, 두 번째는 「바뀌지 않은 코드를 다시 읽는」 것이 되어 새 정보가 나오지 않는다.

## 2. 리팩토링 — 보류한 것과 그 사유

### 2.1 `core.py` 추가 분할 — 재판정 필요

`#38`에서 **의도적으로 보류**했다. 현재 `core.py`는 약 350줄이고 변경 이유가 넷이다.

| 바뀌는 이유 | 해당 코드 |
|---|---|
| 심사 규칙 | `screen_loan` · `monthly_payment` |
| CSV 스키마 | `load_products` · `_pct` · `_grade` |
| 파싱 정규식 | `parse_korean_amount` · `rule_based_parse` · `missing_required_fields` |
| 데모 자료 | `load_demo_fixtures` · `TEST_CASES` · `EDGE_CASES` |

**보류한 이유:** 분할하면 **15개 파일 · 약 90개 참조 지점**을 건드려야 하고, 그러면 「순수 이동」이 아니게 되어 리뷰 대상이 된다. 배포 직전에 대규모 임포트 변경을 넣는 것은 회귀가 나오는 자리다.

**재판정 기준:** 배포가 끝나 코드가 안정된 뒤, 350줄이 여전히 읽기 불편한가. 불편하지 않으면 **하지 않는 것도 결정이다** — 파일 수를 늘리는 것 자체가 이득은 아니다.

### 2.2 이미 처리한 것 (참고)

`#38`에서 셋 중 둘은 끝냈다 — CSS를 `static/apple.css`로, LLM 경로를 `loan_agent/llm.py`로, 키 헤더를 `api/contract.py`로 분리했다. **`core.py`에 LLM을 부르는 코드가 한 줄도 없다**는 것이 그 결과이고, 이건 「판정은 코드, 설명은 LLM」을 디렉터리 구조가 증명하는 형태다.

## 5. 범위 판정 — 법규 적용 조건 판별기는 SPEC에 넣지 않는다

**판정 2026-08-31 · 조치 불요.** 같은 검토가 다시 올라오면 이 항목을 근거로 닫는다.

**검토 계기.** 현재 LLM은 입구(파싱 후보)와 출구(안내문) 두 곳에만 있고 판정에 닿지 않는다. 여기에 「법규 적용 조건 판별」 기능을 붙여 AI 활용 폭을 넓힐지, 그리고 지금 계획이 AI의 단점을 피하는 쪽으로만 기울어 있는지를 물었다.

**결론: SPEC에 추가하지 않는다.** 근거는 둘이다.

1. **일정.** 공개 표면을 하나 늘리면 `/design` 복귀 → SPEC 개정 → `/build` → `/verify` → 게이트를 다시 돈다. 배포 미완, 열린 라벨 17건, `G3` BLOCK, README 미작성, 완료 판정 「배포 보류」인 상태에서 그렇게 하면 「새 기능은 있는데 배포가 없는」 결과가 가장 유력하다. 중단 기준은 09-06이다.

2. **형태가 어긋난다 — 이쪽이 더 무겁다.** 적용 조건은 이미 `docs/리스크_통제_대장.md`와 `PROJECT_STATE.md` 인바리언트에 3단 표로 있고, 문서가 올바른 형태다. 문서일 때 그것은 **설계자의 판단 기록**이지만("PIPA 37-2의 구속력 있는 자동화 결정에 해당하지 않도록 사람이 결정하게 설계했다"), 런타임 기능이 되는 순간 **시스템의 주장**이 된다. 교육용 데모가 할 수 있는 주장이 아니고, 틀리면 그 자체가 가장 나쁜 실패다. 게다가 판별 대상이 **자기 자신**이라 입력이 고정되어 있다. 매 요청 같은 답이 나오는 것은 기능이 아니라 상수다.

**동반 판단 — 「AI 단점만 피하고 있는가」는 진단이 어긋났다.** 회피가 아니라, 이미 쓰고 있는데 그렇게 읽히지 않게 서술돼 있다. 코드에 실재하는 것:

- LLM을 **독립 파서로 세워 규칙 파서와 교차 대조**하고 불일치를 사람 검토로 승격(ADR-029) — LLM 없이는 성립하지 않는 기능이다
- **Eval 하네스 6지표** · 고정 픽스처 · 비용 0 · CI 실행(`loan_agent/eval.py`)
- 프롬프트 버전 · 모델명 · 토큰 · 레이턴시 · 에러코드를 실행 단위로 영속화
- 재생성 동시성 통제(앱 검사 + 부분 UNIQUE), 200s 상한, RUNNING 재클레임(ADR-019·022·024)
- 키 소유자에 따라 동기·비동기 경로가 갈리되 같은 감사 행을 클레임(ADR-024 §24-R)

관통 논리가 「뺄셈과 덧셈은 쌍」인데 덧셈 항목이 뺄셈의 부속으로 서술돼 있는 것이 실제 문제다. **범위가 아니라 서술의 문제이므로 `/handoff`에서 다룬다.**

**덧셈 축을 더 세우려면 표면이 아니라 측정이다.** ADR-020(로컬 sLLM 비교 축, P1, 미구현)이 그 자리다. 지원 대상 조직이 자체 Llama 기반 모델을 계획 중이고, 「왜 이 작업에 이 모델을 골랐는가」는 Eval 하네스로 이미 측정 가능하다. **새 공개 표면이 0개다.**

## 6. 배포 자체가 만들 검토 항목 (미리 적어 둔다)

배포하면 아래가 새로 생긴다. 배포 후 리뷰에서 함께 본다.

- **`README.md` 재작성 (`#13`)** — 배포 URL·실행 절차·API 표가 전부 바뀐다. **가장 마지막에 쓴다.** 앞의 것이 끝나야 사실을 적을 수 있다
- **공개 데모의 동작 범위 명시** — 운영에는 워커가 없어 **비동기 실행 경로가 동작하지 않는다**(ADR-031 §31.3). 이것을 README에 적지 않으면 문서가 다시 거짓이 된다
- **TLS 구성 기록** — ADR-031 §31.5에 실제 구성(무엇으로 인증서를 받았고 갱신이 어떻게 도는지)을 남긴다
- **비용 관측** — EC2·데이터 전송 실측치. 「돌려 보고 얼마 들었다」가 있어야 운영 판단을 말할 수 있다
