# LLM 출력 품질 평가 리포트 (Eval)

> 3-Agent 파이프라인의 **출력 품질을 정량 평가**한 결과와 방법을 정리한다.
> 구현: [`loan_agent/eval.py`](../loan_agent/eval.py) · 테스트: [`tests/test_eval.py`](../tests/test_eval.py)

---

## 1. 접근 — 비용 0, 재현 가능한 평가

LLM 출력은 비결정적이라 "잘 나왔다"를 감으로 판단하기 쉽다. 이를 막기 위해 **정답 대비 자동 채점**을 도입했다.

- **정답(ground truth):** 결정적 심사 함수 `screen_loan`이 산출하는 판정·추천상품·수치.
- **평가 대상:** 사전 녹화된 실제 3-Agent 출력([`demo_fixtures.json`](../loan_agent/demo_fixtures.json), 5개 케이스).
- **핵심:** LLM을 **재호출하지 않고** 녹화 출력을 채점하므로 **API 비용 0**, 완전 재현 가능하며 CI에서도 실행된다.

## 2. 지표

프롬프트 설계의 안전 목표를 그대로 지표로 만들었다(각 케이스 0/1).

| 지표 | 무엇을 보는가 |
|---|---|
| 파싱정확도 | Agent 1의 파싱 JSON이 규칙기반 정답과 핵심 필드(월소득·부채·신용등급·희망금액·직장유형) 일치 |
| 판정정합성 | 안내문의 결론이 결정적 판정과 어긋나지 않음(거절/불가 등 모순 표현 없음) |
| 디스클레이머 | 안내문에 필수 디스클레이머 포함 |
| 추천정합성 | 안내문이 결정적 추천상품(코드)과 일치, '어려움'이면 상품 미추천 |
| 수치근거 | 안내문의 금리·한도·수수료가 CSV/입력에 근거(환각 0) |
| 조건부표현 | '승인합니다' 같은 확정 표현 없이 조건부 표현 사용 |

## 3. 결과 (현재 파이프라인)

```
------------------------------------------------------------------------

상담필요 케이스               ✅       ✅       ✅       ✅       ✅       ✅   6/6
```


## 4. 평가가 실제로 결함을 잡는가 (검증)

전 지표 통과(30/30)만으로는 "평가가 무의미하게 통과만 하는 것"과 구분되지 않는다. 이를 배제하기 위해
**일부러 결함을 심은 출력**을 넣어 평가가 잡아내는지 테스트로 검증했다([`tests/test_eval.py`](../tests/test_eval.py)).

| 주입한 결함 | 잡아낸 지표 |
|---|---|
| 디스클레이머 누락 | 디스클레이머 ❌ |
| CSV에 없는 금리(예: 2.0%) 삽입 | 수치근거 ❌ |
| 확정 표현("승인합니다") | 조건부표현 ❌ |
| 결정적 추천과 다른 상품 언급 | 추천정합성 ❌ |
| 파싱 필드 오류 | 파싱정확도 ❌ |
| 판정 모순("거절되었습니다") | 판정정합성 ❌ |
| '어려움'인데 상품 추천 | 추천정합성 ❌ |

→ 평가 하네스는 통과뿐 아니라 **회귀(품질 저하)를 실제로 탐지**한다.

## 5. 활용

- 프롬프트를 수정한 뒤 이 평가를 다시 돌려 **품질이 오르내리는지 수치로 확인**한다(프롬프트 생성→평가→선택 루프의 평가 축).
- 파이프라인 출력을 갱신할 때 회귀 가드로 CI에서 함께 실행한다.

## 6. 한계와 확장

- 현재 평가는 **규칙 기반 채점**(문자열·수치 대조)이다. 표현의 자연스러움·설득력 같은 정성 품질은 다루지 않는다.
- 케이스 5종으로 한정된다. 경계·적대적 입력(프롬프트 인젝션 시도 등) 케이스를 확장하면 커버리지가 넓어진다.
- 확장 방향: LLM-as-judge(모델로 정성 평가), 케이스 자동 생성, 프롬프트 A/B 비교 채점.
