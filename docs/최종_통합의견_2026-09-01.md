# 최종 통합 의견 — 2026-09-01

> 대상: Loan Suitability Assessment Agent
> 관점: 한화금융 IT팀 테크리더의 최종 인수·배포 판단
> 목적: 세 리뷰의 중복을 제거하고 상충 의견을 판정해 실행 기준을 하나로 고정

## 1. 최종 결론

**기술 방향은 타당하지만 현재 공개 입력 기능과 금융회사 운영 인수는 승인할 수 없다. 다만 녹화·합성 데이터 전용 포트폴리오 데모는 유지할 수 있고, 아래 P0를 닫으면 공개 입력 기능도 조건부 승인할 수 있다.**

이 판단은 아키텍처 자체를 부정하는 것이 아니다. 결정적 판정을 LLM에서 분리한 구조, Caddy 단일 외부 진입점, DB 내부망, 원문 미저장, DB 제약 기반 멱등성은 유지할 가치가 있다. 승인하지 않는 이유는 다음 네 가지다.

1. 라이브 결과가 전체 적격·부적격 정보를 사실과 다르게 표시할 수 있다.
2. 실제 금융정보 입력 금지·저장·보유·삭제 고지가 없는 상태에서 구조화 값이 저장된다.
3. 명세가 약속한 413·415·429와 전역 자원 통제가 서버에 없다.
4. 문서·화면이 3-Agent·이중 파서·키 처리·통제 수준을 실제보다 강하게 설명한다.

| 사용 목적 | 최종 판정 | 허용 조건 |
|---|---|---|
| 녹화 결과만 보여주는 포트폴리오 데모 | **GO** | 노출 취급된 키 회전, 실제 입력·저장 경로 비활성, 녹화 결과임을 명확히 표시 |
| 현재 형태의 공개 라이브 입력 | **NO-GO** | P0 완료 전에는 녹화 데모 전용으로 제한 |
| P0 완료 후 공개 포트폴리오 데모 | **조건부 GO** | 결과·고지·비밀·자원 통제·모바일 기본 사용성 검증 |
| 한화금융의 실제 고객 대상 운영 | **NO-GO** | P0·P1 완료와 P2 운영 통제의 별도 인수 증거 필요 |

직접 악용 가능한 외부 Critical 취약점은 세 문서의 확인 범위에서 입증되지 않았다. 그러나 이는 “금융 운영에 안전하다”는 뜻이 아니라, 현재 외부 노출면에서 즉시 악용 경로를 재현하지 못했다는 뜻이다.

## 3. 세 문서의 공통 합의

### 3.1 유지해야 할 강점

- 핵심 대출 판정은 LLM 밖의 결정적 코드가 담당한다.
- 자연어 원문을 DB에 저장하지 않고 구조화 값과 판정 결과를 분리한다.
- Idempotency-Key, 요청 해시, DB UNIQUE 제약을 함께 사용한다.
- PostgreSQL transaction, FOR UPDATE SKIP LOCKED, statement timeout, readiness와 Alembic head 확인의 사용 목적이 명확하다.
- 외부에서 확인한 8000·8501·5432·2019는 닫혀 있었고 공개 API 경로는 Streamlit shell로 응답했다.
- SQL injection, command injection, SSRF, path traversal과 현재 렌더 경로의 XSS는 확인되지 않았다.
- 테스트는 DB 제약·멱등 경쟁·worker claim·Eval 결함 주입까지 포함한다.

### 3.2 공통으로 인정된 핵심 결함

- 서버 측 413·415·429 통제가 명세에만 있고 구현에는 없다.
- 전체 eligibility와 부적격 사유가 API/UI 경계에서 손실된다.
- 실제 개인정보 입력 금지 고지와 데이터 수명주기가 없다.
- UI가 불필요한 DB 비밀번호를 환경변수로 가진다.
- 3-Agent·두 파서 교차검증이 공개 UI에서 실제로 실행되지 않는다.
- 모바일 sidebar, 다크모드 label, 진행 상태와 오류 안내가 사용을 방해한다.
- 운영 핵심 컨테이너의 자동 재시작 정책이 없다.
- 의존성이 고정되지 않았고 CI가 lint·type·dependency·image 검사를 필수화하지 않는다.

### 3.3 공통 원인

개별 버그의 공통 원인은 **문서가 약속한 통제와 실제 실행 경로가 갈라졌지만 그 약속을 직접 겨냥한 계약 테스트가 없었다는 것**이다.

- 명세는 413·415·429를 이미 구현된 통제처럼 적었지만 endpoint 목록 검사만 있어 동작 부재를 잡지 못했다.
- 위험 통제 대장은 개인정보 입력 금지 고지를 적었지만 화면에는 notice bar가 렌더되지 않는다.
- 주석은 파싱정확도 N/A를 통과로 기록하지 않는다고 설명하지만 다음 줄에서 True로 기록한다.
- 화면은 두 파서 대조를 설명하지만 실제 UI는 규칙 파서만 호출한다.
- 503을 사용자에게 전달하기 위해 client timeout을 조정했지만 catch-all exception이 상세를 다시 지운다.

따라서 가장 중요한 개선은 문서를 늘리는 것이 아니라 **각 약속에 실행 가능한 검증을 하나씩 연결하는 것**이다.

## 4. 상충 의견에 대한 최종 판정

| 쟁점 | 상충 의견 | 최종 판정 |
|---|---|---|
| 3-tier 우회가 모두 차단됐는가 | 테크리더 문서는 실제로 막혔다고 평가하고, 1차 리뷰는 전부 막혔다고 보증할 수 없다고 평가 | **관측한 외부 경로는 차단 확인, 전체 보증은 불가.** 외부 포트와 프록시 경로는 합격이다. SG·NACL·IPv6·IAM·IMDS와 다른 출발지는 미검증이므로 “전부”라는 표현은 쓰지 않는다 |
| 공개 데모는 모바일·다크모드만 고치면 되는가 | 테크리더 문서는 두 건을 제출 조건으로 제시하고, 1차 리뷰는 라이브 입력 중지를 권고 | **두 건만으로는 부족하다.** 잘못된 eligibility 표시와 실제정보 입력 고지가 사용자 판단·데이터 처리에 직접 영향을 주므로 함께 P0다 |
| 내부 API 인증·mTLS가 지금 필요한가 | 1차 리뷰는 권고하고 project_review는 오버엔지니어링으로 평가 | **현재 단일 노드 데모의 P0가 아니다.** app 외부 노출, UI 다중 인스턴스, 목록 기능 연결, 실제 사용자 식별 중 하나가 발생하면 즉시 필수로 전환한다 |
| ChromaDB Critical advisory가 배포 차단인가 | upstream CVSS 9.3이지만 서비스는 Chroma endpoint를 실행하지 않음 | **현재 직접 RCE로 판정하지 않는다.** 미사용 transitive dependency이므로 P1에서 제거한다. Chroma server를 켜는 순간 즉시 배포 차단으로 승격한다 |
| AWS Multi-AZ·RTO/RPO·IAM 검증이 앱 리뷰 범위인가 | 1차 리뷰는 금융 운영 조건으로 요구하고 project_review는 인프라 조직 영역이라고 평가 | **현재 데모 수정 범위는 아니지만 금융 운영 인수 조건은 맞다.** 애플리케이션 결함이 아니라 Infra/Security 소유의 P2 증거로 분리한다 |
| Streamlit을 바로 React/Vue로 바꿔야 하는가 | 앞 리뷰는 CSS 수정, project_review는 구조적 한계와 frontend 전환을 지적 | **지금은 바꾸지 않는다.** 포트폴리오 데모는 light theme 고정과 responsive CSS로 충분하다. 실제 고객·인증·접근성 SLA·복잡한 비동기 상태가 요구되면 frontend 재선정 ADR을 연다 |
| Denial of Wallet 통제가 빠졌는가 | project_review는 CAPTCHA·hard quota를 요구 | **현재 운영은 방문자 본인 키를 쓰므로 서비스 소유자의 API 과금 폭증 경로는 없다.** 대신 서버 자원 DoS는 남는다. 서버 소유 키를 도입하는 순간 CAPTCHA, per-user hard quota, 예산 alert와 kill switch가 필수다 |
| LLM parser prompt injection 검토가 빠졌는가 | project_review가 자연어 parser의 adversarial 공격을 지적 | **현재 공개 UI는 LLM parser를 호출하지 않아 현행 판정 경로의 직접 취약점은 아니다.** 두 파서 기능을 연결할 때 구조화 schema, 값 범위, 불일치 표시, 사용자 확정, adversarial test를 함께 넣어야 한다 |
| core.py를 분할해야 하는가 | 1차 리뷰는 대형 module을 부채로 보고 테크리더 문서는 유지 판단 | **지금은 분할하지 않는다.** 결정적·무키 core라는 경계가 명확하고 353줄 분할의 실익이 작다. 500줄 초과 또는 하위 영역의 변경 주기가 갈릴 때 재검토한다 |
| 과거 G3 BLOCK이 배포 차단인가 | 테크리더 문서는 상주 BLOCK을 조건부 허용 | **제품 결함은 아니다.** 과거 이력에 대한 경고는 해소 불가능하므로 신규 BLOCK 0과 경고별 판정 기록을 기준으로 삼는다. raw 경고 개수를 품질 지표로 사용하지 않는다 |

## 6. 실행 우선순위

### 6.1 즉시 사고 대응

1. 검토 중 노출 취급된 OpenAI 키를 폐기·회전하고 사용량을 확인한다.
2. 회전 증거가 없으면 해당 키를 사용 중인 모든 로컬·CI·운영 경로를 잠정 불신한다.
3. 공개 서비스는 P0가 끝날 때까지 실제 입력을 받지 않는 녹화 데모 모드로 제한한다.

### 6.2 P0 — 공개 입력 기능 재개 전

1. **결과의 진실성**
   - live 경로에서 빈 부적격 사유를 “모든 상품 충족”으로 표시하지 않는다.
   - 최소 조치는 정보 없음과 빈 결과를 구분하는 것이다.
   - 완전한 해결은 전체 eligibility와 reason을 core→DB→API→UI에서 동일하게 전달하는 것이다.

2. **데이터 처리 고지**
   - 실제 개인정보 입력 금지, 합성 상품, 저장 항목, 보유기간과 삭제 방법을 제출 전에 표시한다.
   - 데모 목적이면 예시 선택형 또는 비영속 처리 경로를 우선한다.

3. **비밀 최소화**
   - UI의 env_file을 제거하고 API_BASE_URL처럼 필요한 비밀 아닌 값만 전달한다.
   - 방문자 키가 DB에는 저장되지 않지만 Streamlit 서버 메모리와 내부 API를 통과한다는 사실을 정확히 고지한다.

4. **서버 자원 통제**
   - body·header 상한, Content-Type 검사, API rate limit, LLM global concurrency 상한을 구현한다.
   - 413·415·429가 실제 통합 테스트에서 발생해야 한다.

5. **기본 사용 가능성**
   - sidebar 강제 고정과 collapse button 제거를 desktop media query 안으로 제한한다.
   - 현 디자인은 light-only로 고정하고 다크모드에서 label이 사라지지 않게 한다.
   - app·ui·postgres에 운영 restart policy를 적용하고 재기동을 확인한다.

6. **제품 설명 정합성**
   - 두 파서를 연결하기 전에는 3-Agent·이중 파서 대조가 현재 실행 중이라고 표시하지 않는다.
   - USER_GUIDE.md를 대출 서비스 전용 문서로 교체한다.

### 6.3 P1 — 다음 기능 배포 전

1. 한국어 억·만·천만 단위와 trailing comma를 정규화하고 Eval mutation test를 추가한다.
2. 파싱정확도 N/A를 True로 기록하지 않도록 metric·DB 계약을 정리한다.
3. 금액·Idempotency-Key 상한과 FastAPI response model을 정의한다.
4. 두 파서 UI를 연결한다면 structured schema, 값 범위, 후보 불일치, 사용자 확정, prompt injection test를 동시에 도입한다.
5. visitor LLM 실행을 queue+polling으로 바꾸거나 최소한 진행 표시, 오류 구분, stable idempotency와 concurrency 상한을 제공한다.
6. explanation 상태 전이마다 AuditEvent와 연결 가능한 correlation ID를 기록한다.
7. 사용하지 않는 crewai tools extra와 ChromaDB를 제거하고 hash가 있는 lock·SBOM을 만든다.
8. CI에 Ruff, format, type, coverage, Compose invariant, migration, dependency와 image scan을 required check로 추가한다.
9. 운영 배포 기준을 main이 아니라 명시적 release tag/SHA와 단일 deploy command로 고정한다.

### 6.4 P2 — 금융 운영 전환 조건

다음 항목은 현재 포트폴리오 데모를 위해 모두 구현할 필요는 없지만, 실제 고객·사내 사용자를 받는 순간 필수다.

1. 사용자 인증, assessment 소유권, 목록·재생성 권한 검사
2. app 외부·사내망 노출 또는 UI scale-out 시 UI→app workload 인증과 필요 시 mTLS
3. migration owner·runtime DML·read-only DB role 분리
4. IaC 기반 SG·NACL·IPv6·egress, IMDSv2, 최소 IAM, EBS·snapshot 암호화
5. backup restore rehearsal, RTO/RPO, 중앙 log redaction, 보안·비용 alert
6. worker를 운영 활성화하기 전 fencing token과 저장 판정 기반 Eval
7. 실제 고객정보 처리 시 개인정보·금융소비자보호·모델 리스크 검토
8. 인증·복잡한 비동기 상태·접근성 SLA가 생기면 Streamlit 유지 여부 재판정
9. 서버 소유 OpenAI 키를 도입하면 CAPTCHA, per-user hard quota, budget alert와 kill switch

## 7. 승인 기준

### 7.1 공개 라이브 데모 재개

다음 결과가 모두 증거로 남아야 한다.

- 노출 취급 키가 폐기·회전됐다.
- UI container에 DB password와 server OpenAI key가 없다.
- live·recorded 경로의 판정·eligible count·ineligible reason 의미가 일치한다.
- 실제정보 금지·저장·보유·삭제 고지가 제출 전에 보인다.
- 413·415·429와 LLM concurrency 제한이 자동 테스트로 확인된다.
- 375~390px 모바일에서 입력·결과에 접근할 수 있다.
- light theme 고정 또는 dark theme label 대비가 확인된다.
- app·ui·postgres가 EC2·Docker 재기동 후 복구된다.
- 화면·README·USER_GUIDE가 실제 파서와 키 처리 경로를 그대로 설명한다.

### 7.2 금융회사 운영 인수

공개 데모 승인만으로는 부족하다. 추가로 다음 증거가 필요하다.

- P1 전체 완료와 미해결 advisory의 reachability·보완통제·만료일
- 사용자·서비스·DB 권한 모델과 데이터 수명주기
- AWS 설정 export 또는 IaC 검증, backup restore와 장애 훈련 결과
- 모바일·다크·키보드·화면낭독기·200% 확대 회귀 결과
- 부하·침투 시험, 비용 상한, 운영 관측성과 incident runbook
- 실제 고객정보를 다룰 수 있다는 보안·개인정보·금융 규제 승인

## 8. 구현하지 않을 것과 재검토 조건

현재 단계에서 아래 작업은 하지 않는 것이 낫다.

| 보류 작업 | 현재 판단 | 재검토 조건 |
|---|---|---|
| core.py 기계적 분할 | 경계를 약하게 만들고 실익이 작음 | 500줄 초과 또는 하위 기능의 변경 주기 분리 |
| 모든 내부 구간 mTLS | 단일 노드 데모에는 과도함 | app 노출, UI scale-out, 실제 사용자·테넌트 도입 |
| 즉시 React/Vue 전환 | 포트폴리오 데모에는 CSS·theme 수정이 저비용 | 인증, 복잡한 비동기 UX, 모바일·접근성 SLA |
| Multi-AZ 구축 | 현재 데모 목적·비용에 맞지 않음 | 금융 운영 RTO/RPO와 가용성 SLA 승인 |
| Chroma 취약점만 이유로 서비스 중단 | 현재 endpoint가 실행되지 않아 직접 도달 불가 | Chroma import·server endpoint 또는 관련 tool 활성화 |

이 보류는 “위험이 없다”가 아니라 **현재 범위에서 더 직접적인 P0를 먼저 해결한다는 우선순위 결정**이다. 전환 조건이 발생하면 자동으로 다시 열린다.

## 9. 남은 불확실성

- AWS 보안그룹 전체 source, NACL, IPv6, IAM, IMDS, EBS·snapshot
- 다른 외부 출발지에서의 SSH와 backend port 차단
- 실제 운영 로그의 secret·금융정보 redaction과 보유기간
- iOS·Android 실기기, Safari·Firefox, VoiceOver·TalkBack
- 고부하, provider 429·quota·장시간 지연, 패킷 유실
- backup·restore 실효성과 운영자 장애 대응
- 키 회전이 실제로 완료됐는지

이 항목은 추측으로 통과 처리하지 않는다. 금융 운영 판단에서는 미검증을 실패와 동일하게 취급하고, 포트폴리오 데모에서는 범위와 한계를 화면·문서에 명확히 표시한다.

## 10. 최종 테크리더 의견

**이 프로젝트의 가장 좋은 판단은 LLM을 판정에서 제외한 것이고, 가장 큰 약점은 그렇게 만든 안전 서사를 실제 실행 경로와 테스트가 끝까지 따라가지 못한 것이다.**

따라서 다음 단계는 아키텍처를 크게 바꾸는 일이 아니다. 먼저 거짓으로 보일 수 있는 결과와 설명을 없애고, 실제 데이터·비밀·자원 사용의 경계를 코드와 화면에서 일치시키며, 문서에 적힌 통제를 그 통제 자체를 겨냥한 테스트로 고정해야 한다.

한화금융 IT팀의 인수 관점에서는 현재 운영 승인을 거절한다. 그러나 결정적 core, 트랜잭션·DB 제약, 단일 외부 진입점과 테스트 자산은 재사용할 가치가 충분하다. P0와 P1을 증거 기반으로 닫고 P2를 조직별 인수 항목으로 분리한다면, “기술을 많이 쓴 데모”가 아니라 “위험한 일을 식별하고 통제 가능한 경계로 축소한 금융 의사결정 지원 시스템”으로 방어할 수 있다.
