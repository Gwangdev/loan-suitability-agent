# 리스크 통제 대장

> 본 서비스는 **교육용 데모**다. 아래 어느 항목도 「법령을 준수했다」고 주장하지 않는다.
> 이 문서가 기록하는 것은 **어떤 조건에서 무엇이 적용·필요해지는지, 데모가 왜 그 조건 밖에 있는지, 실서비스로 전환하면 무엇을 검토·도입해야 하는지** 세 가지다.
> 법률 자문을 받지 않았고 받았다고 주장하지 않는다.
> **조문 번호는 확정한 것만 적는다.** 확정하지 못한 것은 법 이름과 취지만 쓴다 — 틀린 조문 번호는 없느니만 못하고, 하나가 틀리면 나머지 서술의 신뢰도까지 함께 떨어진다.

## 읽는 방법 — 3단 구조

```
① 실무에서 이 조건이면 이것이 적용·필요하다      ← 지식
② 본 데모는 그 조건 밖으로 범위를 설계했다         ← 판단
③ 실서비스로 전환하면 무엇을 검토·도입해야 하는가   ← 확장 이해
```

②에서 멈추면 "안 걸리게 피했다"로 끝나 소극적으로 읽힌다. **③이 있어야 "모르는 게 아니라 안 한 것"이 증명된다.**

관통 논리와 같은 형태다 — **범위를 좁히는 것(뺄셈)과 신뢰 가능한 수단으로 채우는 것(덧셈)은 쌍이다.**

## A. 법적 리스크

### A1. 자동화된 결정 — 이 대장의 중심축

| 칸 | 내용 |
|---|---|
| **① 조건 / 적용** | 승인·거절을 **확정**해 제공하면, 개인정보보호법 **제37조의2**(자동화된 결정에 대한 거부·설명요구권)의 대상이 된다. 대출 승인·거절은 「개인의 권리에 중대한 영향을 미치는 자동화된 결정」의 교과서적 사례다 |
| **② 데모의 범위 설계** | **확정 판정을 하지 않는다.** 시스템은 구조화된 적합성 판단과 근거를 제시하고 **상담원이 최종 결정**한다. 제품 범위 선택이 곧 조건 회피로 이중 기능한다 |
| **기각한 대안** | 「참고용입니다」 고지만 붙이고 확정 판정 제공 → 고지는 결정의 성격을 바꾸지 못한다. 실제로 그 값으로 승인·거절이 이뤄지면 자동화된 결정이다 |
| **③ 전환 시 도입 검토** | 자동화 결정 **사전 고지**, **거부 요청 접수 창구**, 설명 요구에 대한 응답 절차, 재심사 경로, human-in-the-loop 개입 지점의 명문화 |
| **검증 방법** | API에 승인·거절을 확정하는 표면이 없음을 `SPEC.yaml`로 대조(게이트 `S4`). 안내문에 확정 표현이 없음을 Eval **조건부표현** 지표로 채점 |

### A2. 대출성 상품 권유·중개

| 칸 | 내용 |
|---|---|
| **① 조건 / 적용** | 특정 상품을 **권유하거나 중개**하면 금융소비자보호법상 적합성 원칙과 설명의무가 적용된다 |
| **② 데모의 범위 설계** | 상품 **비교와 근거 제시**까지만 한다. 계약·신청·중개 행위가 없고, 합성 상품 데이터임을 화면에 고지한다. 모든 안내문에 디스클레이머를 **코드로 강제 삽입**한다 |
| **기각한 대안** | 프롬프트로 디스클레이머 삽입을 지시 → LLM이 누락할 수 있다. **후처리 강제가 우월하다**(관통 논리: 개선이 아니라 범위 밖으로) |
| **③ 전환 시 도입 검토** | 적합성·적정성 확인 절차, **설명의무 이행 기록 보존**, 부당권유 금지 통제, 광고 심의, 판매업자 등록 여부 검토 |
| **검증 방법** | Eval **디스클레이머** 지표(결함 주입: 디스클레이머 삭제 → 실패해야 함) |

### A3. 개인신용정보 처리

| 칸 | 내용 |
|---|---|
| **① 조건 / 적용** | 실제 소득·부채·신용등급을 수집하면 개인정보보호법 제15조(수집·이용)·제16조(최소수집)·제21조(파기)·제30조(처리방침)와 신용정보법이 적용된다 |
| **② 데모의 범위 설계** | **합성 데이터만 사용**하고 실제 개인정보 입력을 금지·고지한다. 자연어 원문을 저장·로깅하지 않는다(ADR-002) |
| **기각한 대안** | 암호화 저장 → **수집하지 않은 데이터는 유출되지 않는다.** 암호화는 키 관리·접근통제·파기 절차를 새로 만들지만 미저장은 그 문제군을 없앤다 |
| **③ 전환 시 도입 검토** | 수집·이용 동의 설계, 최소수집 항목 명세, **보유기간·파기 자동화**, 접근권한 분리, 저장·전송 암호화, 개인정보 처리방침 게시, 처리위탁 관리 |
| **검증 방법** | 저장 스키마에 원문 컬럼이 없음을 마이그레이션으로 확인. 로그 필드 화이트리스트 테스트 |

### A4. 국외 제3자 전송 (LLM 제공자)

| 칸 | 내용 |
|---|---|
| **① 조건 / 적용** | 개인정보를 국외 사업자에게 전송하면 개인정보보호법의 국외이전 규정이 적용된다(별도 동의·이전 항목 고지 등) |
| **② 데모의 범위 설계** | **개인정보 자체를 받지 않으므로 전송할 대상이 없다.** 구조화된 합성 수치만 전송한다. 방문자 API 키는 세션 메모리에만 두고 `os.environ`에 쓰지 않는다 |
| **기각한 대안** | 서버 키를 공유해 방문자 모두가 사용 → 비용 남용에 노출되고 처리자 책임이 한 곳에 집중된다 |
| **③ 전환 시 도입 검토** | 국외이전 별도 동의, **국내 리전 모델 또는 온프레미스 LLM 검토**, 처리위탁 계약, 전송 항목 최소화, 전송 로그 |
| **검증 방법** | 게이트 `X1`(자격증명 하드코딩). 키가 `os.environ`에 기록되지 않음을 단위 테스트로 확인 |

### A5. 거절 사유의 설명 책임

| 칸 | 내용 |
|---|---|
| **① 조건 / 적용** | 자동화된 결정에 대한 **설명 요구권**(A1과 같은 축)에 답하려면 「왜 이 결과인가」를 재현·설명할 수 있어야 한다 |
| **② 데모의 범위 설계** | 판정을 결정적 규칙이 산출하고 **부적격 사유를 항목별 코드**로 남긴다. LLM이 생성한 문장이 아니라 코드가 산출한 사유가 근거다 |
| **기각한 대안** | LLM이 생성한 설명을 근거로 사용 → 비결정적이라 같은 입력에 다른 설명이 나오고 **감사에서 재현되지 않는다** |
| **③ 전환 시 도입 검토** | 설명 이력 보존기간, 이의제기 프로세스, **차별 영향 평가**(신용등급 기반 거절이 특정 집단에 편중되는지) |
| **검증 방법** | 동일 입력 → 동일 판정·동일 사유 코드 재현 테스트. Eval **추천정합성**·**판정정합성** 지표 |

### A6. 감사 대응

| 칸 | 내용 |
|---|---|
| **① 조건 / 적용** | 금융 시스템은 「누가 언제 어떤 규칙·모델로 이 결과를 만들었는가」를 답할 수 있어야 한다. 전자금융업에 해당하면 감독규정상 기록·보존 의무가 함께 붙는다 |
| **② 데모의 범위 설계** | 규칙·상품·모델·프롬프트 **4종 버전을 결과에 불변 저장**(ADR-005). `audit_event`에 비민감 메타데이터와 Correlation ID 기록 |
| **기각한 대안** | 로그에만 남긴다 → 보존기간이 짧고 회전·유실된다. **과거 판정을 당시 규칙으로 재현할 수 없으면 감사 주장이 성립하지 않는다** |
| **③ 전환 시 도입 검토** | 감사 로그 **무결성**(append-only·해시체인), 보존기간 정책, 접근 자체에 대한 감사, 분리 보관 |
| **검증 방법** | 버전 4종이 저장되는지 통합 테스트. 판정 레코드에 `UPDATE` 경로가 없음을 `SPEC.yaml`로 대조 |

## B. 보안 리스크

### B1. 프롬프트 인젝션

| 칸 | 내용 |
|---|---|
| **① 조건 / 필요** | 사용자 자유 입력이 프롬프트에 삽입되는 모든 시스템에서 발생한다 |
| **② 데모의 범위 설계** | **판정을 LLM 밖에 두었다.** 인젝션이 성공해도 판정·추천·DSR은 바뀌지 않는다. 수치는 도구를 통해서만 얻으므로 CSV 밖 값을 만들 경로가 없다 |
| **기각한 대안** | 입력 필터링 강화 → **필터는 우회 가능하다.** 방어를 쌓는 대신 공격 대상이 그 자리에 없게 만드는 쪽이 우월하다 |
| **③ 전환 시 도입 검토** | 입력 구분자 격리, 출력 스키마 강제, 인젝션 시도 탐지·기록, 도구 호출 권한 최소화 |
| **검증 방법** | Eval **적대적 케이스**에 인젝션 입력 추가 → 판정 불변·디스클레이머 유지 확인 |

### B2. 수치 환각으로 인한 소비자 오인

| 칸 | 내용 |
|---|---|
| **① 조건 / 필요** | 금리·한도·수수료를 LLM이 생성하면 실제와 다른 값이 안내될 수 있다 |
| **② 데모의 범위 설계** | 수치는 **생성 대상이 아니다.** ReAct로 도구 조회한 값만 사용하고, Eval **수치근거** 지표로 CSV·입력 근거를 채점한다. 실패하면 설명을 공개하지 않는다(ADR-007) |
| **기각한 대안** | 환각 억제 프롬프트 강화 → 확률적 완화일 뿐 보장이 아니다 / 사후 사람 검수 → 확장 불가·비결정적 |
| **③ 전환 시 도입 검토** | 상품 데이터 실시간 동기화, 수치 표시 시점의 재검증, 안내문 스냅샷 보존 |
| **검증 방법** | 결함 주입 — CSV에 없는 금리(예: 2.0%) 삽입 시 **수치근거 지표가 실패해야 한다** |

### B3. 계층 격리 — 데이터 계층 노출

| 칸 | 내용 |
|---|---|
| **① 조건 / 필요** | 앱 계층이 뚫렸을 때 데이터 계층이 외부로 나가는 경로가 있으면 피해가 확산된다. 애플리케이션 규칙은 그 앱을 거치는 요청만 막지만 **인프라 격리는 거치지 않는 경로까지 막는다** |
| **② 데모의 범위 설계** | `postgres`를 **내부 전용 네트워크에만** 두고 호스트 포트를 게시하지 않는다(ADR-011). non-root + read-only 루트 파일시스템을 한 세트로 적용. DB 어드민 도구는 기본 기동 대상에서 제외 |
| **남은 타협(정직하게)** | `app`을 호스트에 노출한다 — Swagger를 포트폴리오 증거로 쓰기 위해서다. **실서비스라면 진입점을 리버스 프록시 하나로 모으고 `app`도 내부에만 둔다** |
| **③ 전환 시 도입 검토** | 리버스 프록시·API Gateway 단일 진입점, WAF, TLS 종료, DB 계정 최소권한(DDL 없음), 시크릿 매니저 |
| **검증 방법** | 게이트 축 **I** — `I1`(호스트 포트 게시) `I2`(non-root·read-only) `I3`(준비 상태) `I5`(내부망 격리) |

### B4. CORS — 설정이 아니라 구조로 없앤다

| 칸 | 내용 |
|---|---|
| **① 조건 / 필요** | 브라우저가 API를 **직접** 호출하는 구조에서만 CORS가 발생한다. 그리고 **CORS는 방어가 아니다** — 브라우저만 지키는 규약이라 서버 간 요청에는 적용되지 않는다 |
| **② 데모의 범위 설계** | Streamlit은 서버사이드 렌더링이라 `ui` 서버가 API를 호출하고 브라우저는 직접 호출하지 않는다. **CORS 설정이 필요 없는 구조**이므로 와일드카드 오리진을 열 이유 자체가 없다 |
| **기각한 대안** | CORS를 넓게 열고 「나중에 좁힌다」 → 넓게 연 설정은 좁혀지지 않는다 |
| **③ 전환 시 도입 검토** | SPA로 전환한다면 프록시 뒤 same-origin 경로 배치를 먼저 검토하고, 그래도 필요하면 허용 오리진을 명시 목록으로 |
| **검증 방법** | 코드에 CORS 미들웨어가 없음을 확인. 있으면 사유를 이 대장에 적는다 |

### B5. 비용 남용

| 칸 | 내용 |
|---|---|
| **① 조건 / 필요** | 공개 데모에서 LLM 호출이 무제한이면 키 소유자의 비용이 새어나간다 |
| **② 데모의 범위 설계** | 방문자별 키(세션 한정), 입력 길이 상한, 세션당 실행 횟수 상한, 연속 실행 쿨다운. 키 없는 방문자는 **녹화 픽스처**로 토큰 0 열람 |
| **알려진 한계** | 현재 상한이 세션 상태 기반이라 **다중 인스턴스에서는 무력화된다**(방어질문 ⑧) |
| **③ 전환 시 도입 검토** | Redis 등 공유 저장소 기반 레이트리밋, 인증 주체별 쿼터, 예상 비용 사전 표시, 누적 토큰 관측 |
| **검증 방법** | 한도 초과 시 **429** 반환 통합 테스트 |

## C. 책임·표현 리스크

### C1. 검증 범위의 과대 해석

| 칸 | 내용 |
|---|---|
| **① 조건 / 필요** | 「Eval 30/30 통과」를 안전성 증명으로 제시하면 실제보다 강한 주장이 된다 |
| **② 데모의 범위 설계** | **통과율과 함께 커버리지 한계를 항상 병기한다.** 100% 통과는 정의한 데이터셋·지표 안에서의 결과다. 규칙 기반 Eval은 표현의 자연스러움·설득력을 평가하지 못하고, 녹화 출력 평가는 실시간 제공자 장애를 검증하지 못한다 |
| **기각한 대안** | 통과율만 제시 → 전략기획서 §12 금지 과장에 해당 |
| **③ 전환 시 도입 검토** | 케이스 자동 생성, 정성 평가(LLM-as-judge **병행**), 실사용 입력 기반 회귀 |
| **검증 방법** | README·포트폴리오에 한계 절 존재 — 게이트 `D2` |
