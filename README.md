# 대출 상담 의사결정 지원

[![CI](https://github.com/Gwangdev/loan-suitability-agent/actions/workflows/ci.yml/badge.svg)](https://github.com/Gwangdev/loan-suitability-agent/actions/workflows/ci.yml)
[![Live Demo](https://img.shields.io/badge/Live%20Demo-loan.gwang.dev-0066cc)](https://loan.gwang.dev)

**LLM의 정확도를 높이는 데만 의존하지 않고, 책임져야 할 판단에서 LLM을 제외했습니다.**

자연어로 받은 대출 상담 정보를 구조화하고, 규칙 기반 코어 함수가 적합성과 DSR을 계산한 뒤,
LLM이 확정된 결과를 고객용 안내문으로 설명하는 의사결정 지원 데모입니다.

[라이브 데모](https://loan.gwang.dev) · [API 명세](SPEC.yaml) ·
[설계 결정](docs/설계결정.md) · [평가 리포트](docs/평가리포트.md)

> 합성 데이터로 동작하는 데모 프로젝트입니다. 실제 대출 승인·거절, 상품 중개, 법률·금융
> 자문을 수행하지 않습니다.

---

## 한눈에 보기

| 질문 | 이 프로젝트의 답 |
|---|---|
| LLM이 틀리면 판정도 바뀌는가? | 판정과 DSR 계산은 코어 함수가 수행하므로 바뀌지 않습니다 |
| 자연어를 잘못 읽으면 어떻게 하는가? | LLM·규칙 파서 후보의 불일치를 노출하고 사람이 값을 확정합니다 |
| 안내문이 숫자를 지어내면 어떻게 하는가? | 확정값만 주입하고 Eval 6지표를 통과하지 못한 안내문은 공개하지 않습니다 |
| 같은 요청이 중복 실행되면 어떻게 하는가? | 요청 해시·멱등키·DB UNIQUE 제약으로 차단합니다 |
| 결과를 나중에 설명할 수 있는가? | 규칙·상품·모델·프롬프트 네 가지 버전을 판정과 함께 저장합니다 |

## 핵심 설계

```text
자연어 입력
   │
   ├─ LLM 파서 ─┐
   └─ 규칙 파서 ─┴─ 불일치 노출 → 사람이 폼 값을 확인·수정
                                      │
                                      ▼
                              확정된 구조화 입력
                                      │
                                      ▼
                              screen_loan()
                         적합성 · DSR · 상품 추천
                              (LLM 미개입)
                                      │
                                      ▼
                              LLM 안내문 생성
                                      │
                                      ▼
                              Eval 6지표 게이트
```

LLM은 고객과 직접 소통하는 **입구의 파싱 후보**와 **출구의 안내문**에만 있습니다. 승인가능·
상담필요·어려움 판정, DSR 계산, 상품 필터링과 추천은 `core.screen_loan`이 수행합니다.

```bash
grep -c "crewai\|Agent(\|Crew(" loan_agent/core.py   # → 0
```

금융 분야에서 중요한 것은 AI를 사용하는 사실보다 **어떤 판단을 AI에 맡기지 않았는지**라고
보았습니다. 프롬프트로 환각을 억제하는 것만으로는 부족하므로, 결과를 책임져야 하는 영역에서는
LLM의 성능을 개선하는 대신 LLM이 할 수 있는 일의 범위를 줄였습니다.

## 설계가 실제로 막은 오류

### 1. LLM 파서의 10배 금액 오류

LLM 파서는 “부채 200만원”과 “희망금액 500만원”을 각각 200,000원과 500,000원으로
읽었습니다. 규칙 파서는 2,000,000원과 5,000,000원으로 읽었고, 두 후보의 불일치가
드러나 사람이 심사 전에 값을 바로잡았습니다.

단일 LLM 파서만 사용했다면 10배 작은 금액을 기준으로 심사가 진행될 수 있었습니다. 당시
후보와 확정값은 `loan_agent/demo_fixtures.json`의 `parse_check`에 남겨 재현할 수 있습니다.

### 2. 규칙 파서의 10,000배 금액 오류

반대로 규칙 파서도 `3,000,000`을 300억 원으로 읽었습니다. “월급 700”을 700만원으로 보는
단위 생략 규칙이 콤마가 있는 원 단위 표기까지 적용된 것이 원인이었습니다.

콤마 개수와 금액 범위를 함께 보도록 로직을 수정하고, 한국어 수 단위 조합을 포함한 16가지
표기를 회귀 테스트로 고정했습니다. 다만 `500,000`처럼 콤마 하나에 백만 미만인 표기는 만원
관행이 적용되어 50억으로 읽힙니다. 원 단위로 적은 사용자일 수도 있으므로, 규칙을 임의로
늘리지 않고 실행 전에 사람이 자리수와 단위를 확인하도록 했습니다.

두 사례는 “LLM보다 규칙이 항상 옳다”는 결론이 아닙니다. 서로 다른 실패 방식을 가진 장치를
나란히 두고, 불일치를 사람이 확인할 수 있어야 한다는 근거입니다.

## 검증 결과

| 검증 | 결과 | 확인하는 것 |
|---|---:|---|
| 자동화 테스트 | **166개 수집**(DB 통합 포함) | 코어·API·DB·워커·UI 경계의 회귀 |
| LLM 출력 Eval | **90/90** | 15케이스 × 6지표 |
| Eval 역검증 | **결함 주입 7종** | 채점기가 실제 결함을 구분하는지 확인 |
| 기계 게이트 | **제출 전 자동 차단** — 현재 BLOCK 1 · WARN 11 | 명세·코드 괴리, 비밀키 노출, 미사용 표면 |
| 결정적 API 부하 시험 | **535 req/s** | 동시 요청 100건, 60초, 실패율 0%, p95 268ms |
| 설계 결정 기록 | **ADR 34건** | 채택·기각 이유와 전환 조건 보존 |

Eval은 파싱정확도·판정정합성·추천정합성·수치근거·조건부표현·디스클레이머를 검사합니다.
점수가 90/90이라는 사실만으로는 평가기가 정상인지 알 수 없기 때문에, 디스클레이머 삭제,
근거 없는 금리 삽입, 잘못된 상품 추천, 확정 승인 표현 등을 일부러 넣어 대응 지표만 실패하는지
확인했습니다.

```bash
pytest
python3 -c "from loan_agent import eval; eval.run_eval_selftest()"
python3 tools/gate.py .
```

부하 수치는 단일 Uvicorn 프로세스의 결정적 심사 API를 로컬 PostgreSQL과 함께 측정한 결과입니다.
LLM 호출 성능이나 다른 장비의 절대 성능을 의미하지 않으며, 같은 코드도 측정 머신의 다른 작업 부하에 따라
실행마다 최대 약 14% 흔들렸습니다. 측정 원본(측정 시각·커밋 해시·장비·
커넥션 풀 설정 포함)은 [`tests/load/results/`](tests/load/results/)에 있습니다. 미들웨어 구현 방식이
처리량을 약 10%씩 깎던 원인을 커밋 단위로 추적한 과정과 한계는 [프로젝트 로그](PROJECT_LOG.md)에
기록했습니다.

## 기술 구성

| 영역 | 선택 |
|---|---|
| API | FastAPI · Pydantic · RFC 9457 오류 응답 |
| 데이터 | PostgreSQL · SQLAlchemy · Alembic |
| AI | CrewAI · OpenAI · 규칙 파서 병렬 후보 |
| 정합성 | 단일 트랜잭션 · 멱등키 · 요청 해시 · DB UNIQUE 제약 |
| 비동기 처리 | 트랜잭셔널 아웃박스 · `FOR UPDATE SKIP LOCKED` |
| 배포 | AWS EC2 · Docker Compose · Caddy · Let's Encrypt |
| 검증 | pytest · Eval 하네스 · 기계 게이트 · GitHub Actions |

모듈러 모놀리스를 선택한 이유는 현재 규모에서 독립 배포·컴포넌트별 확장·프로세스 경계의
장애 격리가 필요하지 않았기 때문입니다. 대신 화면·API·DB는 컨테이너와 네트워크로 분리하고,
PostgreSQL은 외부에서 접근할 수 없는 내부망에 두었습니다. 전환 조건은
[ADR-001](docs/설계결정.md#adr-001-모듈러-모놀리스-fastapi--서비스-분리-기각)에 명시했습니다.

## 빠른 실행

LLM 키는 선택 사항입니다. 키가 없어도 결정적 심사와 사전 녹화 데모는 동작합니다.

공개 데모(https://loan.gwang.dev)에는 서버 LLM 키와 설명 워커를 두지 않았습니다. 안내문을
새로 생성하려면 방문자 본인의 OpenAI 키가 필요하며, 키는 세션 메모리에만 머물고 저장·로깅하지
않습니다. 키가 없으면 **토큰 없이 데모 보기**에서 사전 녹화된 실제 출력을 볼 수 있습니다.

```bash
cp .env.example .env
# .env에 POSTGRES_USER와 POSTGRES_PASSWORD를 입력합니다.

docker compose --profile local up -d --build
```

| 주소 | 내용 |
|---|---|
| http://localhost:8501 | 데모 화면 |
| http://localhost:8000/docs | OpenAPI 문서 |

공개 API 계약은 [`SPEC.yaml`](SPEC.yaml), 운영 배포는
[배포 절차서](docs/배포절차.md)에서 확인할 수 있습니다.

## 남긴 한계

- 실제 상품과 고객 정보가 아닌 합성 데이터만 사용합니다.
- DSR은 연 6%·60개월을 가정한 단순화 모델이며 개별 상품 금리를 반영하지 않습니다.
- 공개 화면은 규칙 파서가 채운 값을 사람이 확인하는 흐름만 제공하며, 두 파서 대조는 API에만
  노출합니다.
- `500,000`처럼 단위가 없는 표기는 만원 관행이 적용되어 50억으로 읽힙니다. 어느 쪽인지는
  표기만으로 확정할 수 없어 사람의 확인 단계로 넘겼습니다.
- 인증·권한이 없어 사용자를 식별하거나 자원 소유권을 구분하지 않습니다.
- 요청 상한은 프록시 구조상 방문자별이 아니라 사실상 인스턴스 전체에 적용됩니다.
- Eval 90/90은 녹화된 15케이스와 6개 규칙 지표 안에서만 성립하며 실시간 제공자 장애나 문장의
  자연스러움까지 보장하지 않습니다.

규제 준수를 주장하지 않습니다. 자동화된 결정, 상품 중개, 개인신용정보 처리, 전자금융거래의
적용 조건과 실서비스 전환 시 필요한 통제는 [리스크 통제 대장](docs/리스크_통제_대장.md)에 별도로
정리했습니다.
