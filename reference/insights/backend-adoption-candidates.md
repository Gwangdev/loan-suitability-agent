# 백엔드 채택 후보 — 판정이 필요한 목록

> **종류: 후보.** 미채택은 결함이 아니다. 검증 단계에서 이 파일의 항목을 결함으로 올리지 않는다.
> 원칙 목록과 혼동하지 않는다 — `INDEX.md` 참조.

## 판정 원칙

**아이디어 자체의 좋음과 「지금 이 프로젝트에 넣을지」는 별개다.**
후자는 언제나 **현재 규모에서 비용 대비 가치가 맞는가**로만 판정한다.
좋은 아이디어라는 이유로 채택하면 쓰지 않는 구조가 먼저 들어오고, 그 구조가 이후의 모든 변경에 비용을 붙인다.

각 항목은 **①무엇 ②가치가 생기는 조건 ③지금 넣을 때의 비용 ④채택 전 확인**의 네 칸으로 판정한다.
판정 결과는 채택·보류 어느 쪽이든 사유와 함께 프로젝트 기록에 남긴다. 보류는 결정이지 누락이 아니다.

## A. 구조 변경 없이 얹는 것 — 기본 채택 쪽으로 기운다

**로그 로테이션**
- 컨테이너 로그 드라이버에 파일 크기·보관 개수 상한을 건다. 여러 서비스에 같은 값을 쓸 땐 앵커로 한 번만 정의한다.
- 가치: 장기 실행이 예정된 순간부터. 짧은 실습에서도 비용이 0에 가깝다.
- 비용: 설정 몇 줄. 기존 구조에 영향 없음.
- 확인: 없음.

**서비스별 리소스 상한**
- CPU·메모리 상한을 서비스마다 건다.
- 가치: 한 서비스의 폭주가 다른 서비스를 죽일 수 있는 구성부터.
- 비용: 설정 몇 줄. 다만 **상한이 실제로 반영되는지는 런타임 버전에 달렸다.**
- 확인: **구성을 해석한 결과를 먼저 출력해 본다.** 오케스트레이터 전용 키로 취급돼 조용히 무시되는 버전이 있고,
  그 경우 「상한을 걸었다」는 문서상 사실만 남는다. 무시된다면 런타임이 지원하는 다른 키로 바꾸거나 채택을 보류한다.

## B. 규모가 커질 때 꺼내는 것 — 기본 보류

**목록 API 페이지네이션**
- 가치: 레코드가 실제로 쌓여 응답이 커지기 시작할 때. 그 전에는 이득이 관측되지 않는다.
- 비용: **응답 형태가 바뀌므로 API 계약 변경이다.** 명세 개정 절차를 거쳐야 하고 클라이언트가 함께 바뀐다.
- 확인: 명세에 이미 나간 표면인지. 나갔다면 계약 변경 비용을 판정에 포함한다.

**멱등 스키마 마이그레이션**
- 스키마 변경을 「있으면 넘어가고 없으면 추가」 형태로 쓰고, 초기화 경로와 기동 경로 양쪽에 같은 규칙을 둔다.
- 가치: 데이터 볼륨이 유지된 채 컨테이너만 재생성되는 환경에서 무중단 변경이 필요해질 때.
- 비용: 같은 규칙이 두 자리에 생기므로 둘이 갈라지지 않게 유지하는 부담이 붙는다.
- 확인: 데이터가 컨테이너 수명과 분리돼 있는가. 매번 초기화되는 구성이면 가치가 없다.

## 여기 넣지 않는 것

- **기능 단위 파일 분리** — 후보가 아니라 이미 불변 규칙이다(`CLAUDE.md` SRP). 규모와 무관하게 적용한다.
- **원칙에 해당하는 항목** — 「규모가 커지면 보안을 켠다」는 판정은 성립하지 않는다. `backend-hardening.md`로 보낸다.
