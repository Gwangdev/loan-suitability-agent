# 디버깅 프로토콜 (필요할 때만 로드한다)

> **버그를 만났을 때만 로드한다.** `/build` 정상 흐름에서는 읽지 않는다.
> 진입: `/build` 중 테스트 실패·예상과 다른 동작, 또는 `/debug` 직접 호출.

## 이 절차의 역할

**진단은 구성과 다른 작업이다.** `/design`·`/build`·`/verify`는 만드는 절차이고, 여기는
**이미 만든 것이 왜 그렇게 동작하는지 알아내는** 절차다. 만드는 절차의 규칙을 그대로
쓰면 추측으로 코드를 읽게 되고, 그것이 디버깅에서 시간과 토큰이 가장 많이 새는 자리다.

**고치는 것이 목표가 아니다. 원인을 아는 것이 목표다.** 원인을 모르고 증상이 사라지면
그것은 해결이 아니라 이동이다.

---

## 1. 재현을 먼저 고정한다

**재현하지 못하는 것은 고칠 수 없다.** 고쳤다고 판단할 근거가 없기 때문이다.

- 증상을 관측한 **입력·환경·순서**를 그대로 적는다
- 그것으로 매번 재현되는지 확인한다. 간헐적이면 그 사실 자체를 적는다 — 간헐성은 원인의 단서다
- 재현되지 않으면 **여기서 멈추고 사용자에게 관측 조건을 묻는다.** 추측으로 고치지 않는다

재현 절차는 나중에 그대로 회귀 테스트가 된다. 버리지 않는다.

## 2. 증상과 원인을 분리해서 쓴다

관측한 것과 해석한 것을 같은 문장에 넣지 않는다.

```
증상   POST /api/orders 가 재고 부족일 때 500을 낸다
관측   로그에 NullPointerException, StockService.java:47
해석   [미검증] 재고 조회가 빈 결과일 때 null을 반환하는 것으로 보인다
```

**해석에는 `[미검증]` 라벨을 붙인다.** 불변 카드의 증거 규칙과 같은 구조다. 확인되기 전의
원인 추정은 사실이 아니다. 라벨을 붙여 두면 그것을 근거로 다음 판단을 쌓는 실수를 막는다.

## 3. 가설마다 그것을 틀리게 만들 관측을 정한다

가설을 세우는 것은 쉽고, 가설을 **버리는 기준**을 정하는 것이 어렵다. 기준 없이 세운
가설은 확증만 모으다가 끝난다.

| 가설 | 맞으면 보일 것 | 틀리면 보일 것 |
|---|---|---|
| 재고 조회가 null을 반환한다 | 조회 직후 로그에 null | 빈 리스트 또는 정상 값 |

**관측 한 번에 가설 하나.** 두 개를 함께 확인하면 어느 쪽이 배제됐는지 남지 않는다.

## 4. 추측으로 읽지 말고 범위를 절반씩 줄인다

코드를 처음부터 읽으며 원인을 찾는 것은 가장 비싼 방법이다. 파일이 늘어나는 만큼 토큰이
늘고, 읽은 것이 전부 컨텍스트에 남는다.

싼 것부터 쓴다.

1. **오류 메시지·스택트레이스의 최상단 프레임** — 대부분 여기서 끝난다
2. **입력 절반 줄이기** — 어느 절반에서 사라지는지
3. **범위 절반 줄이기** — 실패 지점과 정상 지점 사이를 관측 지점 하나로 나눈다
4. **이력 이분 탐색** — 이전에는 되던 것이면 `git bisect`. 코드를 읽지 않고 커밋을 찾는다

## 5. 한 번에 하나만 바꾼다

두 곳을 동시에 고치고 통과하면 **무엇이 고친 것인지 모른다.** 원인을 모르는 상태로
증상만 사라진 것이고, 다음에 같은 버그가 나도 이번에 얻은 정보가 없다.

되돌리기 쉽게 유지한다. 시도한 변경이 원인이 아니었으면 **되돌리고 나서** 다음을 시도한다.
되돌리지 않은 시도가 쌓이면 마지막에 무엇이 남았는지 아무도 모른다.

## 6. 3회 실패하면 멈추고 컨텍스트를 정리한다 — 하네스 고유 규칙

**디버깅은 실패한 시도를 컨텍스트에 쌓는다.** 실패 이력이 남아 있으면 이후 판단이 그것에
끌려간다. 이미 배제된 방향을 다시 시도하거나, 반대로 배제되지 않은 방향을 배제된 것으로
착각한다. 컨텍스트 감쇠 프로토콜이 다루는 문제가 디버깅에서 가장 빠르게 나타난다.

세 번째 시도가 실패하면:

1. `PROJECT_LOG.md`에 **시도한 것 · 배제된 원인 · 남은 가설**을 적는다
2. `/compact`를 돌린다
3. 정리된 상태에서 다시 시작한다. 배제된 원인은 파일에 있으므로 다시 시도하지 않는다

**이 규칙은 기한 압박 시 생략 대상이 아니다.** 생략하면 오염된 컨텍스트로 시도를 반복하고,
비용이 시도 횟수에 비례해 늘어난다.

## 7. 고칠 때 — 회귀 테스트를 먼저 쓴다

`/build`와 같은 순서다. **버그를 재현하는 테스트가 실패하는 것을 보고 나서 고친다.**

고친 뒤에 쓴 테스트는 고친 코드를 베낀다. 그 버그가 다시 들어와도 잡지 못할 수 있고,
그러면 회귀 테스트라는 이름만 남는다. 1단계에서 고정한 재현 절차가 그대로 그 테스트다.

## 8. 증상만 없애지 않는다

원인을 모르는 상태에서 다음을 하면 버그를 숨기는 것이다.

- 재시도·타임아웃 늘리기
- 예외를 잡아서 삼키기
- 조건을 추가해 그 입력만 우회
- 실패하는 테스트를 고치거나 지우기

**그렇게 할 수밖에 없는 경우가 있다.** 외부 시스템이 원인이거나 일정상 우회가 필요할 때다.
그때는 **그것이 우회임을 코드 주석에 남긴다.** 원인 → 과정 → 결론으로 쓴다 — 태그·번호는
쓰지 않는다(게이트 `L2`가 BLOCK한다).

```java
// 결제 게이트웨이가 간헐적으로 202 후 본문 없이 끊는다. 재현 조건을 특정하지 못해
// 원인은 미확인이고, 응답 본문이 빌 때만 1회 재조회하도록 우회했다.
// 게이트웨이 쪽 로그를 받으면 원인부터 다시 볼 자리다.
```

## 9. 멈추고 사용자에게 가는 조건

- **재현되지 않는다** — 관측 조건을 모르면 고칠 수 없다
- **3회 실패 후에도 남은 가설이 없다**
- **원인이 규제·데이터 등급·금지 자동화 행위 영역에 있다** — 프로덕션 데이터 조회, 외부
  전송, 롤백, 권한 변경은 디버깅 중이라는 이유로 승인 없이 실행하지 않는다
- **고치려면 설계를 바꿔야 한다** — `/build`가 아니라 `/design`으로 되돌아간다

## 종료 조건

1. 원인을 한 문장으로 쓸 수 있다 (`[미검증]` 라벨이 남아 있지 않다)
2. 그 원인을 재현하는 테스트가 있고, 고치기 전에 실패했음을 확인했다
3. 고친 자리에 원인 → 과정 → 결론 주석이 있다
4. `python3 tools/gate.py .`가 BLOCK 0건이다
5. `PROJECT_LOG.md`에 배제된 원인이 남아 있다 — 다음에 같은 증상이 나올 때 쓸 정보다

**이 절차는 기계로 검사되지 않는다.** 순서와 판단이라 최종 상태에 남지 않는다. 게이트가
보는 것은 결과물 쪽뿐이다 — 회귀 테스트의 존재(`T1`·`T2`), 고친 자리의 '왜'형 주석 비율(축 `C`),
잔존 `[미검증]` 라벨(`L1`). 나머지는 이 파일을 읽고 지키는 것으로만 지켜진다.
