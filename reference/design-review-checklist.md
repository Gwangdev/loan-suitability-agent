# 설계 검토 체크리스트

> `code-tell-checklist.md`가 「사람이 쓴 것처럼 보이는가」를 본다면, 이 파일은 「설계가 옳고 일관된가」를 본다.
> `/verify`의 `independent-verifier`가 검증하고, 셀 수 있는 항목은 `tools/gate.py` 축 7(S1·S2)이 맡는다.
> 근거: Google eng-practices의 Design·Consistency·Context, OWASP API Security Top 10,
> Microsoft Azure API 설계 지침(RESTful web API design / api-implementation).
>
> **출처 표기:** 아래 항목 중 `[관례]`가 붙은 것은 공식 지침이 규정하지 않은 실무 관례다.
> 공식 지침에서 온 항목과 같은 권위로 다루지 않는다. 프로젝트 사정에 따라 다르게 정할 수 있고,
> 다르게 정했다면 사유를 적는다.

## 0. 프레임을 먼저 바꾼다

**요청 범위를 기준으로 삼은 검토는 요청 범위 밖의 결함을 구조적으로 볼 수 없다.**
1차(요청한 것이 동작하는가) 통과가 2차(시스템이 일관된가) 통과를 뜻하지 않는다. 이 목록은 2차 전용이다.

## 1. 형제 대칭성 — 가장 자주 놓친다

같은 구조를 가진 도메인의 공개 표면을 **나란히 놓고** 비교한다.

- 자원 A가 하위 자원 접근을 제공하면 같은 축의 자원 B도 제공하는가
- 한쪽에만 있는 연산은 의도된 것인가 누락인가
- **사유를 남기지 않은 비대칭은 결함으로 판정한다**

> 판정 기준: 형제 자원 A가 `/{id}`와 `/{id}/{하위자원}`을 모두 제공하는데 B는 앞의 것만 제공하고,
> B의 하위 자원 조회가 하위 계층(Repository 등)에 이미 구현돼 있다면 **누락**이다.
> 하위 계층에도 없다면 미구현이므로 요구사항 범위를 확인한다.

## 2. 죽은 표면

- 선언됐으나 호출되지 않는 공개 메서드·엔드포인트·설정이 있는가
- 있으면 **「살릴지 지울지」 판정을 부여한다.** 기능 아이디어로 넘기지 않는다
- `code-tell-checklist.md` §3의 「미사용 흔적 0건이면 신호」와 다르다. 그쪽은 TODO·주석 처리된 옛 구현 같은 **시간의 흔적**이고, 이쪽은 **미완성 공개 표면**이다

## 3. 오류 응답의 정합성

- 같은 성격의 실패가 같은 상태 코드로 나가는가
- 자원 부재(404)·상태 충돌(409)·입력 오류(400)·권한(401·403)이 뭉개지지 않았는가
- 「부재」의 의미가 맥락마다 다른 곳은 분리했는가 (조회에서는 오류, 판정에서는 수량 0)
- 협상·조건 실패가 500으로 뭉개지지 않았는가 — 미지원 Content-Type은 415, `Accept` 불일치는 406,
  조건부 요청 불일치는 412, 본문 용량 초과는 413, 호출 한도 초과는 429 또는 503 + `Retry-After`
- **빈 컬렉션을 부재로 처리하지 않았는가.** 조회 결과가 없는 것은 정상 값이다 — `200` + 빈 배열로 낸다.
  `204`는 본문이 없는 응답(삭제 성공 등) 전용이다. 빈 배열을 204로 내면 클라이언트가 파서 경로를 분기해야 한다 `[관례]`
- 오류 본문 형식이 전 구간 하나인가 (`application/problem+json`, RFC 9457 권장) `[관례]`
- 오류 본문에 스택 트레이스·내부 경로·쿼리가 실려 나가지 않는가. 상세는 서버 로그에만 남긴다
- 예외가 처리되지 않은 채 프레임워크까지 올라가 500이 되는 경로가 있는가.
  제약 조건 위반은 500이 아니라 409다

## 4. 검사와 실행 사이

선행 검사 후 실행하는 구조(`existsBy…()` → `delete()`)는 그 사이에 상태가 바뀔 수 있다. 단일 프로세스 환경이면 넘길 수 있으나 **넘긴다는 판정을 명시**한다.

같은 문제가 **클라이언트와 서버 사이**에도 있다. 조회한 값을 고쳐서 되돌려 보내는 갱신은,
그 사이에 다른 사용자가 바꾼 내용을 조용히 덮어쓴다(lost update).

- 갱신·삭제가 **자기가 본 버전을 근거로** 수행되는가 (`ETag` + `If-Match`, 또는 버전 컬럼 대조)
- 버전이 어긋나면 덮어쓰지 않고 412로 되돌리는가
- 조건 없이 갱신하는 설계라면, **덮어쓰기를 감수한다는 판정이 명시돼 있는가**
- 버전 값을 런타임마다 달라지는 해시로 만들지 않았는가 — 콘텐츠 해시나 DB 버전·갱신시각 컬럼을 쓴다 `[관례]`

## 5. 권한 표면

- 식별자를 바꿔 넣으면 타인의 자원에 접근되는가 (OWASP API1)
- 상태를 바꾸는 연산에 권한 검사가 있는가 (API5)
- 목록 조회에 상한이 있는가 (API4). **상한을 서버가 강제하는가** — 클라이언트가 보낸 `limit`을
  그대로 따르면 상한이 없는 것과 같다. 기본값도 함께 정한다
- 필드 선택(`?fields=`)을 받는다면 **허용 목록으로 검증하는가.** 검증이 없으면
  공개 대상이 아닌 필드가 이름만으로 조회된다
- 정렬·필터 파라미터가 컬럼명으로 그대로 흘러 들어가지 않는가

## 6. 관례 대비 검토 — 유일한 외부 축

1~5는 전부 **「우리가 정한 규격을 지켰는가」**를 본다. 이 항목만 **「우리가 정한 규격이 타당한가」**를 본다.
내부 일관성 검사는 잘못된 규격을 일관되게 구현한 결과를 통과시킨다. 이 축이 없으면 그 결함을 볼 수단이 없다.

- **표준 모듈을 직접 구현하지 않았는가.** 인증·인가·암호화·세션·검증·직렬화·스케줄링은 프레임워크가 제공한다. 직접 구현했다면 사유가 문서에 있는가
- **SQL·쉘 명령·쿼리 문자열을 f-string·`%`·`+` 문자열 결합으로 직접 조립하지 않았는가.** 드라이버가 파라미터 바인딩(`?`, `$1`, named placeholder)을 제공하면 그것을 쓴다. 지금 들어가는 값이 사용자 입력이 아니라 내부에서 계산된 값이라도, 문자열 결합으로 값을 쿼리에 넣는 방식 자체가 "표준 모듈이 제공하는 안전한 조립 방법을 직접 재구현"한 것이므로 이 항목 위반으로 판정한다. 컬럼명·테이블명 같은 식별자는 바인딩 대상이 아니므로 별개로 본다
- **재시도·서킷 브레이커를 직접 구현하지 않았는가.** 대부분의 클라이언트·SDK가 내장한다.
  직접 만들었다면 사유가 있는가. 그리고 만들었다면 — 호출 체인의 여러 계층이 각자 재시도하고 있지 않은가,
  대기 시간에 상한이 있는가, 재시도 대상 연산이 반복 실행돼도 결과가 같은가 `[관례]`
- **이 프레임워크의 일반적인 구조와 다른가.** 다르다면 이 프로젝트 고유의 사정이 있는가, 아니면 그냥 몰라서 다른가
- **위임만 하는 클래스·인터페이스가 있는가.** 명세에 이름이 박혔다는 이유로 남은 껍데기는 결함이다. 「이 추상화가 없어도 되는가」를 묻는다
- **설계 결정을 뒤집은 이력이 있으면, 그 결정에 딸린 부속 규격도 함께 무효화했는가.** 뒤집기는 이름·클래스·인터페이스를 남긴다

**판정 방법:** 이 축은 자기검토로 성립하지 않는다. 같은 컨텍스트가 정한 규격을 같은 컨텍스트가 타당하다고 판정하기 때문이다.
`independent-verifier`(격리 컨텍스트) 또는 **파이프라인 밖의 외부 도구**로 확인한다.

## 마지막 — 발견의 처리

결함은 **선택지 목록에 섞지 않는다.** 「고쳤다 / 안 고쳤고 사유는 이것 / 미결로 남긴다」 중 하나로 처리 상태를 남긴다.
고르지 않은 제안은 사라져도 되지만, **고르지 않은 결함은 여전히 결함이다.**
