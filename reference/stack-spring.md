# 스택별 실행 절차 — Spring Boot + Swagger

> `report-exec-harness.md`의 조사·실행·캡처 단계를 이 스택에서 구체화한 파일이다.
> **해당 스택일 때만 로드한다.** 다른 스택이면 이 파일을 읽지 말고 같은 순서를
> 그 스택의 빌드·실행·API 문서 도구로 바꿔 적용한다.

## 1. 조사

1. `source_spec`을 처음부터 끝까지 읽는다.
2. 빌드 도구, 런타임 버전, 실행 명령, 포트, Swagger 경로를 확인한다.
3. Controller, Service, Repository, Entity, DTO, 예외 처리, 설정, 테스트를 조사한다.
4. 요구사항 항목별로 내부 작업표를 만든다 — 원문 · 구현 위치 · 확인 엔드포인트 ·
   정상 기대 결과 · 오류 경계 · 필요한 캡처.
5. 기존 이미지와 보고서는 최신 실행 결과와 모순되지 않을 때만 재사용한다.

조사 중 발견한 사용자 변경사항을 덮어쓰지 않는다. 현재 작업과 무관한 파일은 수정하지 않는다.

## 2. 실행

1. 빌드 또는 테스트 명령을 먼저 실행한다.
2. 실패하면 원인을 진단한다. 구현 수정을 요청받지 않았다면 보고서 작성에 필요한 범위를
   넘어 코드를 고치지 않는다.
3. 애플리케이션을 실행하고 기동 로그와 실제 포트를 확인한다.
4. Swagger UI 또는 API 문서 엔드포인트에 접속한다.
5. 초기 데이터와 실행 순서를 파악해 시나리오 간 데이터 충돌을 막는다.
6. 정상·오류 시나리오를 요구사항 순서대로 실행한다.
7. 종료 시 애플리케이션 프로세스를 정리한다.

## 3. 캡처

각 캡처는 보고서 주장에 필요한 만큼 다음을 포함한다 — HTTP 메서드와 경로, 입력 파라미터
또는 요청 본문, 실행 사실을 식별할 맥락, 응답 상태 코드, 핵심 응답 본문.

- 전체 브라우저 창보다 Swagger의 관련 작업 영역을 우선한다.
- 빈 공간은 줄이되 메서드·경로·상태 코드·응답의 관계를 끊지 않는다.
- 원본은 `images/source/`에 보존하고, 크롭은 파생 이미지로 만든다. 원본을 덮어쓰지 않는다.
- 파일명은 실행 순서가 드러나는 2자리 번호와 짧은 설명을 쓴다.

```text
01-swagger-overview.png
02-create-resource-201.png
03-validation-error-400.png
```

- 토큰·비밀번호·개인 식별 정보가 화면에 있으면 캡처 전에 제거하거나 마스킹한다.
- 외부 서비스 호출이나 데이터 변경이 위험하면 승인 없이 실행하지 않는다.

## 4. 표기

- 메서드명, 클래스명, 엔드포인트, 상태 코드는 원문과 대소문자를 유지한다.
- 요구사항 명칭의 괄호를 임의로 제거하지 않는다.
- 캡처 화면의 값을 본문에 옮길 때 반올림하거나 다듬지 않는다.

설계 판단은 `무엇을 구현했는가 → 어떤 조건을 사용했는가 → 왜 그 조건이 필요한가 →
실행 결과에서 무엇을 확인했는가` 순서로 쓴다.

나쁜 예: `사용자 기능을 완벽하게 개선하였다.`

좋은 예: `사용자명이 실제로 변경되는 경우에만 중복 검사를 수행하여, 기존 값을 유지하는
수정 요청이 자기 자신과 충돌하는 것으로 오판되지 않게 하였다.`
