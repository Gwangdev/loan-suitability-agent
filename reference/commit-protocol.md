# 커밋 프로토콜 (체크포인트 전용)

> **체크포인트에서만 로드한다.** `/build` 반복 구간에서는 읽지 않는다.
> 전체 개발이 끝났거나 일정상 끊기로 한 파트가 끝난 시점의 절차다.

## 커밋은 AI가 하지 않는다

**`git commit`·`git push`를 실행하지 않는다.** 커밋은 사용자가 직접 수행한다.

이력 관리 주체가 사람이기 때문이다. AI가 자동으로 커밋하면 단기간에 수십 개가 쌓여 팀 리더가 히스토리로 진행 상황을 읽을 수 없게 된다. 팀 개발에서 커밋은 **작업 로그가 아니라 리뷰 단위**다.

**개발 리듬과 커밋 단위는 다른 문제다.** 파트로 묶어 개발하더라도 커밋은 기능 단위로 쪼갠다. "이 파트 전부"라는 커밋 하나로 뭉치면 리뷰 단위가 다시 사라진다.
중간 저장·시행착오는 커밋하지 않는다. 그것들은 작업 트리에서 끝낸다.

---

## 1단계. 품질 판정

```bash
python3 tools/gate.py . --commit
```

| 판정 | 뜻 |
|---|---|
| `COMMIT READY` | 차단 항목 0건. 2단계로 간다 |
| `NOT READY` | **어떤 커밋 블록도 만들지 않는다.** 해소 후 다시 돌린다 |

**커밋 시점 기준은 단계 완료 기준과 다르다.** 개발 중에는 아직 손대지 않은 명세 항목이 남아 있는 것이 정상이므로 그것만 예외로 둔다.

- `S3`(미구현 명세 항목) → **정보(`▶`)로 표시하고 차단하지 않는다**
- `S4`·`L1`·`L2`·`T1`·`V1`을 포함한 그 밖의 모든 BLOCK → **그대로 차단한다**

`V1`은 이 모드에서만 도는 항목으로, `SPEC.yaml`의 `test_command`를 **실제로 실행한다.** 테스트 파일이 있다는 것(`T1`)과 통과한다는 것은 다른 사실이다.

```yaml
# SPEC.yaml
test_command: "./gradlew test"     # 또는 "python3 -m pytest -q"
```

`test_command`가 없으면 `V1` WARN이 뜬다 — 기계로 검증하지 못했다는 뜻이므로 그 상태로 커밋할지는 사람이 판단한다.

**전체 테스트 스위트를 돌리므로 느리다.** 체크포인트에서만 낸다.

`X1`(박힌 자격증명)은 항상 돌지만 `X2`(semgrep)·`X3`(의존성)은 이 모드에서만 돈다.
도구가 없으면 WARN이고, **WARN은 통과가 아니라 미검사다.** 그 상태로 커밋하면 보안 축이
비어 있는 채로 나간다. `X1`이 BLOCK이면 코드에서 지우는 것으로 끝내지 않는다 — 이미
커밋된 키는 git 이력에 남으므로 **폐기·재발급**해야 한다.

## 1.5단계. 리뷰 커맨드 — 커밋 범위당 1회

기계 게이트가 통과한 뒤에 돈다. 게이트는 셀 수 있는 것만 세고, 아래는 그 밖을 본다.

| 커맨드 | 언제 | 횟수 |
|---|---|---|
| `/code-review` | 이 체크포인트에서 항상 | 커밋 범위당 1회 |
| `/security-review` | **외부 표면(엔드포인트·권한·입력 경로)이 추가·변경된 경우에만** | 해당 범위당 1회 |

`/build` 반복 구간에서는 돌리지 않는다. 지적을 고친 뒤 다시 볼 필요가 있으면 **고친 범위만**
대상으로 한다. 바뀌지 않은 코드를 다시 읽는 데서는 새 정보가 나오지 않는다.

자리와 근거는 `.claude/commands/verify.md` §내장 리뷰 커맨드와의 분담에 있다.

## 2단계. 커밋 분할 원자료

**`COMMIT READY`면 위 명령이 이어서 자동으로 출력한다.** 따로 칠 필요 없다.
(따로 보고 싶으면 `python3 tools/gate.py . --changeset`)

미커밋 변경을 **명세 항목 기준으로** 묶어 보여준다. 묶음의 근거는 추측이 아니라 코드에서 실제로 추출한 엔드포인트다.

```
│ ● GET /api/orders
│     ?? src/order/OrderListController.java
│ ○ 공통·기반 / 미분류 — 어느 기능에 속하는지 사람이 판단한다
│     ?? src/config/DataSourceConfig.java
```

`○` 묶음은 엔드포인트를 선언하지 않는 파일이다. 설정·공통 모듈·테스트가 여기 들어간다. **어느 커밋에 실을지는 판단이 필요하므로 기계가 정하지 않는다.**

## 3단계. 커밋 시나리오 제시

순서가 있는 커밋 목록을 만들어 제시하고 **멈춘다.**

**순서 규칙**

- **공통·기반이 먼저다.** 기능 커밋이 그것에 의존하므로, 뒤집으면 중간 커밋이 깨진 상태가 된다
- **테스트는 대응하는 기능 커밋에 함께 싣는다.** 별도 커밋으로 빼면 그 사이 커밋이 테스트 없는 상태로 남는다
- `○` 묶음 중 어디에 속하는지 불분명한 파일은 **추측하지 말고 사용자에게 묻는다**

**제시 형식**

````
**1/4 — 공통 기반**
```bash
git add src/config/DataSourceConfig.java
git commit -m "chore: 데이터소스 설정 추가"
```

**2/4 — 주문 목록 조회 (GET /api/orders)**
```bash
git add src/order/OrderListController.java tests/order/OrderListTest.java
git commit -m "feat: 주문 목록 조회 API 추가

정렬 기준을 서버가 고정해, 호출부가 순서를 신뢰할 수 있게 했다."
```
````

- 번호를 붙여 순서를 드러내고, **블록을 분리한다.** 하나로 합친 스크립트로 주지 않는다 — 사용자가 중간에서 멈추거나 순서를 바꿀 수 있어야 한다
- **`git add .`를 쓰지 않는다.** 해당 커밋과 무관한 변경이 섞인다
- 사용자가 메시지를 고치거나 커밋을 미룰 수 있다. **제시하고 멈춘다. 대신 실행하지 않는다**

## 커밋 메시지

```
<타입>: <무엇을 했는가 — 한 줄>

<왜 이렇게 했는가. 판단이 갈렸던 지점이 있으면 그것>
```

타입은 저장소의 기존 관례를 따른다. 관례가 없으면 `feat`·`fix`·`refactor`·`test`·`docs`를 쓴다.
**"제거·정리·삭제"를 표방하는 메시지는 실제 삭제가 있을 때만 쓴다.** 게이트 `G4`가 주장과 diff를 대조한다.
