# 보고서 콘텐츠 계약 (교체 불가)

> `/handoff report`가 만든 프롬프트와 보고서 실행 주체가 읽는다. 문체·색상은
> `reference/report-style.md`, 보고서별 구성은 선택된 `reference/report-profiles/` 파일이 맡는다.
> 이 파일은 모든 보고서에 공통인 판단·증거·작성 절차만 정한다.

## 1. 한 번만 설계한다

`/handoff report`는 `prompts/report-brief.json`에서 독자, 독자가 내릴 결정, 핵심 주장,
근거 위치, 구성, 시각화 메시지를 한 번 고정한다. 실행 주체는 브리프를 다시 기획하거나
같은 자료를 다시 요약하지 않고 바로 보고서를 작성한다.

- 브리프에 원문 문단을 복사하지 않는다. 주장과 근거 위치만 남긴다.
- 선택된 프로필 하나만 읽는다. 다른 프로필을 비교하거나 혼합하지 않는다.
- 프롬프트에 브리프·스타일·프로필 내용을 다시 복사하지 않는다. 경로만 지정한다.
- 브리프가 불완전하면 보고서를 추측해 쓰지 않고 누락 필드만 보완한다.
- 초안 뒤 별도 계획 단계로 돌아가지 않는다. 검출된 결함만 국소 수정한다.

## 2. 브리프 계약

경로는 `prompts/report-brief.json`이다. JSON은 표준 라이브러리로 검증할 수 있고 실행
환경에 별도 YAML 의존성을 요구하지 않는다.

```json
{
  "version": 1,
  "profile": "technical-project",
  "profile_reason": "코드·테스트·실행 결과가 주된 근거",
  "audience": "보고서를 읽고 판단할 구체적 독자",
  "decision": "독자가 보고서를 읽은 뒤 내릴 결정 한 가지",
  "length": {"pages": "6-10", "reason": "증거 화면과 검증표를 판독 가능한 크기로 배치"},
  "claims": [
    {
      "statement": "보고서가 입증할 문장",
      "evidence": ["파일:라인", "로그 또는 공식 출처 URL"],
      "status": "verified"
    }
  ],
  "counterevidence": ["주장을 약화하거나 적용 범위를 제한하는 근거"],
  "outline": ["결론과 핵심 결과", "분석", "권고 또는 인수인계", "한계"],
  "visuals": [
    {
      "message": "그림 하나가 전달할 결론 한 문장",
      "evidence": ["데이터·로그·파일 위치"],
      "form": "table"
    }
  ]
}
```

필수 필드는 `profile`, `profile_reason`, `audience`, `decision`, `claims`, `counterevidence`,
`outline`이다. 프로필은
`technical-project`, `business-strategy`, `policy-research`, `brief` 중 하나다.
`profile_reason`과 `counterevidence`도 반드시 기록한다. 반대 근거를 찾았으나 없으면
`counterevidence`를 빈 배열로 둔다. `claims[].status`는 `verified` 또는 `partially-verified`만
허용한다. 부분 검증이면 `verified_scope`와 `limitation`을 함께 쓴다. 전혀 검증하지 못한 주장은
브리프에 넣지 않고 확인 질문으로 돌린다. `visuals`는 필요할 때만 쓰되, 각 항목에 메시지와
근거가 모두 있어야 한다.

브리프가 12,000자를 넘으면 원문을 복사했을 가능성이 높다. 주장 수를 억지로 줄이지 말고
중복 설명을 지우고 근거는 위치로 축약한다.

## 3. 보고서의 논리 단위

보고서의 기본 단위는 `사실 → 해석 → 조치`다.

- **사실:** 관찰값, 실행 결과, 제도, 시장 데이터. 출처와 측정 조건을 붙인다.
- **해석:** 사실이 독자의 결정에 갖는 의미. 사실처럼 위장하지 않는다.
- **조치:** 누가 무엇을 언제 어떤 조건에서 할지 쓴다. 근거가 허용하는 강도로 제안한다.

세 요소를 모든 문단에 기계적으로 반복하지 않는다. 중요한 판단이 형성되는 지점에서만
연결하고, 단순 배경·방법·출처 설명에는 억지로 조치를 붙이지 않는다.

핵심 주장마다 브리프의 근거를 적어도 하나 사용한다. 정량 수치는 기준 시점, 모집단 또는
표본, 단위, 산출 방법 중 해석에 필요한 조건을 함께 쓴다. 비교는 같은 기간·단위·정의인지
확인한다. 조건이 다르면 차이를 표 주석이나 본문에 밝힌다.

## 4. Executive Summary

요약은 본문을 쓴 뒤 한 번 작성한다. 독자가 요약만 읽어도 결정을 내릴 수 있어야 한다.

1. 첫 문장에서 질문에 답한다.
2. 답을 지지하는 핵심 근거를 중요도 순으로 2~4개 제시한다.
3. 필요한 조치, 우선순위 또는 다음 결정을 명시한다.
4. 결론을 바꿀 수 있는 가장 중요한 한계나 조건을 한 문장으로 적는다.

배경으로 시작하지 않으며, 본문에 없는 수치나 권고를 요약에서 새로 만들지 않는다.
목차를 순서대로 축약하는 실패 패턴은 `reference/ai-tell-checklist.md` §1 참조.

## 5. 표와 차트

- 차트 제목은 주제가 아니라 결론을 쓴다. `시장 규모`보다 `2024년 이후 성장의 70%가 B2B에서 발생`이 낫다.
- 한 차트에는 메시지 하나만 둔다. 여러 질문을 답하면 분리한다.
- 축, 단위, 기간, 표본, 출처, 계산 또는 추정 여부를 표시한다.
- 비교 기준과 강조색은 결론을 왜곡하지 않게 사용한다.
- 원자료가 없거나 표본이 너무 작으면 차트를 만들지 않고 사실을 짧게 쓴다.
- 표는 정확한 값 비교, 차트는 패턴·격차·추세 설명에 사용한다.
  장식용 시각화의 실패 패턴은 `reference/ai-tell-checklist.md` §3 참조.

## 6. 작성과 검증 순서

```text
브리프 검증 → 본문 작성 → Executive Summary 작성 → 통합 감사 1회
→ 결함이 있을 때만 국소 수정 → PDF가 필요할 때만 렌더 검수
```

통합 감사는 다음을 한 번에 확인한다.

- 브리프의 핵심 주장·수치가 본문과 일치하는가
- 사실·해석·권고의 경계가 흐려지지 않았는가
- 반대 근거와 한계가 결론의 적용 범위에 반영되었는가
- `reference/ai-tell-checklist.md`의 구조·문장 흔적이 남았는가
- 표와 차트의 메시지, 단위, 출처가 완전한가

Claude 전용 에이전트 감사와 실행 주체의 자체 감사를 연달아 돌리지 않는다. 실행 주체가
어느 쪽이든 위 통합 감사 한 번만 수행한다. PDF 검수는 `reference/report-exec-harness.md`가
요구하는 경우에만 추가한다.

## 7. 중단 조건

- 독자나 독자가 내릴 결정이 특정되지 않았다.
- 핵심 결론을 뒷받침할 근거가 없다.
- 서로 충돌하는 수치의 정의·시점을 대조할 수 없다.
- 민감정보를 안전하게 마스킹할 수 없다.
- 외부 실행이나 데이터 변경에 필요한 승인이 없다.

중단할 때는 전체 질문 목록을 만들지 않는다. 결과를 가장 크게 바꾸는 누락 한 가지를 먼저 묻는다.
