# 개발 완료 기준

> `/verify`의 독립 검증자가 이 목록 전부를 실제로 확인한다. 하나라도 미충족이면 완료로 판정하지 않는다.
> 포트폴리오·보고서 관련 기준은 이 시점에 산출물이 존재하지 않으므로 `reference/portfolio-criteria.md`에서 별도로 검증한다.

- 필수 요구사항과 수용 기준 충족
- **`SPEC.yaml` 대조 통과** — 게이트 `S3`(누락)·`S4`(명세 대비 과잉 구현) 0건. 명세와 코드가 어긋난 채로는 완료가 아니다
  - **예외:** HTTP/API 표면이 없는 프로젝트(배치 스크립트·데이터 파이프라인 등)는 `/design`에서 `SPEC.yaml`을 아예 두지 않을 수 있다(`gate.py`의 `check_spec()`이 파일 부재 시 이 축을 건너뛴다). 이 경우 "공개 표면"은 `PROJECT_LOG.md`의 요구사항·수용 기준 표로 대체하고, 독립 검증자는 S3/S4 대신 그 표와 코드를 한 줄씩 대조해 판정한다. 이 예외를 쓴 프로젝트는 `PROJECT_LOG.md`에 사유를 반드시 기록해야 하며, 기록이 없으면 예외가 아니라 미충족이다
- **내부 자산 유출 없음** — `L1`(미해결 라벨)·`L2`(하네스 내부 태그) 0건. 제출물에 작업용 표기가 남으면 완료가 아니다
- **기능 테스트 실제 통과** — `SPEC.yaml`의 `test_command`가 실행되어 통과했다(`V1`). 테스트 파일 존재만으로는 충족하지 않는다
  - 위 예외를 쓴 프로젝트에서 `test_command`를 둘 수 없다면(예: 단일 파일 제출 규칙으로 별도 테스트 파일 추가가 금지된 경우), 대신 **산출물 코드 안에 실행 시점 검증(assertion)을 두어 매 실행마다 자동으로 통과·실패가 확인되게 하고, 그 실행 로그를 증거로 삼는다.** 육안 비교나 1회성 출력만으로는 `V1`을 충족한 것으로 보지 않는다
- 적용 규제 준수 확인
- **모든 사실 주장에 출처 확보, `[미검증]`·`[확인 필요]` 잔존 없음**
- 치명적 위험의 예방·탐지·복구 수단 확인
- 필수 테스트 실제 실행 및 증거(로그·출력) 확보
- **독립 검증(서브에이전트) 통과**
- **`reference/design-review-checklist.md` 통과** — 요구사항 충족과 별개로 판정한다. 사유 없는 형제 비대칭·판정 없는 죽은 표면이 남아 있으면 미충족
- **§6 관례 대비 검토 통과** — 표준 모듈을 사유 없이 직접 구현했거나, 위임만 하는 껍데기 클래스가 남아 있으면 미충족
- 치명적 실패 없음
- 미해결 위험·제한사항 명시
- 실행·재현·복구 절차 작성
- 구현·테스트·문서 상태 일치

미충족 시 표시: `개발 중 / 검증 필요 / 조건부 완료 / 배포 보류 / 사용자 결정 필요`.
