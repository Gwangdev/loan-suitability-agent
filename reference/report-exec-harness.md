# 실행형 기술 보고서 생성 하네스

버전: 3.0 (하네스 v9)
용도: 프로젝트를 직접 실행하고 증빙 화면을 수집해 Markdown·HTML·PDF·ZIP을 생성하는 작업

> **`/handoff report`가 실행형(실행 증빙·캡처·PDF·ZIP 요구)일 때만 프롬프트에 이 파일의 경로를 포함한다.**
>
> **문체와 구성은 이 파일이 정하지 않는다.** `reference/report-style.md`,
> `reference/report-contract.md`, 선택된 `reference/report-profiles/` 파일이 맡는다.
> 조판 값은 `reference/report.css`가 갖는다. 이 파일은 실행·증거·산출물·검증만 다룬다.

---

## 0. 실행 입력

아래 값을 우선 사용한다. 비어 있으면 프로젝트 파일과 요구사항 명세에서 확인 가능한 범위만
추론한다. 결과를 크게 바꾸는 정보만 질문하고, 파일에서 확인되는 내용은 묻지 않는다.

```yaml
project_root: 현재 작업 폴더
source_spec: <프로젝트별 요구사항 파일. 없으면 비워 둔다>
report_title: 요구사항 명세에서 확인
author: 요구사항 명세에서 확인
output_basename: 제목과 작성자에서 안전한 파일명으로 생성
report_profile: technical-project
theme: black | orange | blue | vermilion   # 지정이 없으면 묻는다. 임의로 고르지 않는다
layout: classic | modern | formal
mode: full
create_zip: true
```

`mode`는 다음 중 하나이다.

- `full`: 실행, 검증, 캡처, Markdown 작성, 승인, HTML·PDF 생성, 렌더 검수, ZIP까지 전부.
- `content-only`: 준비된 화면으로 Markdown과 산출물을 만든다.
- `render-only`: **승인된 Markdown 하나만 읽어** HTML과 PDF를 다시 만든다.
  본문을 다시 쓰지 않는다. 문체를 다시 정규화하지 않는다. 그 작업이 사용자의 손을 지운다.

`content-only`와 `render-only`에서는 승인 루프를 다시 돌리지 않는다.

`layout: formal`은 관공서 용역보고서 판면을 실측 이식한 축이다. 기본 판단 규칙과 넷이
충돌하므로 문체 파일로 `reference/examples/report-style-formal.md`를 함께 로드한다. 그 파일
없이 이 축만 켜지 않는다.

스택별 조사·실행·캡처 절차는 해당 파일을 로드한다. Spring Boot + Swagger는
`reference/stack-spring.md`, DB 클라이언트(DBeaver 등) 화면 캡처가 증빙이면
`reference/stack-db-tool.md`. 둘 다 아니면 같은 순서를 그 도구에 맞춰 적용한다.

## 1. 산출물 계약

```text
report/
├── 보고서.md          ← 단일 사실 원본. 사용자의 편집 지점
└── images/
output/
├── 보고서.html        ← 조판 미리보기. 항상 제공한다
├── 보고서.pdf         ← 최종 제출물
└── preview/
```

1. **Markdown이 단일 사실 원본이자 편집 지점이다.** HTML과 PDF는 여기서 파생된다.
   Markdown과 PDF를 서로 독립된 문서로 따로 쓰지 않는다. 제목·문단·표·이미지·캡션·수치가
   일치해야 한다. PDF에서 이미지를 크롭하거나 위치를 바꿔도 내용과 그림 번호는 같다.
2. **HTML은 항상 제공한다.** 요청이 없어도 제공한다. 중간 산출물이라는 이유로 숨기지 않는다.
   조판을 눈으로 확인하는 가장 싼 수단이다.
3. **docx는 요청이 있을 때만** 만든다. Markdown에서 변환하며 따로 작성하지 않는다.
4. 최종 보고에 **Markdown 경로를 PDF보다 먼저** 제시한다.

## 2. 승인 루프

```text
브리프 검증 → Markdown 작성 → gate.py → HTML 렌더
→ ■ 사용자 검토·승인 ■ → PDF 렌더 → 렌더 검수 → ZIP
```

**승인 없이 PDF 단계로 넘어가지 않는다.** 승인 요청은 한국어로, Markdown과 HTML 경로를 함께
제시하고 `이 내용으로 PDF를 만들까요` 한 문장으로 묻는다. 질문 목록을 만들지 않는다.

사용자가 Markdown을 직접 고쳐 오면 `mode: render-only`로 그 파일만 읽어 다시 만든다.

## 3. 사실성과 증거

사실이 충돌하면 다음 순서로 판단한다.

1. 사용자의 최신 직접 지시
2. 요구사항 명세 또는 `source_spec` — 무엇이어야 하는가
3. 직접 실행한 결과 — 실제로 무엇이 일어났는가
4. 현재 코드와 설정 — 실행 결과가 나온 이유
5. 기존 README 및 보고서 — 보조 설명

코드와 실행 결과가 명세와 다르면 차이를 숨기지 말고 실제 상태를 기술한다. 제공되지 않은
수치·기능·성능·성공 여부를 만들거나 추정하지 않는다.

- 상태 코드와 응답 본문은 실제 실행값을 쓴다. 실행마다 달라지면 캡처 시점 조건을 함께 기록한다.
- 정상 응답만 보여주지 말고 요구사항이 정한 오류 경계도 검증한다.
- 실행하지 않은 기능을 실행한 것처럼 쓰지 않는다. 실패한 테스트를 빼고 성공만 보고하지 않는다.
- 깨진 이미지 링크, 임시 경로, 로컬 서버 주소를 최종 보고서의 근거 링크로 남기지 않는다.
- 디자인을 이유로 기술적 사실이나 요구사항 항목을 삭제하지 않는다.

브리프(`prompts/report-brief.json`)의 주장·순서·우선순위를 그대로 쓴다. 캡처 수에 맞춰 새 절을
만들지 않는다. 브리프에 없는 결론이 필요하면 본문에서 즉흥적으로 쓰지 말고 브리프부터 고친다.
실행으로 값이 달라졌으면 브리프를 한 번 수정하고 R축을 다시 통과시킨다.

## 4. Markdown

Markdown은 콘텐츠 원본이다. 디자인은 `report.css`가 담당하므로 Markdown에 억지로 표현하지 않는다.

허용: 제목, 문단, 목록, 표, 코드 블록, 인용, 수평선, 표준 이미지·링크 문법.
금지: HTML 레이아웃 태그, 인라인 CSS, 중첩 표, 4단계 이상 제목, 쪽 배치용 빈 줄 반복,
로컬 절대 경로 이미지 링크.

이미지는 `![그림 N. 설명](images/파일명.png)` 형식을 쓴다.

## 5. 렌더

### 5.1 렌더 전 — 이미지 배치를 먼저 계산한다

이미지가 있는 절은 **렌더하기 전에** `python3 tools/image_plan.py <계획.json>`을 통과시킨다.
배치를 판정하는 데 필요한 건 픽셀이 아니라 가로세로 비율(파일 헤더)과 이미지의 종류(작성자가
안다) 둘뿐이다. 이 둘로 렌더 폭·판독성·쪽 넘침이 전부 계산되므로 PNG를 눈으로 열어 보는
루프가 없어진다. 종료코드가 1이면 슬롯을 다시 짜고, 그 뒤에 HTML로 옮긴다.

여기서 확인된 배치 제약 하나: **조밀한 텍스트 캡처(터미널·EXPLAIN 덤프)는 전폭 한 단에만
쓸 수 있다.** 2단 이상으로 나누면 축소율이 판독 한계를 넘는다. 2×2 격자나 아래쪽 2단처럼
다단이 필요한 자리에는 래스터 캡처 대신 벡터 차트를 쓴다 — 벡터는 픽셀 해상도가 없어
축소해도 판독성이 깎이지 않는다.

**캡션은 이 방식으로 뺄 수 없다.** "그림 6은 Materialized View 조회 결과다" 같은 문장은
실제로 그 화면을 본 뒤에만 쓸 수 있다. 계획기는 배치까지만 맡는다.

### 5.2 렌더

```bash
# 보고서.html은 report.css를 link하고 <body class="report t-{theme} l-{layout}">를 쓴다
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless \
  --no-pdf-header-footer --print-to-pdf=output/보고서.pdf output/보고서.html
```

- 렌더러는 **Chrome(HTML/CSS)로 고정한다.** ReportLab은 쓰지 않는다.
- 조판 값은 `report.css`가 전부 갖는다. **HTML이나 스크립트에 색·pt·mm을 다시 쓰지 않는다.**
  인라인 `style="…"`은 예외 없이 금지다 — 필요하면 `report.css`에 클래스를 만든다.
  "이번 한 줄만"을 허용하면 다음 사람이 또 예외를 만든다. 게이트 `E6`이 검사한다.
- 외부 SVG 차트는 호스트 문서의 CSS 변수를 **상속받지 않는다.** 차트를 굽는 스크립트가
  `report.css`의 `--accent`와 같은 값을 따로 갖고 있으므로, 강조색을 바꿀 때는 둘을 같은
  커밋에서 함께 바꾼다.
- 쪽은 `<section class="sheet">` 하나가 A4 한 장이다. 자동 흐름이 아니라 의미 단위로 직접
  나눈다. 설명·표·이미지·검증 결과는 한 덩어리이므로 쪼개지 않고, 제목만 쪽 하단에 남기거나
  캡션을 이미지와 다른 쪽으로 넘기지 않는다. 다중 이미지 절은 최대 두 쪽까지 쓴다.
- 이미지는 원본 비율을 유지하고 원본 이상으로 확대하지 않는다. 축소 후 상태 코드와 응답이
  판독되지 않으면 쪽을 나눈다.
- 카드를 파트 단위로 나눠 다음 쪽에 이어 배치할 때, 이미지 압축(축소) 여부는 카드의 원본
  전체 파트 수가 아니라 **그 쪽에 실제로 배치되는 파트 수**로 정한다. 원본 기준으로 정하면
  분할된 파트가 다른 카드와 한 쪽에 있을 때 넘치거나, 그 파트만 홀로 있는 쪽에서 불필요하게
  계속 작게 나온다.
- 글꼴을 찾지 못하면 조용히 대체하지 않고 **중단하고** 사용 가능한 대체 글꼴을 보고한다.

렌더 후 **먼저 좌표로 잰다.** `python3 tools/gate.py <보고서 폴더>`의 `E7`이 쪽마다 콘텐츠
경계를 실측해 판면(`--mt`/`--mb`/`--ml`/`--mr`) 침범을 잡는다. 육안 검토는 이 결함을 놓친다 —
쪽이 넘쳐 다음 쪽으로 밀려난 이미지가 그 쪽의 불투명한 배경 밑에 깔려, 렌더 PNG를 전부
넘겨봐도 보이지 않은 사례가 있다(캡션만 앞 쪽에 남아 캡션과 이미지가 갈라진 상태였다).

넘쳤으면 **표를 줄이지 말고 표 옆의 서술을 줄인다.** 앞 문단은 결론 한 문장으로, 뒤 해석
문단은 각주 한 줄로 옮긴다. 근거를 버리지 않고 위치만 바꾸는 것이 압축의 방향이다. 코드
블록과 이미지가 한 쪽에 다 안 들어가면 처음부터 쪽을 나눈다.

그 다음 `pdftoppm -r 144 -png`로 전 쪽을 PNG로 만들어 잘림·겹침·왜곡·깨진 한글을 확인한다.
**여백 과다**(빈 쪽)도 같이 본다 — 콘텐츠의 마지막 y좌표와 하단 여백 기준선(`--mb`) 사이
채움 비율을 스캔한다. 목표치는 가이드일 뿐 강제하지 않는다. 짝지을 상대가 구조적으로 없는
마지막 항목이면 그대로 둔다. 썸네일 육안 판단은 오차가 크므로 반드시 픽셀 스캔으로 실측한다.
결함이 있으면 HTML을 고쳐 다시 렌더한다. 최신 렌더가 깨끗할 때만 최종 파일로 채택한다.

## 6. 검증

`python3 tools/gate.py <보고서 폴더>`를 실행하고 결과를 §8 보고에 포함한다.
BLOCK이 남으면 완료를 선언하지 않는다. 별도의 수기 체크리스트는 두지 않는다.

브리프의 R0~R4는 작성 전 `python3 tools/gate.py prompts`에서 이미 확인하며 여기서 반복하지 않는다.

## 7. 중단 조건

다음 상황에서는 사실을 만들거나 우회하지 말고 원인을 보고한다.

- 프로젝트가 빌드되지 않거나 실행되지 않는다.
- API 문서 경로를 찾을 수 없다. 요구된 기능이 코드에 존재하지 않는다.
- 실행 데이터가 없어 시나리오를 재현할 수 없다. 이미지가 누락되었거나 손상되었다.
- 한글 글꼴을 등록할 수 없다. PDF 렌더러가 없고 설치도 허용되지 않는다.
- 승인 없이는 수행할 수 없는 외부 변경이 필요하다.

일부 시나리오만 실패한 경우 전체를 포기하지 않는다. 성공한 검증과 실패한 검증을 분리하고,
실패 원인을 확인한 뒤 사실대로 기술한다.

## 8. 출력 구조와 ZIP

ZIP에는 Markdown, 참조 이미지 폴더, 최종 PDF, 간단한 파일 안내를 넣는다. ZIP 내부에서도
Markdown의 상대 이미지 경로가 유효해야 한다.

다음은 ZIP과 제출 폴더에 **넣지 않는다.**

```text
.superpowers/  .claude/  .aider*  .cursor/          ← 도구 세션 흔적
*프롬프트*.md  *하네스*.md  reference/               ← 생성 지시서 원문
tmp/  build/  bin/  .gradle/  __pycache__/          ← 빌드·중간 산출물
.DS_Store  .env  *.key  *.pem                       ← OS·비밀
output/sample/  tools/report_sample/  docs/**/specs/ ← 샘플·계획 문서
```

패키징 직후 `python3 tools/gate.py <ZIP 해제 경로>`로 확인한다. H1이 뜨면 다시 만든다.

## 9. 최종 보고

```text
보고서 생성과 검증을 완료했습니다.

- Markdown: [경로]
- HTML: [경로]
- PDF: [경로]
- ZIP: [경로]

검증: A4 N쪽, 이미지 N개, 실행 시나리오 N건(성공 N / 실패 N).
게이트: BLOCK 0 · WARN N
렌더 검수에서 잘림·겹침·왜곡·깨진 한글이 없음을 확인했습니다.
한계: (기재한 미해결 항목 요약)
```

실패 또는 미완료 항목이 있으면 성공한 것처럼 표현하지 말고 해당 항목과 원인을 같은 응답에서
분명하게 기술한다.

## 10. 실행 시작

입력값과 현재 작업 폴더를 확인하고 `mode`에 해당하는 작업을 실제로 수행하라. 조사 결과나
계획만 설명하지 말고 실행·캡처·작성·승인·렌더·검수·패키징을 끝까지 진행하라.
