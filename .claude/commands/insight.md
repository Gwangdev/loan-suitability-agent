# 인사이트 — 파이프라인 밖에서 쓰는 자산

## 이 커맨드의 자리

**실행 순서에 속하지 않는다.** `/design`·`/build`를 쓰지 않는 프로젝트에서도 단독으로 돈다.
`PROJECT_STATE.md`·`SPEC.yaml`이 없어도 동작해야 하며, 없다고 만들지 않는다.

파이프라인을 쓰는 프로젝트에서는 이 자산이 `/design` §2·§4와 `independent-verifier`를 통해
이미 로드된다. **그 경우 같은 항목을 여기서 다시 판정하지 않는다.**

## 로드

`reference/insights/INDEX.md` 먼저. 목록을 보고 **이 프로젝트에 해당하는 자산만** 로드한다.
해당 없는 자산은 열지 않는다.

## 모드

인자가 없으면 `read`다.

| 인자 | 하는 일 |
|---|---|
| (없음) · `read` | 자산을 현재 코드에 대조하고 결과를 보고한다 |
| `add <내용>` | 이번 작업에서 나온 인사이트를 수집 기록에 남긴다 |
| `promote` | 수집된 항목이 하네스 자산이 될 자격이 있는지 판정한다 |

## read — 대조

1. `tools/gate.py`가 있으면 먼저 돌린다. **기계가 세는 항목을 눈으로 다시 세지 않는다.**
2. 원칙 자산(`backend-hardening.md` 등)을 대조한다. 미적용 항목은 **결함**이다.
3. 후보 자산(`backend-adoption-candidates.md` 등)을 대조한다. 미채택 항목은 **결함이 아니다.**

보고는 두 목록을 **분리해서** 낸다.

```
결함 (조치 필요)
- <항목> — 근거 위치 · 판정 이유
후보 (판정 필요)
- <항목> — 가치가 생기는 조건 · 지금 넣을 때의 비용 · 권고
```

**결함에는 반드시 처리 상태를 붙인다** — 고쳤다 / 안 고쳤고 사유는 이것 / 미결로 남긴다.
후보 목록에 섞어 넣어 사용자가 고르지 않았다는 이유로 사라지게 하지 않는다.
후보는 사용자가 고르지 않으면 사라져도 된다.

## add — 수집

코드리뷰·개발 중에 나온 재사용 가능한 판단을 **그 자리에서** 남긴다. 세션이 끝나면 사라진다.

기록 위치:
- `PROJECT_LOG.md`가 있으면 그 파일의 「인사이트 수집」 절
- 없으면 프로젝트 루트 `INSIGHTS.md` (없으면 만든다)
- **하네스 저장소 자신이면 항상 루트 `INSIGHTS.md`.** 그곳의 `PROJECT_LOG.md`는 기록이 아니라
  복사되는 템플릿이므로, 여기 쓰면 다음 프로젝트마다 남의 항목을 짊어진다.
  판별은 게이트의 `HARNESS_MODE`와 같다 — `.claude/agents` 또는 `.claude/commands`가 있으면 하네스 저장소다

형식 — 한 항목 네 줄:

```
- **<한 줄 규칙>**
  - 종류: 원칙 | 후보 | 미판정
  - 왜: <이 규칙이 성립하는 이유. 사건 서술이 아니라 이유>
  - 범위: 이 프로젝트만 | 같은 스택 | 스택 무관
```

**규칙 문장으로 적는다.** 「이번에 이런 문제가 있었다」는 서술은 재사용되지 않는다.
자격증명·내부 URL·개인정보는 값 자체를 적지 않는다. 불변 카드의 데이터 등급 규칙이 여기에도 적용된다.

## promote — 승격 판정

수집 기록의 항목을 하나씩 다음 네 질문으로 판정한다. **하나라도 아니오면 승격하지 않는다.**

1. 특정 프로젝트·스택·인물에 국한되지 않는가
2. 「왜」가 규칙 안에 들어 있는가 — 이유 없는 규칙은 다음 프로젝트에서 판단할 수 없다
3. 기존 자산·불변 카드·게이트와 겹치지 않는가 — 겹치면 새로 쓰지 않고 **기존 문장을 고친다**
4. 기계가 셀 수 있는가 — 셀 수 있으면 문서가 아니라 게이트 축으로 간다

통과한 항목은 **원칙인지 후보인지 먼저 정하고** 해당 자산 파일에 넣을 문안까지 만든다.

승격 대상은 **하네스 저장소**이지 이 프로젝트의 복사본이 아니다.
프로젝트 폴더의 `reference/`만 고치면 다음 프로젝트에 전달되지 않는다.
**하네스 저장소 위치는 환경마다 다르므로 사용자에게 묻는다.** 경로를 문서에 기록하지 않는다.
작성 규칙은 하네스 저장소의 `MAINTENANCE.md` §1·§6·§7을 따른다.

## 완료 점검

- 결함과 후보가 분리돼 보고됐는가
- 결함 각각에 처리 상태가 붙었는가
- 수집 항목이 사건 서술이 아니라 규칙 문장인가
- 승격 판정에서 「기계가 셀 수 있는 것」을 문서로 보내지 않았는가
