# 설계 — 검증이 집중되는 단 하나의 단계

## 이 단계의 역할

**여기서 틀을 만든다. 개발은 틀로 찍어내는 반복 작업이 된다.**
설계에서 걸러내지 못한 것은 개발 단계의 자기검토로 걸러지지 않는다. 같은 컨텍스트가 자기 산출물을 다시 보는 일에는 새 정보가 없다. 그러므로 판단이 필요한 검토는 전부 이 단계에 있다.

## 로드
`CLAUDE.md` 불변 카드 준수 + `PROJECT_STATE.md` read.

## 1. 범위와 규제 확정

- 문제 정의, 주요 사용자, 정상 흐름과 실패 시나리오
- 핵심 요구사항 — **각각에 검증 가능한 수용 기준을 연결한다**
- **포함·제외 범위.** 제외를 명시적으로 적는다. 적지 않은 것은 만들지 않는다
- **적용 법령·인허가·감독규정·업계 표준**
- **데이터 등급과 취급 방식**, **금지 자동화 행위**

규제·인허가·데이터 등급·금지행위가 미확정이면 **진행을 멈추고 질문한다.** 경미한 누락으로 처리하지 않는다.

## 2. 기술 선택

- 프레임워크·표준 라이브러리가 제공하는 기능은 **기본 채택**한다
- 직접 구현하려면 **사유를 여기에 적는다.** 사유 없는 자체 구현은 설계 결함이다
- 인증·인가·암호화·세션·검증·직렬화·스케줄링은 특히 그렇다

서버·DB·컨테이너 배포가 있는 프로젝트면 `reference/insights/backend-adoption-candidates.md`를 로드해
항목별로 **채택·보류를 판정하고 사유를 여기에 적는다.** 보류도 결정이므로 기록한다. 해당 없으면 로드하지 않는다.

## 3. `SPEC.yaml` 작성 — 이 단계의 핵심 산출물

프로젝트 루트에 쓴다. **여기 없는 것은 만들지 않는다.**

```yaml
version: 1

endpoints:
  - GET /api/orders
  - GET /api/orders/{id}
  - POST /api/orders
  - DELETE /api/orders/{id}

exclude:
  - endpoint: GET /actuator/health
    reason: 프레임워크 제공, 명세 관리 대상 아님
```

규칙:
- **요구사항 하나가 엔드포인트 0개면 그 요구사항은 이 시스템의 것이 아니다.** 범위에서 빼거나 요구사항을 고친다
- **엔드포인트 하나가 요구사항에 걸리지 않으면 지운다.** 「있으면 좋을 것」은 과잉 구현의 씨앗이다
- 경로 변수명은 대조에 쓰이지 않는다(`{id}`와 `{orderId}`를 같게 본다). 읽는 사람을 위해 쓴다
- 프레임워크가 자동으로 여는 경로는 `exclude`에 **사유와 함께** 적는다

## 4. 논리 검토 — 사람·독립 수단이 보는 유일한 지점

`gate.py`는 명세와 코드가 **일치하는지**만 본다. **명세 자체가 옳은지는 보지 못한다.** 그 판단이 여기 있다.

- **논리적 오류:** 상태 전이가 닫혀 있는가. 도달 불가능한 상태나 빠져나올 수 없는 상태가 있는가
- **요구사항 대비 정합:** 각 요구사항이 명세의 어느 항목으로 충족되는가. 대응이 없는 요구사항, 요구사항이 없는 명세 항목을 각각 짚는다
- **형제 대칭성:** 같은 축의 자원이 같은 연산을 제공하는가. 비대칭이면 **사유를 적는다**
- **오류 응답:** 같은 성격의 실패가 같은 상태 코드로 나가는가
- **권한 표면:** 식별자를 바꿔 넣으면 타인의 자원에 접근되는가. 상태 변경 연산에 권한 검사가 있는가

- **배포 경계:** 계층 격리·상시 노출·상태 확인의 실효성. 배포 구성이 있으면
  `reference/insights/backend-hardening.md`를 함께 기준으로 삼는다. **미적용은 결함이고, 사유 없이 넘기지 않는다**

`reference/design-review-checklist.md`를 기준으로 삼는다. **판단이 갈리는 항목은 사용자에게 올린다.**

## 5. 명세 개정 — 개발 중 추가가 필요해졌을 때

`/build` 도중 명세에 없는 것이 필요해지면 여기로 돌아온다. **1~4를 전부 다시 돌지 않는다.** 아래만 한다.

### 5.1 먼저 판정한다

| 질문 | 예 | 아니오 |
|---|---|---|
| 이미 승인된 요구사항을 충족하는 데 **반드시** 필요한가 | 설계 누락 → 5.2 | ↓ |
| 사용자가 새로 요구한 것인가 | 범위 확장 → 5.2 (요구사항부터 추가) | ↓ |
| — | | **「있으면 좋을 것」이다. 지운다** |

**세 번째가 기본값이다.** 앞의 둘에 해당한다고 말하려면 어느 요구사항인지 지목할 수 있어야 한다. 지목하지 못하면 세 번째다.

### 5.2 개정 범위 검토 — 추가되는 항목에 대해서만

- **형제 대칭성:** 같은 축의 다른 자원에도 같은 연산이 필요한가. 한쪽에만 넣는다면 사유를 적는다
- **오류 응답:** 이 항목의 실패가 기존 항목과 같은 상태 코드로 나가는가
- **권한 표면:** 식별자를 바꿔 넣으면 타인의 자원에 접근되는가. 상태 변경이면 권한 검사가 있는가
- **부속 규격:** 이 추가가 기존 설계 결정을 뒤집는가. 뒤집는다면 **무효화되는 부속 규격을 함께 적는다** (안 적으면 껍데기가 남는다)

### 5.3 기록

- `SPEC.yaml`에 항목 추가
- `PROJECT_LOG.md`의 **명세 개정 이력**에 한 줄: 추가 항목 / 사유(요구사항 지목 또는 새 요구사항) / 개정 시각
- 범위 확장이면 요구사항과 수용 기준을 `PROJECT_LOG.md`에 먼저 추가한다

### 5.4 승인

**범위 확장은 사용자 승인을 받는다.** 설계 누락 보완은 승인 없이 진행하고 개정 이력만 남긴다.
둘의 차이는 「사용자가 요구한 적 있는가」다.

개정이 끝나면 `/build`로 돌아간다.

**개정 이력이 길어지면 그것 자체가 신호다.** 설계 단계가 얕았다는 뜻이므로 다음 프로젝트에서 `/design`에 시간을 더 쓴다.

## 완료 점검

- `SPEC.yaml`이 존재하고 `python3 tools/gate.py .`가 `S0`(형식 오류)를 내지 않는다
- 요구사항·수용 기준·기술 선택 사유는 `PROJECT_LOG.md`에 쓴다
- `PROJECT_STATE.md`에 불변 항목·현재 유효한 설계 결정·다음 작업=`/build`를 기록하고 버전+1
- `/compact` 실행

## 실패 시
원인·영향 기록 → `PROJECT_STATE.md`에서 복구 → 재실행 범위 명시.

---

**끝에 규제·금지행위·중단 기준을 다시 명시하고 사용자 승인을 요청한다.**
**이것이 개발 착수 전 마지막 승인 지점이다. 승인 없이 `/build`로 이동하지 않는다.**
