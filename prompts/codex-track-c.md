# Codex 작업 지시 — Track C (엔드포인트 구현 이후)

## 상황

`loan-suitability-agent` — 대출 상담 의사결정 지원 서비스. FastAPI 모듈러 모놀리스.
브랜치 `feature/decision-support-rebuild`, HEAD `356252b`, 커밋 43건. **작업 트리는 깨끗하다.**

**`SPEC.yaml`의 엔드포인트 9개가 전부 구현됐다(`S3`·`S4` 0건).** 남은 것은 표면을 늘리는
일이 아니라, **이미 한 주장을 증거로 바꾸는 일**이다.

## 코드 배치 — 기능 하나가 파일 하나다

```
loan_agent/api/__init__.py       라우터 등록만
loan_agent/api/errors.py         RFC 9457 problem+json — 전 구간 공통
loan_agent/api/health.py         /health/live · /health/ready
loan_agent/api/assessments.py    심사 생성·단건조회·목록
loan_agent/api/explanations.py   설명 재생성·이력 (+ 시도 메타데이터 직렬화)
loan_agent/api/parsing.py        파싱 미리보기 — DB를 쓰지 않는다
loan_agent/api/demo.py           녹화 데모 조회 — 키도 DB도 쓰지 않는다
loan_agent/decision.py           판정 결과를 저장 가능한 형태로 변환 + 버전 확정
loan_agent/db/                   models · engine · readiness
```

**의존은 한 방향으로만 흐른다** — 심사가 설명을 가져다 쓰고 그 반대는 없다.
표면을 추가하는 것이 아니므로 **이 배치를 바꾸지 마라.** 새 파일이 필요하다고 느끼면
기능이 하나 더 생긴다는 뜻이니 보고해라.

## 먼저 읽어라 — 내용을 여기 옮겨 적지 않았다. 파일을 직접 열어라

| 파일 | 무엇이 있는가 |
|---|---|
| `PROJECT_STATE.md` | 현재 상태·불변 항목·유효한 설계 결정. **컨텍스트와 충돌하면 이 파일이 이긴다** |
| `SPEC.yaml` | 공개 표면 9개 + 오류 코드 정책·목록 상한 |
| `docs/설계결정.md` | ADR 22건. 각 항목에 **기각한 대안과 사유**가 있다 |
| `docs/데이터모델.md` | ERD·상태 전이·제약·**인덱스 2단 분리** |
| `docs/리스크_통제_대장.md` | 리스크별 **검증 방법** 칸이 이번 작업의 대상이다 |
| `PROJECT_LOG.md` §구현 상태 · §측정 계획 | 확정된 관례와 **무엇을 어떤 기준으로 잴지** |

## 절대 규칙

1. **커밋하지 마라.** `git commit`·`push`·`checkout`·`stash` 금지. 변경만 남기고 보고한다.
2. **`SPEC.yaml`에 없는 공개 표면을 만들지 마라.** 필요하다고 느끼면 만들지 말고 보고해라.
3. **주석에 태그·번호를 쓰지 마라.** 원인 → 과정 → 결론을 자연어로. 게이트 `L2`가 BLOCK한다.
4. **테스트를 먼저 쓰고 실패를 확인한 뒤 구현해라.** 곧바로 통과하면 이미 구현됐거나
   아무것도 검사하지 않는 것이다. 어느 쪽인지 확인 전에 넘어가지 않는다.
5. **측정값을 일반화하지 마라.** 실행 환경과 데이터 건수를 반드시 함께 적는다.

# C1. `app.py`를 API 클라이언트로 배선 — 가장 중요하다

**지금 compose는 `ui → app → postgres` 3-tier인데 `app.py`가 `core`를 10곳에서 직접 부르고
API를 한 번도 거치지 않는다.** 구조는 선언돼 있으나 실행 경로가 그것을 지나가지 않는다.

이대로면 「3-tier 보안을 안다」는 주장이 **문서상 사실로만 남는다.** 화면에서 심사를 눌렀을 때
요청이 실제로 `app` 계층을 지나 DB에 닿아야 그 주장이 증거가 된다.

- `app.py`가 `core.screen_loan`을 직접 부르는 자리를 **`POST /api/v1/assessments` 호출로 교체**한다.
  API는 기능별 모듈로 나뉘어 있으니 호출할 경로는 `SPEC.yaml`에서 확인한다
- 접속처는 환경변수(`API_BASE_URL` 등)로 받는다. compose에서 서비스 이름으로 닿는다
- `Idempotency-Key`를 클라이언트가 생성해 보낸다. 같은 입력을 두 번 눌러도 심사가
  하나여야 한다 — **서버가 이미 보장하지만, 화면이 키를 안 보내면 그 보장이 발동하지 않는다**
- API가 죽었을 때 화면이 무엇을 보여줄지 정한다. 오류 원문을 그대로 노출하지 않는다
- **무토큰 데모 경로는 키·API 없이도 동작해야 한다**(핵심 요구사항). 이 경로까지 API에
  묶지 마라. 묶으면 「키 없이 열람 가능」이 깨진다
- `core`를 직접 부르는 것이 정당한 자리가 남는다면(예: 규칙기반 파싱 미리보기) **왜 그런지
  주석에 남겨라.** 사유 없이 남은 직접 호출은 배선 누락과 구분되지 않는다

끝나면 `docker compose up`으로 **실제로 화면 → API → DB가 이어지는지 확인**하고 그 결과를
보고해라. 코드만 바꾸고 확인하지 않으면 이 작업은 끝난 것이 아니다.

# C2. ADR-016 리소스 상한 — 런타임 강제 확인

`docker compose config`에는 `cpus: 0.5`·`memory: 536870912`로 반영돼 있다. 그런데 ADR-016이
요구한 확인은 **런타임이 실제로 적용하는가**이다. 오케스트레이터 전용 키로 취급돼 조용히
무시되는 버전이 있고, 그 경우 「상한을 걸었다」는 문서상 사실만 남는다.

- `docker compose up` 후 컨테이너의 실제 제한을 확인한다(`docker inspect`의 `HostConfig`,
  또는 `docker stats`의 LIMIT 열)
- **반영되면** 확인 방법과 결과를 `PROJECT_LOG.md`에 남긴다
- **무시되면** 런타임이 지원하는 키로 바꾸거나, **채택을 보류하고 사유를 기록해라.**
  무시되는 설정을 남겨 두는 것이 가장 나쁘다

# C3. 부하 테스트 — T1 #8

`PROJECT_LOG.md` §측정 계획에 무엇을 어떤 기준으로 잴지 이미 적혀 있다. 그대로 따른다.

- **대상은 결정적 경로(`POST /api/v1/assessments`)뿐이다.** 설명 생성 경로는 LLM 제공자
  지연이 지배하므로 우리 시스템 성능을 재지 못한다 — 재면 제공자를 재는 것이다
- 지표: p50·p95·p99 지연, 처리량, 오류율 / 조건: 동시 10·50·100, 각 60초
- **합격·불합격 기준을 두지 마라.** 포트폴리오 규모에서 SLO를 선언하면 근거가 없다.
  목적은 **어디서 꺾이는지(포화점)를 찾는 것**이다
- ADR-022의 계산(100 req/s에서 필요 커넥션 ≈ 1개)이 맞는지 여기서 검증된다.
  **풀이 포화되기 전에 다른 곳이 먼저 꺾이면 계산이 옳았다는 증거다**
- 하드웨어·데이터 건수·풀 설정을 결과와 함께 적는다

# C4. 인덱스 전후 비교 — T1 #4

ADR-014가 이것을 위해 마이그레이션을 정합성(`0001`)과 성능(`0002`)으로 나눠 뒀다.

- 합성 심사 이력 10,000건을 생성한다
- `0002` **적용 전** `EXPLAIN ANALYZE`로 `status + created_at DESC` 조회를 측정
- `0002` 적용 후 같은 쿼리를 다시 측정
- 실행계획이 어떻게 바뀌었는지(Seq Scan → Index Scan 등)와 시간을 함께 기록
- **복합 인덱스 컬럼 순서의 근거**(등호 조건 먼저, 범위·정렬 나중, `id`는 커서 tiebreaker)가
  실측으로 뒷받침되는지 확인한다

# C5. 토큰 비용 모델 — T1 #10

`explanation_run`에 `input_tokens`·`output_tokens` 컬럼이 이미 있다. 남은 것은 노출이다.

- 요청당 평균 토큰 → 단가 적용 → 요청당 비용 → 월 N건 추정
- **단가는 상수로 분리하고 출처·기준일을 함께 적어라.** 단가는 바뀌므로 본문에 숫자를
  박으면 문서가 조용히 틀려진다
- 3-Agent 구조의 비용을 정직하게 드러내는 것이 목적이다. 경계 3개는 LLM 3턴이고
  ReAct 재조회가 더해진다

# C6. README 한계 절 — 게이트 `D2`

README에 한계·미해결 절이 없다. 결손 0건으로 보이는 보고서는 신뢰를 잃는다.

- 합성 데이터·단순화된 DSR·검증 범위·미검증 범위를 명시한다
- **`docs/리스크_통제_대장.md`의 「알려진 한계」·「남은 타협」을 옮겨 적지 말고 요약하고
  가리켜라.** 같은 내용이 두 곳에 있으면 한쪽만 갱신되어 갈라진다
- 통과율을 쓸 때는 **커버리지 한계를 반드시 병기한다.** 100% 통과는 정의한 데이터셋·지표
  안에서의 결과다
