# Codex 작업 지시 — 측정과 증거 (Track C 잔여)

## 상황

`loan-suitability-agent` — 대출 상담 의사결정 지원 서비스. FastAPI 모듈러 모놀리스.
브랜치 `feature/decision-support-rebuild`, HEAD `f5a222e`, 커밋 49건. **작업 트리는 깨끗하다.**

**구현은 끝났다.** 엔드포인트 9개 + 설명 실행기까지 있고 명세와 코드가 일치한다.
남은 것은 **이미 한 주장을 수치로 뒷받침하는 일**이다. 새 기능을 만드는 작업이 아니다.

## 먼저 읽어라 — 내용을 여기 옮겨 적지 않았다. 파일을 직접 열어라

| 파일 | 무엇이 있는가 |
|---|---|
| `PROJECT_STATE.md` | 현재 상태·불변 항목·유효한 설계 결정. **컨텍스트와 충돌하면 이 파일이 이긴다** |
| `PROJECT_LOG.md` §측정 계획 | **무엇을 어떤 기준으로 잴지 이미 정해져 있다. 그대로 따른다** |
| `docs/설계결정.md` | ADR 23건. 각 항목에 기각한 대안과 사유 |
| `docs/데이터모델.md` | 인덱스 2단 분리의 근거와 컬럼 순서 |
| `SPEC.yaml` | 공개 표면 + 비HTTP 표면(워커) |

## 코드 배치 — 바꾸지 마라

```
loan_agent/api/       errors · health · assessments · explanations · parsing · demo
loan_agent/worker.py  설명 실행기 (PENDING 클레임 → 실행 → 기록)
loan_agent/decision.py 판정 변환 + 버전 확정
loan_agent/db/        models · engine · readiness
alembic/versions/     0001_integrity(제약만) · 0002_performance_indexes(성능)
```

**이번 작업은 표면을 늘리지 않는다.** 새 파일이 필요하다고 느끼면 기능이 하나 더
생긴다는 뜻이니 만들지 말고 보고해라. 측정 스크립트는 예외이며 `tests/load/` 아래에 둔다.

## 절대 규칙

1. **커밋하지 마라.** `git commit`·`push`·`checkout`·`stash` 금지. 변경만 남기고 보고한다.
2. **주석에 태그·번호를 쓰지 마라.** 원인 → 과정 → 결론을 자연어로. 게이트 `L2`가 BLOCK한다.
3. **측정값을 일반화하지 마라.** 하드웨어·데이터 건수·설정을 반드시 함께 적는다.
4. **합격 기준을 만들지 마라.** 이 규모에서 목표치를 선언하면 근거가 없다.
   알아야 할 것은 **어디서 꺾이는가**이다.
5. 기존 마이그레이션 두 개를 **합치지 마라.** 나뉘어 있는 것이 C2의 전제다.

## 환경

```bash
pytest                        # python3는 3.14로 잡혀 의존성이 없다. 3.11을 쓴다

```

## 기준선 — 새로 늘어난 것만 네 책임이다

```
pytest        88 passed
test_gate     91/91
gate          BLOCK 1 · WARN 8       (S3·S4 0건)
gate --commit COMMIT READY
```

`BLOCK 1`은 `G3`(과거 커밋 이력)이며 **이력 재작성 없이는 해소되지 않는다. 판정이
끝난 항목이니 건드리지 마라.** WARN 8건도 전부 판정 완료분이다.

# C1. 인덱스 도입 전후 비교 — Docker 불필요

마이그레이션이 정합성(`0001`)과 성능(`0002`)으로 나뉜 이유가 이것이다. 한꺼번에 만들면
전후를 잴 수 없다.

- 합성 심사 이력 **10,000건**을 생성한다. 생성 스크립트는 재현 가능해야 한다
- `0002` **적용 전** `EXPLAIN ANALYZE`로 `status` 필터 + `created_at DESC` 정렬 조회를 측정
- `0002` 적용 후 같은 쿼리를 다시 측정
- **실행계획이 어떻게 바뀌었는지**(Seq Scan → Index Scan 등)와 시간을 함께 기록
- 복합 인덱스 컬럼 순서의 근거 — 등호 조건 먼저, 범위·정렬 나중, `id`는 커서
  tiebreaker — 가 실측으로 뒷받침되는지 확인한다. **어긋나면 그 사실을 보고해라**

`alembic downgrade`/`upgrade`로 상태를 오갈 수 있다. **측정 후 반드시 head로 되돌려라.**

# C2. 부하 측정 — Docker 불필요

`PROJECT_LOG.md` §측정 계획에 조건이 이미 적혀 있다. 그대로 따른다.

- **대상은 결정적 경로(`POST /api/v1/assessments`)뿐이다.** 설명 생성 경로는 제공자
  지연이 지배하므로 우리 시스템을 재지 못한다 — 재면 제공자를 재는 것이다
- 지표: p50·p95·p99 지연, 처리량, 오류율 / 조건: 동시 10·50·100, 각 60초
- **멱등 키를 요청마다 새로 만들어라.** 같은 키를 재사용하면 두 번째부터 기존 심사를
  돌려주는 경로로 빠져 생성 성능이 아니라 조회 성능을 재게 된다
- ADR-022가 「100 req/s에서 필요 커넥션 ≈ 1개」라고 계산했다. **풀이 포화되기 전에
  다른 곳이 먼저 꺾이면 그 계산이 옳았다는 증거다.** 어디가 먼저 꺾이는지 보고해라

# C3. 토큰 비용 모델

`explanation_run`에 토큰 컬럼이 있고 워커가 채운다. 남은 것은 노출이다.

- 요청당 평균 입력·출력 토큰 → 단가 적용 → 요청당 비용 → 월 N건 추정
- **단가는 상수로 분리하고 출처·기준일을 함께 적어라.** 단가는 바뀌므로 본문에 숫자를
  박으면 문서가 조용히 틀려진다
- 3-Agent 구조의 비용을 정직하게 드러내는 것이 목적이다. 경계 3개는 LLM 3턴이고
  ReAct 재조회가 더해진다

# C4. 컨테이너 리소스 상한 — **여기만 Docker가 필요하다**

`docker compose config`에는 `cpus: 0.5`·`memory: 536870912`로 반영돼 있다. 그런데
ADR-016이 요구한 확인은 **런타임이 실제로 적용하는가**이다. 오케스트레이터 전용 키로
취급돼 조용히 무시되는 버전이 있고, 그 경우 「상한을 걸었다」는 문서상 사실만 남는다.

- `docker compose up` 후 실제 제한을 확인한다(`docker inspect`의 `HostConfig`,
  또는 `docker stats`의 LIMIT 열)
- **반영되면** 확인 방법과 결과를 기록한다
- **무시되면** 런타임이 지원하는 키로 바꾸거나 **채택을 보류하고 사유를 기록해라.**
  무시되는 설정을 남겨 두는 것이 가장 나쁘다

**함께 확인할 것 — 3-tier가 실제로 이어지는가.** 화면에서 심사를 제출했을 때 요청이
`ui → app → postgres`를 지나는지, 그리고 워커가 대기 작업을 집어 상태를 옮기는지
눈으로 확인해라. 코드는 그렇게 돼 있지만 컨테이너에서 실제로 도는 것은 확인되지 않았다.

**Docker가 꺼져 있으면 C4를 건너뛰고 그 사실을 보고해라.** 나머지 셋은 영향받지 않는다.

## 순서

C1 → C2 → C3 → C4. 앞의 셋은 서로 독립이라 순서를 바꿔도 되지만, **C4는 마지막에 둔다** —
Docker 상태에 따라 못 할 수 있고 그것이 나머지를 막으면 안 된다.

## 끝내고 보고할 것

1. 무엇을 했고 무엇을 못 했는가
2. `pytest`와 `python3.11 tools/gate.py .`의 **실제 출력**. 기준선 대비 증감
3. **측정 결과는 조건과 함께** — 하드웨어·데이터 건수·풀 설정·실행 환경
4. **예상과 어긋난 지점.** 특히 인덱스 컬럼 순서 근거가 실측과 다르거나,
   부하에서 커넥션 풀이 먼저 꺾였다면 그것은 ADR의 계산이 틀렸다는 뜻이다
5. 명세에 없는 것이 필요하다고 느낀 지점 — **만들지 말고 보고해라**
